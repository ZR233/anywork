# 测试质量与必要性

以最少且充分的测试证明完整功能。先找已有行为证明，再决定是否增强；只有缺少独立证明时才新增。新增配置、参数、平台实例或历史问题不自动要求新增测试，测试数量和覆盖率不是交付目标。

## 按需阅读

- [测试设计与审计](references/design-and-audit.md) 提供必要性、层级和缺陷敏感度的判断方法，可按问题选择相关章节。
- 只有解释方法论、比较定义、提供研究依据或讨论删测依据时，才阅读[方法论依据](references/evidence.md)。
- Rust 实现与接口使用 `rust-code-quality`、`rust-api-design`；并发或取消使用 `rust-concurrency-safety`；unsafe、FFI 或 FRB 安全边界使用 `rust-unsafe-safety`。
- 原生 GUI、生成文件与 Driver 可参考 `flutter-studio-build`；工程入口和授权边界见 [AGENTS.md](../../../AGENTS.md)，不据此增加固定测试流程。

## 判断维度

以下是分析方法，不是每次任务的必经步骤或报告表单。

1. 说明什么输入或操作必须产生什么结果，哪种生产实现错误会破坏它。
2. 查找已有测试，判断独立行为、缺陷敏感度、独特信号、最小充分层级和长期成本。
3. 优先复用或增强完整行为证明。同一回归在错误实现失败、修复后通过可增强缺陷敏感度证据，不要求每个 bug 新增用例或固定先红后绿流程。
4. 同时说明测试目标与执行条件；公开 API 集成测试遵循真实接口，替身仅提供环境，不重新实现被测行为。
5. 审计给出保留、重写、下移、移出门禁或删除结论，核对独特失败信号、真实集成证据及运行器发现与失败传播仍然存在。

测试必须区分正确与错误实现。配置回读、生产清单镜像、无语义的常量／文案锁定和替身自测不形成独立证明；真正的协议、布局、兼容性或历史失败边界仍须保护。通用测试使用具体的合成样例和必要边界，不以去掉具体值、弱化断言或合成巨大用例冒充泛化。

## 交付

结论可说明相关风险、层级、环境、判定及与已有证明的关系。内部失败必须传递到最外层运行器；零测试、缺失执行、取消或预算耗尽不能冒充成功。不通过弱化断言、无限重试或静默跳过制造绿色。
