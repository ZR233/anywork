# Flutter／FRB／Rust 跨层设计

先确定数据语义、协议保证与所有者，再选择接口和组件。目标是让一项事实只有一个权威写入口，
让界面只表达观察需求与用户意图；不为每个功能新增 Manager、Facade、UseCase 或事件总线。

## 适用边界

产品接口以 `{workspace}/design/README.md` 指向的权威文档为准。Native 自有领域与 ACP 等
外部协议分别遵守各自保证：不能把 Native 的历史、修订、ACK、恢复或持久化机制强加给外部协议，
也不能为外部协议没有承诺的能力增加回读验证、补偿缓存或成功保证。
ACP 历史与业务流按 `design/28`：只保存产品关联，使用官方类型化接收入口，不同时消费两条
更新路径或让显示端背压堵塞协议控制。目录/Native root-only mode 按 `design/17` 区分后端，
不能用 Native 空闲状态、模型或工作流默认值填补 ACP 字段；完整 ACP 呈现不属于目录适配。
SSH 项目中的 ACP 仍在宿主运行，业务工具经 Host MCP 复用普通会话远程绑定；前端消费真实
业务根，不把 ACP 本机协议 cwd 当作项目路径，也不维护一份远程执行或任务事实。
本文提供设计方法与演进方向，不表示现役接口已完成迁移；改变产品契约时同步其权威文档与调用方。

先区分可变当前态、可变查询结果、不可变历史、命令回执、临时通知、用户草稿和资源句柄。
不可变完成集合的规则不能推广到所有列表；持续观察也不是所有查询的默认形式。

文中 `{workspace}` 指当前仓库根；跨目录引用按仓库根描述，技能内部参考使用相对路径。
技能不维护第二份 DTO、预算、依赖版本或页面库清单；生成和构建使用 flutter-studio-build。

## 开始改动前回答

1. 谁定义事实与协议保证？明确原生领域和外部协议的边界，不推导对端未提供的能力。
2. 页面需要一次读取，还是在可见期间持续获得最新结果？写清查询条件、排序和有界窗口。
3. 若需要持续观察，初始值与后续变化如何覆盖同一时间边界？数据及现役契约中的版本、成员资格必须说明共同来源；一次性或不支持观察的外部接口不补造通知。
4. 命令结果、通知和查询结果在哪里提交？同一资源只有一个写入口，视图不合并第二份业务列表。
5. 接口承诺哪个完成点？按现役领域或外部协议解释 Future、回执和通知；只有契约确实区分受理、完成、可查询、消费或保存时才分别处理，不为普通成功响应增加验证回读、ACK 或屏障。
6. 失效、恢复与关闭影响什么？范围应与资源或查询一致，不牵连无关历史、草稿和业务任务。
7. 可以删除哪些重复职责？复用现有领域观察、只读投影、组件与资源 owner；不要用刷新和重试修补不完整契约。

异步交接与关闭需单独核对三种顺序：同步通知可能重入关闭，因此先登记任务和资源完成责任，
再发布状态；资源由旧 owner 转给新 owner 后，旧引用的释放不能被“已关闭、不再派发”检查跳过；
呈现接管只结束对应的临时展示责任，不提前取消仍需真实回执、执行或保存证据的观察。
回归优先覆盖“重试后同轮关闭”“呈现早于回执”“回执后保存证据未齐时呈现”，不要以发送主路径通过代替这些证明。
平台回调若返回 FutureOr（例如借用文件的拖放回调），薄适配层必须返回完整异步操作，
不能用 void 回调截断底层的借用窗口或错误传播。

只读镜像、有界在途数据和局部 UI 状态不是第二事实源。必要的身份检查、取消与背压不能因
“简化”直接删除；应在原 owner 内实现一次，避免逐页复制。

按风险读取 rust-code-quality、rust-api-design、rust-concurrency-safety、rust-unsafe-safety 与 test-quality；
不因本技能固定追加全量测试。交付时说明改变的边界、删除的重复职责、保留的协议限制与实际验证范围。
