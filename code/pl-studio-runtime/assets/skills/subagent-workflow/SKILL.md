# 子代理协作方法

本技能帮助选择低协调成本的组织方式，不另设审批、完成或等待协议。角色所有权、实质停工、可靠报告和资源责任遵循共用系统合同；工具调用以当前声明为准。

## 先选工作单元，再选代理

- 用可独立验收的交付切分，而非按文件数量或为了填满容量拆分。比较省下的工作与新增上下文、启动、交接、审查和合并成本；紧密串行的小工作通常直接处理更快。
- 只在真实依赖存在时记录依赖图。先确定共享接口、输入输出与错误语义，再划分互斥写范围；探索只回答具体未知问题，不重做已有调查。
- 限制同时在途的工作，以可及时接收、审查和整合为准，不把代理全部忙碌当成效率。优先解除关键路径阻塞、完成已开始的工作；独立成果就绪后无需无理由等整批。

## 选择执行环境

从实际可用目录按职责、工作区模式、工具能力与冻结权限选择 Profile，不靠名称猜能力。模型选择服从当前分发模式和偏好，不在这里维护模型清单或价格表。

先识别 Profile 的 Native/ACP 后端。自动选模与 `modelSelection` 只服务 Native child；ACP child 引用实际用户级服务定义，使用其新会话默认配置，不填假的模型、effort 或持久输入序号。ACP 不承接 Native structured review、workflow 或 `writablePaths` 限制；声明与宿主校验均按实际支持范围裁剪。

ACP 调用宿主协作时使用实际暴露的 `anywork_` MCP 工具。其 `wait_agent` 读取源报告，续跑保留返回 cursor；最新报告可能早于刚发送的消息，取消或失败也可能属于被替换的旧轮，须核对真实身份。Native 继续使用原通用等待、收件箱与报告机制。前缀和提示词不能禁用外部 agent 自有工具，也不能替代宿主权限检查。

ACP v1 未公告 HTTP MCP 不等于没有 MCP；宿主可提供标准 stdio 接入。HTTP 与 stdio 使用同一 MCP 服务逻辑，stdio 经本地 IPC 调用原运行时，不经 HTTP MCP 桥接。临时连接和凭据由宿主配置，不要求模型修改服务自己的 MCP 设置。协议能力、收到配置、实际连接与真实工具调用分别核对，不能仅凭模型自述或注入成功宣称协作可用。

派发参数的必填条件以工具声明为准，不猜默认值。失败先核对原回执、当前声明与已知路由，只纠正有依据的差异。相同原因没有新证据时停止重试，不通过放宽写范围、创建空任务探针或扫描用户 home、配置与日志碰运气；需要未获授权的诊断或目录信息不足时，报告阻塞。

| 工作关系 | 可考虑的组织方式 | 主要代价 |
| --- | --- | --- |
| 互斥文件、共同基线、低集成风险 | directory 分工，明确写范围 | 必须协调共享依赖及 Git 写入 |
| 需要物理隔离、独立编译或提交 | worktree | 基线、合并冲突与工作树回收成本 |
| 跨模块耦合、难以拆开验收 | 先收敛契约，再集中实施或接管 | 交接范围与责任必须清楚 |
| 需要独立审查 | review 绑定实际交付者 | 被审版本必须能核对 |

这些不是固定阶段或人数配方。没有可绑定的执行者时，不为获取 review 工作区虚设交付；主代理直接核对自己的成果，必要时只读探索提供事实意见，不冒充正式审查批准。

## 规划时先解除共享环境依赖

规划阶段可以在已有授权与实际写权限内准备理解代码所需的最小、可逆工具环境，不必等业务实施计划批准；环境配置本身是交付目标时仍遵循该任务的实施批准边界。准备不覆盖显式只读、Profile、`writablePaths`、安装及外部操作审批，也不自动授权修改真实用户配置或凭据。

例如，几个 Rust 探索都需要尚未配置的 LSP 时，可先派一名窄范围 `executor` 核实执行侧工具链和官方参数、保留已有配置、准备服务并取得有意义的语义结果，再让只读 `explorer` 按独立问题并行调查。小任务也可由根直接准备；不依赖该服务的文档调查可先行。不要让多名只读探索者重复报告同一个缺配置问题，也不把先准备或并发人数设为固定门禁。

准备任务写清允许的配置路径、禁止的业务改动、可能触发的项目代码执行、完成证据与停止条件。交接实际工作区、配置来源、分析平台/features、查询结果和剩余错误；配置保存、初始化、工具发现、语义成功分别报告，真实失败只阻塞依赖它的工作。接手者复用适用服务并验证自己的符号，不重复配置；独立 worktree 不保证继承环境，共享 checkout 也不共享各自临时目录。

## 自包含派发与交接

### 将验证方案与操作执行分开

对多步骤测试、浏览器或桌面交互、命令运行与证据采集，建议主代理先设计验收，在首次验证操作前选择执行者，优先考虑将可独立交付证据的操作交出，自己处理取舍与最终判断；避免先亲自跑完整套再派人重复。通常可按下面的方法收敛，不必为每项填表：

- **给出可执行方案。** 交代被验版本与环境、前置条件、步骤及各步可观察的预期结果、通过与失败判据、证据位置、时间/资源预算和清理责任。明确哪些结果尚未验证，不把“帮我测一下”当作完整交接。
- **按操作选模型。** 先确认 Profile、工具权限及实际所需模态；命令执行、浏览器自动化与看图操作需要的能力不相同。自动模式下，在当前偏好允许的候选中结合模型描述和来源、同类操作的近期评价与指令遵循度、TTFT/TPS 及样本量、价格和返修风险做有界比较，优先考虑够用、快且经济的执行者。`computer use`、电脑操作或 `claw` 类定位可帮助发现候选，但不替代能力核对；少样本、异类任务评价和厂商描述的不确定性应保留，不编造缺失性能或以最高均分直接排名。沿用现有经济性规则，不另建评分公式、模型名单或价格表。
- **划清执行与升级范围。** 写明允许的局部恢复、何时停止并报告、哪些操作需要重新裁定；不让执行者自行放宽预期、切换账号、修改用户配置或扩大验证范围。工具使用仍遵循项目入口，模型擅长电脑操作不构成改用 GUI 点击或绕过专用自动化工具的理由。
- **接收证据，而非重复操作。** 执行者返回实际版本、步骤与结果、失败原文和产物定位；主代理核对关键证据并作验收判断。只补失败、变化或证据不足的路径，不因换了执行者就重跑；执行完成也不自动成为独立审查批准。

很小的检查、紧密串行任务、交接成本更高或没有合格执行者时，直接处理通常更合适。以上是分工建议，不禁止主代理操作，不要求每次验证都派发，也不改变固定模式路由、审批或生命周期责任。

消息可按以下结构组织，只展开相关部分，不用空模板凑篇幅：

1. **交付**：目标、非目标、可观察的完成标准。
2. **事实与契约**：基线、入口、已确认决定、接口及错误语义；必要时给关键状态转换伪代码，明确哪些只是建议。
3. **所有权**：依赖、允许改动的范围、禁区、Git 与外部操作授权；不要只给父会话链接。
4. **验证预算**：需证明的行为、已有证据、必要检查及各自唯一执行责任方。最终入口已覆盖的同一行为，不再默认给每个模块追加导入断言或重复样例；可将子任务限定为静态核对、由整合方执行集中验证。尊重用户给定范围，把“未执行”与“失败”分开。
5. **交付证据**：实际版本、差异、结果与原始产物定位；用当前会话的产物位置，不要求写入父代理临时目录。

探索补充来源和时效要求；正式审查提供完整适用计划及调整、目标身份和版本。接管时移交上述信息及未解决事项，明确原责任人停止哪些写入。资料调查可提供建议，不能将角色保留的架构与方向性写入伪装成“草稿任务”。

## Git 与验证的短反馈循环

- 从核实的基线使用短期主题分支；开始前检查脏改动和 worktree 占用，不通过强制切换、重置或暂存他人成果消除障碍。同一 checkout 的 Git 写操作由明确责任方串行处理。
- directory 交付核对实际差异，不做模拟合入。worktree 交付按真实提交及依赖整合，保留返工现场；只在必要时更新基线，不无限追赶与任务无关的主线变动。
- 共享源码在相对稳定窗口集中执行昂贵构建、生成和检查；构建锁不证明版本稳定。独立且不受其他修改影响的验证可先行，不把小批成果重新攒成大批等待反馈。
- 交接证据说明“范围、版本、环境、命令和结果”，让接管者能按系统的增量验证建议判断复用。测试设计方法使用适用的测试技能，本技能不维护另一份测试选择规则或清单。
- 有明显跨模块风险时尽早核对接口，低风险小改动可集中审阅；审查和验证以解决实际风险为目的，不按每个 commit 或代理机械增加轮次。问题交最适合且明确接管的责任方，避免在原作者间反复转述。

需要解释以上方法的依据和适用限制时，再读[工作流与 Git 研究依据](references/flow-and-git.md)；普通协作不必加载。
