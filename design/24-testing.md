# 24 - 测试与人工验收

本文说明集成测试、模拟对端、原生 GUI 验收与观察边界的整体流程，不规定具体用例写法，也不展开单元测试或组件内部实现细节。常用命令入口见 [AGENTS.md](../AGENTS.md)，CI 实际执行以工作流配置为准。

## PR 质量门禁与 CI 集成流程

`PR Quality Gate` 在 PR、`merge_group` 与主分支推送时触发。普通变更对同一次提交运行对应检查；仅包含版本文件与发行说明更新的纯发布 PR 仅做轻量识别并跳过门禁检查（混合变更或合并队列仍按普通变更执行）。

路径分类按实际受影响模块选择检查范围，混合变更取并集，重命名或复制同时检查来源与目标路径，未知路径或共享构建配置保守执行完整检查：

| 检查范围 | 触发与执行边界 |
| --- | --- |
| 文档与发布配置 | 仅协作说明、技能与设计文档改动时检查文档索引与本地链接；发布配置与脚本改动时检查发布规则与演练 |
| Rust 质量与协议语义 | 在 Linux 容器内执行格式、静态检查及工作区集成验证；Windows 与 macOS 执行各自宿主的静态检查 |
| 前端静态、生成与边界 | 检查 SDK-only 边界、格式、静态分析、导入边界及 GUI 生成产物与代码一致性，不引入原生窗口依赖 |
| Linux 桌面与原生集成 | 由上游准备作业集中构建验收工具、桥接库、辅助进程与模拟服务，经校验后分发给桌面分片与原生生命周期作业只读消费 |
| Windows / macOS 构建与服务端 | 检查各自平台完整应用构建打包与产物收集，及 Linux 服务端构建 |

同一 PR 的新提交会取消尚未完成的旧运行；主分支推送则保留每次运行结果，避免后续纯文档提交取消先前的代码检查。

桌面集成测试通过动态发现与确定性分片执行，各分片无重叠且完整覆盖同一待测集合，不另行维护第二份场景清单。桌面 `smoke` 子集保留基础跨层等待场景；`full` 子集覆盖全部受控桌面集成场景；需要真实外部账号与网络的场景（`acp_real_login`、`chatgpt_real_login`、`acp_agy_conversation`）仅在提供对应环境变量与授权条件时显式启用，不依赖运行期跳过伪装通过。

Linux CI 的桌面与原生作业在每次独立运行编号下创建隔离输出目录，避免复用旧缓存或旧证据；失败时保留脱敏日志、模拟对端请求记录、场景报告与进程退出诊断。除纯版本发布外，`ci-gate` 汇总全部分片和必需作业状态，只有确认计划允许跳过的非必需作业才不阻塞合入。

## 24.1 现有测试基础设施

桌面与运行时集成入口按跨层边界组织，不同入口的观察结论互不替代：

| 入口 | 环境与观察边界 |
| --- | --- |
| 运行时与协议集成 | 本地回环协议对端、临时数据库与受控工作区，观察会话生命周期、取消、恢复、迁移及故障传播 |
| 桌面端集成（`desktop`） | 完整 Flutter 桌面应用、真实桥接、SDK、持久化与本地模拟供应商，验证端到端跨层功能流程 |
| 原生生命周期（`native`） | 真实原生启动器、桌面进程树与正常/强制退出报告，验证进程回收与清理 |
| 隔离人工验收（`manual-gui`） | 独立数据根与模拟环境，供跨层人工交互、性能采样与故障恢复观察 |

生产契约分别见 [15](./15-session-storage.md)、[17](./17-studio-storage.md)、[25](./25-frontend-state.md) 与 [26](./26-timeline-content.md)。本地或单平台测试通过不外推为其他平台或真实外部供应商兼容。

### 24.1.1 集成与分层边界

集成测试仅保留必须跨 Rust 桥接、持久化存储、真实系统进程或原生窗口边界协作的端到端流程。纯前端布局、交互状态和受控传输逻辑在更轻量的无设备层完成，不在原生桌面集成中重复验证组件内部细节或官方控件自带行为。

测试等待统一依赖真实状态变化或模拟对端的显式事件闸门推进，不依赖固定睡眠猜测就绪；失败或取消必须保留原始首错，不得吞掉异步异常或用重试掩盖状态失步。

### 24.1.2 Waiting 集成流程

Waiting 桌面集成场景（`wait_events`）通过隔离主目录与本地回环模拟供应商启动完整桌面应用，按顺序验证：

1. 先等待后触发工具与先返回工具后等待的并发交付。
2. 固定超时、空目标等待消息及主动取消等待对目标任务本身的影响。
3. 子任务消息唤醒后的唯一交付，以及连续轮次交互下状态、历史回执与最终退出的完整性。

该场景同时作为桌面 `smoke` 的核心跨层验证入口。

### 24.1.3 时间线呈现与官方集成测试

普通桌面功能集成采用 Flutter 官方 `integration_test`，保留真实桥接、应用状态图、持久化与隔离配置，不通过私有协议注入业务状态或替代用户路径：

- **冷读与持久化查询（`conversation_read_work`）**：从已关闭的预置 SQLite 数据库冷启动加载会话并切换线程，验证按需读取与跨层记录。
- **问答回执与草稿保留（`question_history`）**：覆盖真实提问交互、草稿保留与继续执行，以及敏感字段脱敏后写入并展开时间线持久化回执的端到端流程。
- **消息提交与中断续行（`message_submission`）**：覆盖运行中提交排队、屏障推进、权威历史交接以及取消后继续执行。
- **实时呈现（`realtime_presentation`）**：复用严格环回对端验证流式增量、思考与工具调用、并行与工作目录执行、错误提示及中断停止后继续的端到端表现；支持以 `stop-background` 子焦点采集前后台并发与停止终态证据。
- **时间线概念与边界/媒体交接（`timeline_concept`）**：覆盖核心完整交互、冷重开与重启一致性；拆出 `timeline-boundary` 定向验证正文边界冻结及跨重启一致切面，拆出 Linux 专用的 `media-handoff`（结合文件系统写租约）验证纯附件提交及后台图片延迟交付与冷重开。
- **长历史与分页（`timeline_presentation`）**：分两阶段运行（实时写入与冷重开），基于大规模历史种子与大字节正文验证流式消费、多页回翻与持久化一致性。
- **侧栏项目与会话管理（`sidebar`）**：保留一次真实侧栏宽度修改经桥接持久化，以及项目与会话的增删改查、归档/恢复、后端状态过滤与退出清理结果；纯布局对齐、搜索过滤、二级菜单和对话框取消均已下移。
- **会话语言服务（`thread_lsp_status`）**：在隔离多项目环境中验证语言服务状态往返、重载绑定与关闭后系统进程清理。
- **真实供应商 opt-in 集成（`acp_real_login`、`chatgpt_real_login`、`acp_agy_conversation`）**：仅在明确提供实时环境与外部账号条件时执行真实登录、配额检查与真实 ACP 对话流程。

### 24.1.4 官方无头工具与界面设计对齐

所有界面与跨层人工实验统一按验证边界选择最轻载体，不将所有层级排成必跑清单：

| 目标 | 优先入口与证据 |
| --- | --- |
| 纯界面排版、主题、多语言、宽窄布局及静态截图 | 使用 `cargo xtask preview-gui --headless --no-devtools` 启动官方 Widget Previewer（复用生产组件与合成呈现数据，不编译 Rust bridge、不启动模型服务、不依赖 X11/Xvfb） |
| 真实模型调用、跨层持久化与原生运行时交互 | 使用 `cargo xtask manual-gui --preset gui --inspect` 启动隔离桌面应用（Linux 无头环境配合 `xvfb-run` 与 `GDK_BACKEND=x11`），通过官方 Dart MCP 观察组件树、截图与错误 |
| 原生窗口、输入法、系统菜单与进程退出生命周期 | 使用对应平台的桌面或 `native` 集成套件验证，不用渲染层截图代替原生系统行为 |

手工布局诊断优先使用官方 DevTools Inspector 与 Dart MCP，重复自动化流程使用 `integration_test`。通过应用渲染层采集的图像不包含系统窗口装饰或原生菜单，涉及平台行为时须采集平台层证据。预览入口独立保存在预览包目录，通过标准包依赖引用生产界面组件，不复制业务代码。

## 24.2 模拟对端与真实模型观察

本地模拟供应商服务（`pl-provider-fixture`）同时支撑自动化集成测试与人工验收：

- 仅监听本地回环动态端口，按既定协议、提示词与轮次返回预设 HTTP/SSE 或 WebSocket 事件流，严格校验请求字段、调用顺序与鉴权信息，错序或未登记请求直接失败。
- 自动化与隔离验收始终使用独立主目录与独立 SSH 配置，禁止读取、改写或复制操作者真实账号数据库与运行中凭据。
- ACP 通知投影与宿主 MCP 工具执行分属不同边界：外部协议回报不保证回显完整宿主结果，真实验收分别核对对端调用参数、宿主实际执行记录与产物；调试用的定向诊断日志默认关闭，不参与业务流程。
- 涉及真实模型费用、外部账号或远程写操作时须事先获得明确授权，并在独立会话或产品公共 HTTP 入口内完成观察，同时记录实际账号、模型版本、前后目录差异与最终资源回收情况。

## 24.3 原生 GUI 观察与隔离

`test-project` 的 `desktop` 与 `native` 套件在单次执行期间建立独占准备租约，集中构建并校验桥接库、辅助进程与锁定依赖，再分发给各隔离场景进程运行；租约过期、产物摘要或源码状态不匹配时立即失败，不回退为隐式重建。

- **Linux 显示与凭据隔离**：无桌面环境使用 `xvfb-run` 并显式指定 `GDK_BACKEND=x11`，同时为每个隔离目录启动独立 D-Bus 会话与最小化密钥环服务，避免访问操作者真实凭据；结束时按结构化挂载信息精准卸载隔离产生的 FUSE 挂载并校验全部 Daemon 退出。
- **原生启动与关闭验收（`shutdown`）**：应用实际持有 MCP、语言服务与后台子进程，测试记录主进程与子进程身份（PID 及创建时间/进程组），触发正常退出后验证退出码为 0、受管子孙全部退出且无强制回收；强制退出阶段单独区分并记录边界，不伪造自行收束。
- **多阶段隔离验收与升级恢复**：`pl-studio-acceptance` 通过隔离 preset 编排多阶段旅程，支持从一致备份副本启动升级恢复验收（自动隔离账号端点并禁用外部机器人/服务，不改动源数据）。无论阶段成功或失败，已生成的脱敏日志与失败证据都会保留用于排查。
- **跨平台 CI 与构建交接**：Linux 自动集成在预先校验的 Docker 镜像内消费同一 workflow 产出的固定只读构件（`ANYWORK_CI_TEST_INPUTS`）；Windows 与 macOS 侧重静态检查与 Release 应用打包构建，本地运行行为按需在对应宿主显式触发 `test-project` 验证。

## 24.4 呈现诊断与受控账号对端

账号与呈现验证严格区分纯呈现预览与原生持久化边界：

- 官方预览使用真实界面组件、主题、本地化与合成数据检验排版与局部回调，不代表真实凭据或持久化成功。
- 原生账号与呈现验收保持只读观察边界，仅在对应界面状态就绪后读取诊断信息，不序列化原始密钥或凭据内容；剪贴板与快捷键检查通过真实指针/键盘交互并回读系统剪贴板完成。
- 受控模拟对端支持在同一运行周期内按控制指令切换响应清单、注入失败或开启请求闸门，并保持有界状态容量与请求收束，用于验证异步刷新、去重与错误隔离而无需重启进程。

## 24.5 显式统计管线性能基准

统计写入与读取性能使用 `pl-studio-runtime` 中由 `benchmarks` 特性门控的独立 Criterion 基准，不纳入日常 CI 门禁：

```sh
cargo bench --locked -p pl-studio-runtime --features benchmarks --bench statistics_pipeline -- --save-baseline before
cargo bench --locked -p pl-studio-runtime --features benchmarks --bench statistics_pipeline -- --baseline before
```

对比在同一硬件、文件系统、优化配置与历史规模样本下预热多轮后执行，分别记录耗时分布、置信区间、操作量与 Linux 进程存储 I/O（`/proc/self/io`），严禁将准备阶段或编译耗时混入业务度量；短时间有界诊断单独标注样本约束，不冒充完整尾延迟结论。

## 24.6 其他观察入口与证据范围

- **机器人与外部协议**：本地模拟对端、平台真实授权与实际终端消息渲染分属不同边界，详见 [27](./27-bots.md#279-验收边界)；本地模拟通过不代表真实外部平台兼容。
- **ACP 安装与真实登录**：受控安装与真实官方授权验收边界详见 [28](./28-acp.md#2810-登录验收)；真实登录需在独立数据目录中依次完成授权登录与重启重检，不得复用未声明的个人凭据。
- **ChatGPT 真实登录**：通过显式启用的 `chatgpt_real_login` 在隔离主目录先后执行官方浏览器授权登录与重启后额度、模型重检，导出截图前对个人隐私信息进行脱敏，并独立确认真实退出与进程回收状态。

## 24.7 流式输出的现实规模基准

容量验证区分单条大输出（如参考 128k 词元规模）、多条目累计历史（如 2,000 条中短条目）与成员碎片化工况，使用公开分词口径独立计量文本大小、编码与元数据体积，并在真实 Runtime、桥接与桌面显示边界联合观察，避免将名义模拟速率或局部成功外推为其他工况表现。

## 24.8 Linux 累计两万历史与持续增长观测

`timeline-history-20k` 复用隔离环境与模拟供应商，通过正常对话轮次累计生成 20,000 条独立文本历史记录并确认落盘，冷重启后在同一基准上执行多次进程冷加载、会话切换与分页滚动采样，并在高历史基数下继续并发追加轮次以观测首内容加载耗时（参考 p95 目标 500 ms）、分位数帧耗时与进程存储 I/O，不通过直接写库或关闭持久同步来制造通过。

## 24.9 按需打开、交付与保存的证据口径

全链路时间线集成验收聚焦冷打开、按需分页读取、折叠与展开、媒体/文件延迟交付、后台交接与事务性持久化落盘：

- 首内容呈现须在目标会话实际完成布局后计时，严禁将占位渲染或内部数据到达当作界面就绪；在参考环境下以冷打开与常规切换首内容布局 p95 不超过 500 ms 作为基准参照。
- 性能与工作量采样按初始化、主时间线读取、成员按需加载及正文读取分别独立计量，验证大工作组不引发全量成员预读，且不增加额外生产统计负载。
- 失败、欠采样或受环境干扰的场景如实标记为缺口，不使用静态睡眠或降低负载尺度掩盖真实问题。

## 24.14 本地 Harbor 手动验收

`integrations/harbor` 仅作本地 Linux 手动集成与基准验证使用，不接入 PR CI 或容器镜像构建。维护者在隔离宿主机上通过固定依赖运行协议与任务验证，确保产出文件由被测 CLI 真实生成、超时取消后无残留进程或写入；持续集成仅通过工作区打包校验 `bin/anywk` 产物的可用性，不自动运行真实付费模型基准。
