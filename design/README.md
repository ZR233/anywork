## 写作规范

- **聚焦契约而非实现细节**：只描述设计目的、架构原理、接口形状、状态转换逻辑与边界约定；可使用关系图及最小配置或协议示例说明契约，不展开具体实现代码、方法签名、内部模块路径、源文件路径或行号。crate 名称、协议/工具/事件/线协议（wire）字段名、配置键与数据库表名属于接口形状，保留英文原文并使用反引号标识。
- **单一事实源**：每项架构事实仅在一个权威文档中定义，其他文档通过链接引用，不重复展开。上表括号中标注了各领域的唯一权威源。架构演进原则归 [AGENTS.md](../AGENTS.md)，数据库与会话迁移归 [17](./17-studio-storage.md)，配置迁移归 [20](./20-config.md)；设计规范与当前实现存在差距时必须明确标注，不得将目标契约表述为已验证能力。
- **权威不等于正确性保证**：“权威”与“唯一来源”表示当前约定的统一维护位置，不使内容免于质疑。与用户讨论时，本文及各领域文档、规约都不作为裁定方案合理性的权威依据；讨论行为见 [20.6](./20-config.md#206-提示词配置)。已确认的变更仍回写原维护位置，不另建平行规范。
- **数值边界与动态配置分离**：行为数值契约（步数上限、持久化容量上限、超时阈值、截断长度等）在对应设计文档中维护；数据结构版本号、依赖版本、模型价格等易变运营数据以代码常量与内置目录为准，文档不保存静态快照。
- **术语与命名口径**：面向用户与智能体系统提示词统一使用产品名「糊来帮」（英文 `anywork`）；仓库与技术标识为 `pure-lang`，Rust crate 统一使用 `pl-` 前缀。中文叙述优先采用标准中文计算机工程术语，智能体角色统一使用「智能体 / 主智能体（根智能体） / 子智能体 / 父智能体」，避免无必要的中英夹杂。
- **章节编号与工程边界**：小节统一采用 `N.M` 编号，与文档编号对应。设计文档描述产品接口和行为，不设置贡献者的工作流、测试白名单或必跑清单；[AGENTS.md](../AGENTS.md)、领域技能与仓库工具提供工程入口及方法，CI 的实际执行以工作流配置为准。
