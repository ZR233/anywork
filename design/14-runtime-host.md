# 14 - 会话运行时宿主与后台工具任务

本文定义 Studio 侧的会话（`Thread`）装配、激活、输入受理、步骤限制、后台工具任务交付与消息唤醒机制。内核契约见 [16](./16-core-contracts.md)，状态与历史存储见 [15](./15-session-storage.md)。

## 14.1 统一装配与激活

Studio 的会话工厂负责解析配置、智能体（Agent）定义、预设（Profile）、工作模式（Mode）、项目及物理工作区绑定；会话装配器登记准备期的会话所有者（owner）并创建内核 `Thread`。根会话、子会话与冷恢复共用同一装配入口。处于准备期的会话所有者不对外发布；若装配失败或调用方取消等待，登记表仍保有已创建的会话所有者以维持资源释放责任，仅在关闭成功后才删除登记。关闭流程先封闭装配入口并等待在途准备收束，再按从子到父的顺序依次关闭；若关闭失败则保留重试入口。

激活流程先登记准备期所有者，再创建物理服务与内核 `Thread`；并发等待者共享同一准备结果，单个等待者取消不会丢失准备期所有者，而宿主关闭会取消并等待所有仍在准备的任务。冷态子会话基于已保存的工作区与项目绑定创建新实例，不重新创建 Git 工作树（`worktree`）或重放历史副作用，且其父会话必须先完成激活。

每个会话独占模型会话与工具实例，同批工具声明与执行器由内核统一冻结。配置、预设与工作区语义由 Studio 解释，不进入内核类型：根会话的无凭据模型选择器作为不透明的 `studio.model-route` 扩展写入当前检查点（checkpoint），并由状态副作用（effect）记录修订历史；子会话使用冻结的预设快照。底层物理服务可按隔离身份共享租约，关闭单个会话不会撤销其他会话的租约。模型切换由会话所有者串行执行：先关闭旧模型会话并清空旧续接状态（`continuation`）与重试计划，再创建新会话；若模型工厂创建失败，会话明确保持模型不可用状态，保留历史记录并允许重新装配。执行中的轮次（`Turn`）不会被参数刷新中途替换，后台工具任务与模型切换相互独立。

所有会话均从同一种已解析的智能体定义进入统一指令装配流程；普通根会话、机器人根会话与子会话的工厂仅选择可信定义及其使用绑定，不按角色 ID 拼接提示词正文。角色来源与工作模式来源分别冻结、独立更新（定义契约见 [12](./12-collaboration.md)）。新建、恢复、工作模式切换、轮次准备与上下文压缩共用同一来源解释逻辑；仅刷新工作模式不会替换智能体指令。统一智能体定义不接管模型路由、工作区分配、步骤预算或工具权限，也不引入额外的执行所有者。旧版指令来源的格式转换在恢复迁移事务中完成，正常模型准备路径不保留新旧格式并行解码。快照中的角色块结构与内容身份消费自身冻结的事实，而非当前目录或特定渠道角色的名称；可信渠道与父子归属仍独立校验。冷恢复直接读取已冻结的定义，不因内置声明或默认模型变化而重新选择智能体。

受信指令来源经统一组合后才提交给模型适配层：会话创建、工作模式切换、轮次准备与压缩恢复不得各自拼接不同的正文或分隔符。运行时仅决定指令来源、有效版本与原子提交边界，具体的供应商角色映射与追加/替换策略由模型层的统一分发机制解释（见 [06](./06-model.md)）。普通动态事实继续通过独立的 `user` 上下文传递，不因前缀缓存优化而混入稳定系统指令；已冻结的请求与重试不会重新读取当前指令来源。

模型路由选择器与待生效的模型更新（`pending model update`）必须通过同一会话所有者邮箱（mailbox）操作原子提交：若扩展 CAS 失败则不改变待生效更新，反之亦然；路由选择器表示期望路由，实际模型实例仍在下一轮次边界替换。账号设置更新可触发模型与工具刷新，但刷新必须逐个会话读取自身选择器并重新解析，不得广播全局角色路由。当选择器失效时，会话进入明确的不可用（`unavailable`）状态，不猜测回退模型。

执行侧文件位置属于宿主运行时事实，而非首轮固定的用户指令。统一装配流程根据当前项目、会话与实际工作区绑定生成 `studio.session-files`，声明执行侧的 `scratch`、`artifacts`、命令输出目录及其所属的本地或 SSH 环境（目录布局见 [17](./17-studio-storage.md)）。新建根会话、子会话、审查会话（reviewer）、冷恢复与工具刷新均消费同一份路径事实，本地目录模式（`directory`）的临时目录访问许可同样消费该值。恢复后的最新宿主事实在安全的模型边界替换同源（`source`）旧值，不重新渲染历史请求或篡改已冻结的请求；上下文压缩同样保留最新宿主事实，不被旧摘要中的路径覆盖。宿主内部数据库、归属清单与传输暂存目录不作为模型可写目录暴露，平台提示词与通用系统提示词负责阐明这一边界。

## 14.2 输入受理与驱动

用户输入按调用方提供的稳定 ID 幂等受理。Studio 的 `submitPrompt` 由内核原子选择“直接启动”或“打断当前轮次后继续”，客户端无需根据可能过期的活动状态自行分支；内核的 `Start`、`Steer` 与 `Queue` 仍作为独立的通用输入策略保留。机器人平台的独立新消息复用相同的内容准备、权限校验、模型路由与持久化受理边界，但采用内核的非打断串行驱动策略，不将后到的独立消息视为当前轮次的补充或中断。驱动策略由产品入口显式指定，既不依赖瞬时活动轮次快照分支，也不设立机器人专属执行队列；桌面端提交与显式交互续接保持原有语义。重复提交相同输入身份仅返回原始回执，不重新启用驱动或重放已消费输入。

HTTP 接口使用 `POST /api/v1/threads/{thread_id}/prompts`（`prompt.submit`），FRB 接口使用 `submitPrompt`；请求的 `input` 载荷包含稳定的 `inputId`、`text` 与 `attachmentDraftIds`。同一 `inputId` 的重试必须保持原始内容；由于附件草稿在首次受理后即提交转正，重复请求会先从权威输入记录返回原始回执，再决定是否需要准备资源。输入受理不伪造 `Turn` ID：提示词提交返回 `inputId` 及首次受理该输入的提交序号（`commit` sequence），客户端通过同 ID 的输入时间线条目关联实际轮次；轮次 DTO 与轮次时间线条目保留关联的 `inputId`，即便模型准备失败也能将错误关联到已受理输入，无需复制从未交付给模型的用户消息。输入受理与模型准入属于两次独立提交：受理成功即返回跨窗口、跨重启稳定的幂等回执——稳定 `inputId` 的最小身份与产生它的状态副作用在同一历史事务中写入，重复提交优先查询该持久化身份索引（见 [15](./15-session-storage.md) §15.3）；仅当模型准备完成且权限与容量复核通过后，输入消费状态才与实际请求记录及用户上下文在同一事务中提交。准备失败时保留待处理输入，驱动暂停不会自动触发产生费用的重试请求。

引导输入（`steer`）记录原始目标轮次，在下一份模型请求冻结时按序并入用户上下文，并与该请求一同提交消费事实；请求冻结后到达的引导输入留待后续请求消费。未消费的引导输入与其他输入一样持久化保留，可在中断恢复后继续处理，不改写已执行的请求。附件在输入受理前完成保存并校验字节长度与摘要，完整的业务元数据随实际模型上下文一同进入会话；附件草稿仅在输入成功受理后提交转正。

会话执行授权通过互斥状态 `Dormant`、`Enabled`、`Paused`、`Failed` 表达：普通消息仅能唤醒处于 `Dormant` 或 `Enabled` 的会话，唯有显式继续命令才能解除 `Paused` 或 `Failed` 状态。物理取消的目标轮次与执行授权正交，停止操作不会提前解除资源清理屏障。当前输入批次仅维护一份身份集合，首条输入身份由集合派生，不维护平行的当前输入状态。

持续消费输入队列的驱动器归属于 `Thread` 执行体（actor）：Studio 显式启用驱动并传入通用步骤上限后，执行体串行处理已受理输入，产品层不为每条输入派生旁路执行任务。普通所有者命令在下一轮驱动前处理，使模型与工具配置更新得以在轮次边界生效。执行失败、交互暂停或达到步骤上限都会停止驱动，防止自动重复发起产生费用的模型调用；受理新输入本身不解除暂停，宿主必须显式发起继续命令。驱动状态仅描述物理执行，冷恢复时不会自动激活驱动。

根会话与子会话共用同一套 `Thread` 机制；预设解析、工作区分配、父子目录维护、派生/关闭（`spawn`/`close`）及消息路由由 Studio 统一协调，工具层仅调用宿主端口，不维护第二套子智能体运行时。预设的目录（`directory`）与工作树（`worktree`）边界由物理工具后端强制执行；Shell、Git 与 MCP 能力需单独授权。

“提交并继续”操作在同一所有者邮箱步骤中先受理输入内容，再绑定当前轮次代次并发起取消请求。若受理失败则不打断当前执行；重复输入 ID 不重复唤醒或取消。当前轮次的在途工具调用随之一并取消，尚未启动的调用直接收束为取消状态；唯有在途执行与清理结果全部提交后，方可发起新的模型请求，其他轮次的后台任务保持原有生命周期。取消收束期间到达的输入按受理顺序合并至下一请求，每条输入独立保留受理与消费事实。已消费内容不再重放，尚未准入模型的原始输入与补充内容共同交付。取消中状态归属于活动所有者，不恢复已触发的物理取消令牌。显式停止或关闭会撤销自动继续意图；执行失败则保留待处理输入并暂停驱动。迟到的普通通知仅更新唤醒水位，不能解除显式停止或失败暂停；普通消息通知不经过该打断控制入口，不会因子智能体进度或后台任务完成而打断父会话。待决交互必须通过专用回答入口解决。

## 14.3 步骤限制、停止与取消

执行预算、步骤限制与取消属于通用类型化执行策略，而预设、角色与父子生命周期决策归属于宿主。步骤策略明确区分无限制（`Unlimited`）与有限步数（`Limited`）：Studio 主会话的新建、恢复与所有续接均采用 `Unlimited`，不因累计模型调用次数或活动总时长而自动停止；子会话每个轮次的上限为 256 步。每个新轮次从零开始计数并获得完整额度，不继承上一轮次的消耗；同一轮次内的模型与工具往返不刷新额度。达到步数上限后会话暂停，显式续接开启新轮次时重新计数。用户停止、会话关闭、交互等待、真实错误与单次外部操作超时独立生效。旧版 `stepLimit` 历史记录保持原样，不自动重启已停止的任务，且不得通过产品层 JSON 字段篡改内核控制行为。

携带预期轮次身份的中断请求由会话邮箱在所有者内部核对，仅取消匹配的当前执行代次；产品层不得先读取快照再去取消一个可能已切换的轮次。显式停止会同时暂停输入驱动并保留待处理输入，后续继续执行必须显式恢复。轮次取消时，已准入但尚未启动的工具调用直接以取消结果收束而不执行外部副作用，并与轮次取消终态在同一提交中发布。会话关闭同样先收束未启动的工具调用，再关闭工具实例，避免留下未配对的调用历史。中断句柄仅持有当前命令的子取消令牌，不共享可变对话记录或任务状态；中断信号在命令队列之外即时生效，既不取消调用方复用的父令牌，也不影响下一执行代次。

当模型调用被运行时定向中断（如插入新消息打断、显式停止、会话关闭或重定向）取消时，模型实现必须以取消语义上报结果，不得归类为账号不可用或传输失败。宿主据此将该轮次收束为取消终态并继续消费已受理输入，避免将定向打断误判为执行失败而暂停驱动；真实的账号故障、请求超时与传输错误仍保持原有失败语义。取消判定必须依据当前调用自身的取消事实，不得仅凭错误文本或同一时刻的其他并发信号推断。

## 14.4 后台工具任务与交付

同一会话的后台工具刷新、工作模式重配置与关闭由同一安装所有者串行协调。准备过程支持取消，提交前校验所属代次，内核工具目录与宿主物理绑定的提交不得与其他安装过程交错。关闭流程先封闭刷新准入，取消并等待在途准备及候选资源清理完成，随后释放工作区租约。关闭成功意味着该会话不再持有后台刷新任务或未接管的候选资源；若清理失败则保留原对象与错误状态，不发布成功回执，也不清空其他有效代次的工具实例。

会话所有者串行管理后台任务、结果交付与消息状态。工具任务先提交 `Running` 事实再开始执行。普通工具默认采用 1 秒同步交付窗口：若在窗口内完成则直接提交实际结果；若超时则提交关联原调用的任务回执，并将执行异步任务（future）留在会话内转为后台运行。后台任务完成时将业务结果、任务终态与完成消息在一次原子提交中落入会话，由模型在后续请求准入时统一消费；已受理的后台任务可跨轮次运行，其终态结果仅交付一次。任务回执与最终业务结果属于两条独立事实。

工具等待调用（`wait`）仅报告就绪状态，完整的后台任务结果由模型准入阶段统一消费，防止 `wait` 返回值与收件箱重复交付。任务状态查询不消费消息；任务取消调用仅提交取消意图并触发执行令牌取消，直至物理执行与资源清理彻底返回后才生成任务终态，不得将取消请求已发出（`Requested`）视作已取消完成。重复取消不会重复提交，已达终态的任务不可被取消命令改写，取消单个后台任务也不会取消其所属轮次。任务查询、等待与取消仅接受本会话回执中的完整 `taskId`，未知任务一律返回 `TaskNotFound`，不猜测前缀、不转换大小写，也不泄露其他会话的任务信息。

`wait` 工具同时观察指定的后台工具任务与未消费的会话消息，任一所选任务进入已提交终态或任一消息就绪即刻返回，无需等待全部任务完成；当 `taskIds` 为空时仅等待新消息（含子智能体终态报告）。`sleep` 工具产生的后台任务回执与其他工具任务共用同一套身份标识与就绪规则，定时器到期同样参与就绪竞争。若调用前目标已就绪则立即返回；单次返回可包含多个已就绪来源，但不承诺还原同一调度间隙内各事件的物理先后次序。

任务状态、`messagesReady` 与 `timedOut` 由同一等待原语判定。等待截止时间点固定，不因无关通知而重置；到达截止时间时先复核已提交的就绪事实，只要存在任一就绪来源即返回就绪而非超时。正常超时既不伪造任务完成，也不取消被等待的后台任务。常驻内存台账淘汰不代表任务未知：等待原语可按需读取本会话持久化的任务终态事实；对于真正未知的任务 ID、跨会话任务、等待自身调用、调用授权失效或存在待提交结果等情形，仍按各自明确的类型化错误拒绝，不以“未知状态”伪装成功返回。取消或释放等待调用仅放弃本次观察；会话关闭、调用取消、存储读取故障与正常等待超时具有严格区分的结果语义。

完整的业务载荷（payload）、实时观察结果、实际交付给模型的上下文（`delivered context`）与任务终态分别保存。失败的任务仍可附带已观察到的输出；取消后迟到的执行结果照常保留供审计，但不再应用其中的扩展状态变更、交互请求或轮次结束控制。模型历史记录消费当时保存的交付上下文，不得使用当前渲染器重新解释历史业务正文。

当工具执行完成但状态提交因存储背压或故障失败时，会话所有者保留原始完成对象与执行租约，并暂停新模型请求准入；后续提交重试直接复用已完成结果，不重复执行工具。完整载荷与交付上下文随会话历史统一保存，不按工具类型拆分表结构。大型二进制对象或长输出文件通过携带摘要与字节长度的稳定资源引用保存；单页预览、临时文件路径或尚未归档的原始捕获文件不替代完整资源引用。

`exec` 与 `write_stdin` 共享会话私有的进程管理器，且任务身份校验先于内部进程映射。命令输出流必须彻底排空后方可执行归档，远端归档通过真实的远端范围读取拉取数据；若归档失败则保留源捕获文件供重试，不重新执行命令。物理路径权限与工作区边界由工具后端强制执行，内核不根据工具名称或参数中的路径字符串猜测授权。

Studio 统一装配根会话、子会话与冷恢复的工具及物理服务，不在每轮请求时重建命令管理器或维护平行的工具注册表。动态目录变更保持仍然有效的物理租约；SSH 重连保持服务器身份、工作目录与权限边界不变，仅替换失效连接对应的工具实例与命令管理器；同一连接上的目录刷新则继续复用现有命令管理器。候选工具集成功移交会话所有者后才对外发布新绑定，失败、取消或目标失效均不得记录为安装成功。旧连接上的遗留任务保留中断结果，既不重放命令，也不将旧进程的标准输入转发至新连接；会话关闭时逐一等待工具实例收束，若失败则保留清理进度供重试。工具刷新按会话独立推进，同一会话内部串行安装并合并重复刷新通知，单个会话的连接或清理等待不阻塞其他会话。技能（Skill）运行时事实通过所有者消息通道受理，按来源保留最新待应用值并在下一次模型请求准备前生效；受理技能更新不修改已冻结的模型输入，也无需等待整个轮次结束；会话关闭时拒绝新的技能更新并收束在途刷新。

## 14.5 消息与统一唤醒

跨会话或后台消息按稳定 ID 幂等受理，消息来源与上下文载荷不得冒充 `system` 角色或伪造审批状态。消息消费水位与模型请求准入在同一提交中生效；若请求准备失败或在准入前被取消，消息保持未消费状态。显式用户输入、后台消息与界面观察各自具备独立语义，后台消息到达本身不会隐式触发产生费用的模型调用。在模型推理与工具执行期间，会话所有者继续受理消息投递与历史读取：新到达的消息写入同一所有者的有界收件箱并持久化提交，但不改变已冻结的当前请求或上下文，仅在后续模型请求准入时被消费。收件箱通道容量有界，不维护第二份会话状态，也不得绕过会话关闭时的受理门禁。

运行时内部通知仅用于提示状态可能发生变化，并非需要逐条消费的业务事件。观察者遵循“先注册订阅、再检查当前状态”的顺序；每次被通知唤醒后重新核对已提交的任务终态与消息消费水位，从而允许底层合并通知而不丢失就绪信号。后台任务、定时器与子智能体消息不维护各自独立的等待者登记表，所有等待操作统一复用会话所有者的状态发布边界。

宿主在投递消息时可显式请求唤醒目标会话：唤醒水位随消息受理一同提交；若当前活动轮次在结束前已顺带消费了该消息，轮次结束后不再额外发起模型调用；若会话空闲且存在未消费的唤醒消息，则通过运行时上下文启动新一轮执行，不伪造用户消息；冷恢复保留持久化的唤醒事实，但仍需宿主显式恢复驱动才会开始执行。

## 14.6 生命周期与观测

应用启动阶段仅加载轻量会话目录摘要（`catalog`），不遍历或激活历史会话。当目标会话被显式激活时，读取并校验其检查点；若检查点或产品目录关联缺失则明确报错，不创建空会话掩盖数据丢失；底层物理服务仅在会话显式激活时按需装配。显式停止、会话关闭与任务取消均由所有者核对当前执行代次：关闭流程先封闭新工作准入，取消在途执行并等待物理资源退出，重试尚未提交的完成结果，随后依次关闭工具与模型会话，刷写（`flush`）该会话固定的历史与调用记录水位并保存最终检查点；若关闭失败则保留所有者以供重试。冷恢复自动将遗留的 `Running` 状态收束为 `Interrupted`，不恢复旧执行器，也不自动重放外部副作用。

实时状态订阅消费当前状态快照与增量状态副作用（`effect`）；历史分页则始终通过独立的 `HistoryReader` 直接查询存储，即便会话执行所有者已关闭，仍可读取数据库中的最终持久化事实。项目或会话归档操作必须等待整棵会话树关闭、持久化保存确认完成以及 Git 工作树清理收束（清理成功，或回退为 `preserved` 状态并发布恢复诊断）。SQLite 写入任务的故障与未保存事实必须对界面可观察；目录写入器仅负责保存产品级目录关联，不代理会话的状态副作用、对话历史或检查点。

## 14.7 交互与业务状态的宿主侧路由

Studio 从内核通用的交互与权限快照（`interaction`/`permission` snapshot）投影产品层提问卡片，并依据编码了会话归属的不透明交互 ID 路由用户回答。计划（Plan）与工作流（workflow）状态由 Studio 负责解释，状态更新采用扩展 CAS 机制；用户回答、扩展状态变更、模型可见上下文投影与续接输入（`continuation` input）在同一内核提交中原子生效。重复提交相同回答仅返回幂等回执，不重复入队或自动触发驱动。

工作模式切换采用空闲重配置（`idle reconfigure`）策略：先核对状态水位并拒绝存在活动轮次、后台任务、待处理输入或待决交互的切换请求，随后原子替换业务扩展、目标工作模式的默认模型选择器、下一轮次待生效模型更新、系统上下文及工具目录；已持久化的历史正文不按新工作模式重新渲染。普通用户提问、计划确认与执行权限审批共用 Studio 的类型化交互路由：路由层直接从内核快照读取待决事实，不维护第二套可写交互状态；用户回答作为一次原子响应连同隐藏续接输入一并提交，模型仅接收提交时确定的内容。对外暴露的交互 ID 编码了所属会话 ID 与内核本地交互标识，客户端仅原样透传该不透明 ID，因此不同会话中即使供应商重用了相同的调用 ID 也不会导致回答串路。
