# 14 - 会话运行时宿主与后台工具任务

本文定义业务会话的运行资源所有权、Native `Thread` 装配、激活、输入受理、步骤限制、后台工具任务交付与消息唤醒机制。内核契约见 [16](./16-core-contracts.md)，状态与历史存储见 [15](./15-session-storage.md)。

生产宿主包括 Desktop、HttpServer 与 Cli，均消费同一运行时装配和资源关闭所有者。Cli 的 `anywk` 入口使用显式数据根、严格启动、环境凭据和一次任务终态观察，契约见 [29](./29-cli-harbor.md)；它不通过 Test 身份绕过生产边界，也不创建另一套执行循环。

## 14.1 统一装配与激活

运行资源按 `StudioRuntime → SessionRuntime → AgentInstance → AgentRuntime` 组合拥有，实际资源只有 `Native` 与 `Acp` 两个具体分支。应用持有活动会话集合与共享服务；业务会话负责本会话的执行准入、准备任务、成员资源和受管关闭；成员实例引用目录冻结的 `SessionId`、`AgentId`、`parent_agent_id`、默认 `ThreadId` 与后端绑定，并拥有本次物化资格。Native 分支组合原有内核句柄、工具资源、观察任务和保存责任；ACP 分支拥有独立 SDK session、当前运行资格、待决权限和工作区使用租约，租用 Studio 按账户连接代次持有的进程与唯一 SDK 连接驱动。各后端独占自身执行状态，不在公共成员层复制轮次、工具状态或检查点。

会话内部只有一份拥有资源责任的成员登记表，不同时维护递归强拥有树。登记表不是第二份可写成员目录；冷成员继续只存在于持久目录，只有申请物化或尚有清理义务的成员才进入运行登记。应用级定位入口只保留位置、弱句柄或被动投影，不另持有相同成员的生命周期责任。

Studio 的会话工厂负责解析配置、智能体（Agent）定义、预设（Profile）、工作模式（Mode）、项目及物理工作区绑定；成员资源的存续责任随准备与构造移交会话作用域。每个 Native 实例拥有自己的 MCP、工具绑定、候选清理与观察任务，工厂不成为另一份长期强拥有表。LSP、SSH 和物理工作区服务仍按现有应用级所有权提供租约。Native 根成员、子成员与冷恢复保留原装配入口；ACP 独立业务会话沿同一会话所有者的准备、发布和关闭边界接入，不创建假的 Native 对象。混合父子派发仍须等相应结果交付与关闭链完成后开放，不能因 ACP 独立会话已可执行就提前放行 Profile。

激活流程先登记准备期所有者，再创建物理服务、Native `Thread` 或 ACP session；失败准备保留实际分支的未完资源。ACP 账户连接由独立于业务成员的应用作用域持有，所有启用账户的后台准备、认证及业务打开共享同一连接实例；临时故障由原账户所有者在旧资源收束后退避重连，禁用、删除及退出取消该重连责任，具体准入见 [28.1](./28-acp.md#账户连接与后台准备)。并发等待者共享同一准备结果，单个等待者取消不会丢失准备期所有者，而宿主关闭会取消并等待所有仍在准备的任务。公共发布返回产品成员身份，只有 Native 专属操作返回内核句柄。Native 冷态子会话基于已保存的工作区与项目绑定创建新实例，不重新创建 Git 工作树（`worktree`）或重放历史副作用；父工作区读取只读公共目录和既有租约，不因需要父路径而启动 ACP 父。

新会话的准备进度覆盖创建命令准入、项目与工作区准备、运行资源装配和首条输入受理；只有真实受理完成才结束准备，不以模型首字响应作为完成点。准备耗时按阶段诊断，区分准入等待、物理工作区验证、工具与指令装配及输入受理，不记录输入正文或凭据。同一次激活中，同一目标已经完成的工作区准备验证不在祖先遍历中重复执行；每个祖先仍验证自己的绑定，已驻留实例的后续执行准入仍核对当前物理身份，不将驻留视为路径未变化的证明。

MCP 就绪门槛按[必需依赖与代次租约](./09-tool-runtime.md#96-mcp-能力声明thread-独占运行时与轮次租约)执行：可选服务仍在准备不阻止会话与首条输入受理成功，必需服务未就绪不能假受理。后台补齐工具不改变已受理输入的身份，也不改变已冻结模型请求的工具清单。

准备登记、执行准入封闭与最终发布共享同一会话串行边界。关闭后拒绝新执行、派发和迟到发布，但既有保存、报告交接与清理责任仍可推进。异步回调必须核对原实例资格及精确存储绑定，不能仅凭相同 `ThreadId` 向再次激活的新实例发布结果。调用方离开不转移资源责任；清理失败保留原对象与进度，实际结束后才摘除登记。

用户提交与无内容继续采用同一准入顺序：先在生命周期锁下核对目录身份与归档状态；继续操作先查询已受理回执，命中时直接返回，不激活会话。新工作先检查运行时并完成 owner 激活，再取得该会话成员的操作许可。激活准备本身也取得这项许可，因此等待激活时不能持有它；持有成员许可时也不能反向取得生命周期锁。取得许可后重新核对目录、关闭封口、会话代次与 Thread 实例，再查重并校验执行、路由和继续点，最后只等待 Core 受理而不等待模型轮次。释放许可后继续等待持久回执；调用方取消等待不撤销已经交给会话负责的准备，关闭会取消并等待准备及其资源清理。

空闲回收区分内存预算与未完成责任：已保存、可从权威历史重建的驻留投影仍计入内存压力，但不单独阻止释放执行实例。只有存储后端确认其来源、投影交接和活跃输出均已收束，且当前提交水位已经持久化时才能将这部分标记为可回收；在途输出、待交付内容、未完成保存、存储故障或未解除的恢复责任仍阻止空闲关闭。最终关闭产生的新提交仍须由原所有者保存并等待确认。

协作端口消费成员的产品身份，不依赖 Native 工具上下文或输出格式，边界见 [12.3.1](./12-collaboration.md#1231-协作端口与-native-适配)。Native 工具装配与刷新冻结本次成员实例资格；进入协作操作前核对实际调用上下文与该绑定，旧工具不能按同一成员 ID 重新绑定新实例。内部准备、发布和受管操作继续归本会话所有者，调用 future 的取消或丢弃不丢失已移交的任务、失败与资源清理责任；不为端口解耦建立第二份成员状态机或关闭队列。

### 14.1.1 生命周期作用域与关闭

| 操作 | 作用域与完成语义 |
| --- | --- |
| 页面离开或读取租约释放 | 只收束自己的观察，不停止业务会话、轮次或后台任务 |
| 取消轮次 | 使用内核原有中断语义，成员与已发布子成员保留 |
| 空闲驻留回收 | 沿现有 pin、空闲封禁、物理租约与保存条件回收指定 Native 实例，不删除持久身份 |
| 会话运行时关闭 | 封闭当前会话运行代次，收束本会话全部创建、执行、观察和清理责任，工作区默认保留 |
| 显式成员关闭 | 只处理授权后代范围，保留原持久封口、容量和工作树判定 |
| 归档或删除 | 使用各自业务事务与授权；删除保留独立的非保存语义，不由通用关闭或析构删除用户数据 |

会话运行代次单向经历 `Open → Closing → Closed`。失败保留在 `Closing`，后续重试仍封闭新执行；仅当准备、执行、候选资源、Native 保存与观察交接责任全部结束才发布 `Closed`。这不代表删除历史或永久封口身份。合法再次激活创建新运行代次，不能把旧对象重新打开；是否准入仍取决于目录、归档和显式关闭规则。单个成员空闲回收不关闭整个业务会话。

会话关闭先向全部执行和准备广播取消，独立分支立即并行收束，父节点只等待真实子依赖。准备任务排空与独立分支清理并行推进，排空后继续处理迟到的未发布资源；一个分支失败不短路其他分支。工具刷新生产者须先封闭，随后按原依赖关系完成候选移交、内核执行、`CommandProcessManager::close().await`（显式封闭新进程准入、取消全部受管 OS 子进程并 `join` 全部生命周期与输出读取任务，避免孤儿子进程阻塞工作树卸载）、工具与模型、MCP/LSP、观察和写者责任。清理时不持有成员登记锁跨异步等待；对仍处于 `Closing` / 失败恢复的子智能体关闭，由 `StudioRuntime::resume_agent_closes()` 在冷启动时按持久化记录物化对应会话并续推，同时即时同步 `StudioRecoveryRegistry`（`agent-close:{id}`）问题状态。

首个关闭调用启动的任务及完成结果由会话持有，重复调用等待同一进行中的运行。取消等待或应用等待期限耗尽不丢任务、结果或资源；一次失败运行真正结束后才可重试剩余责任，已完成节点不重复释放。应用退出只枚举会话并等待其收束，再释放共享服务，各层共用原绝对期限。析构只作最终取消防线，正常关闭必须真实汇合。

Native 内部区分执行、关闭存储与临时报告接收用途。临时接收器不是可执行成员占位，退出不等于永久封口；保存回执不能解除尚未完成的清理责任。历史读取资格独立于执行实例，关闭与回收不得撤销其他合法读取者或激活全部冷成员。

ACP 的 session 关闭、账户连接关闭与物理进程回收分别结算。成员关闭先封闭其准入、取消准备或活动 prompt、回答待决权限，按能力关闭其 session 并释放成员租约，不排空共享 SDK、不终止其他会话。远端关闭不支持或 RPC 失败保留诊断，不为补确认重启进程。账户撤代和应用退出封闭整条连接准入、收束全部所属 session，再排空 SDK、回收进程树与管道；只有本地必需责任未结束才保留原 owner 重试，不能伪造 Native 保存 ACK。`observed_threads` 只枚举 Native，ACP 的更新与运行终态见 [28.11](./28-acp.md#2811-acp-业务会话与原生内容通路)。

ACP 账户连接所有者持有物理进程回收任务的汇合句柄；业务成员只持有自身 session 驱动、关联发布与租约。关闭预算耗尽或调用者取消只结束本次等待，原回收任务继续推进；重试汇合同一任务，不在过期截止点反复创建并取消进程等待。账户关闭的 SDK 与物理回收共享首次关闭截止时间，不为重试刷新预算；成员释放其自身执行和关联责任后可释放工作区租约，不要求其他 session 或空闲账户进程同时退出。Host MCP 的会话资格先撤销；尚由官方进程持有的 helper 映像等物理责任由账户连接接管至真实进程回收，不能随成员句柄丢失。

ACP 业务成员还持有经 Host MCP 接纳的工作区任务和同源命令资源，使用普通会话的冻结执行绑定。ACP 进程和协议仍在宿主，不建立远程 ACP 运行时。关闭先封闭工具准入，取消并等待业务执行、捕获和归档，再释放工作区租约。成员驱动、业务任务、归档和关联发布都结算后才报告本地完成；Native Current/History writer 与 receipt 不复制到 ACP。

每个会话独占模型会话与工具实例，同批声明与执行器由 Core 冻结。Studio 解释配置、预设和工作区。根模型选择器作为 opaque `studio.model-route` extension 进入完整 Current，并通过 typed History event 记录修订，子会话使用冻结 Profile。物理服务按隔离身份共享租约。运行中可保存下一轮的模型选择。在途轮次沿用已安装的模型，新输入在软抢占后的下一步模型请求或新轮边界消费已安装候选模型。候选模型打开后可以受理输入，执行器在边界完成安装并清空旧重试计划，旧会话由原 Core 所有者关闭；当候选模型切换已就绪时，提交新立即输入会触发 Turn 级交接中断（`Interrupted`），先由旧模型完成摘要并收束旧轮次后再切换新模型。首个目标请求准备时，以旧轮收束后的已提交上下文做交接。候选打开失败时，已安装的资源继续保留，故障可重试。

所有会话均从同一种已解析的智能体定义进入统一指令装配流程；普通根会话、机器人根会话与子会话的工厂仅选择可信定义及其使用绑定，不按角色 ID 拼接提示词正文。角色来源与工作模式来源分别冻结、独立更新（定义契约见 [12](./12-collaboration.md)）。新建、恢复、工作模式切换、轮次准备与上下文压缩共用同一来源解释逻辑；仅刷新工作模式不会替换智能体指令。统一智能体定义不接管模型路由、工作区分配、步骤预算或工具权限，也不引入额外的执行所有者。旧版指令来源的格式转换在恢复迁移事务中完成，正常模型准备路径不保留新旧格式并行解码。快照中的角色块结构与内容身份消费自身冻结的事实，而非当前目录或特定渠道角色的名称；可信渠道与父子归属仍独立校验。冷恢复直接读取已冻结的定义，不因内置声明或默认模型变化而重新选择智能体。

受信指令来源经统一组合后才提交给模型适配层：会话创建、工作模式切换、轮次准备与压缩恢复不得各自拼接不同的正文或分隔符。运行时仅决定指令来源、有效版本与原子提交边界，具体的供应商角色映射与追加/替换策略由模型层的统一分发机制解释（见 [06](./06-model.md)）。普通动态事实继续通过独立的 `user` 上下文传递，不因前缀缓存优化而混入稳定系统指令；已冻结的请求与重试不会重新读取当前指令来源。

路由选择器保存期望值，实际资源版本由 Core 的安装回执确认。根会话、子会话、冷恢复、继续和机器人输入共用模型解析与兼容性检查，配置观察者只通知各会话重新读取自身选择器。选择器失效时，新的显式模型受理返回诊断，保留已经有效的执行资源，等待用户修正选择或更新配置。

执行侧文件位置属于宿主运行时事实，而非首轮固定的用户指令。统一装配流程根据当前项目、会话与实际工作区绑定生成 `studio.session-files`，声明执行侧的 `scratch`、`artifacts`、命令输出目录及其所属的本地或 SSH 环境（目录布局见 [17](./17-studio-storage.md)）。新建根会话、子会话、审查会话（reviewer）、冷恢复与工具刷新均消费同一份路径事实，本地目录模式（`directory`）的临时目录访问许可同样消费该值。恢复后的最新宿主事实在安全的模型边界替换同源（`source`）旧值，不重新渲染历史请求或篡改已冻结的请求；上下文压缩同样保留最新宿主事实，不被旧摘要中的路径覆盖。宿主内部数据库、归属清单与传输暂存目录不作为模型可写目录暴露，平台提示词与通用系统提示词负责阐明这一边界。

## 14.2 输入受理与驱动

ACP 实例的 Host MCP 服务、HTTP 或 IPC listener、连接驱动、请求任务与其 join 归原实例资源所有者，与准备、发布和关闭共同收束。共享 MCP handler 通过领域端口访问唯一的 `AgentHost`，HTTP 在原进程直接调用，stdio 服务通过本地 IPC 调用；不以 HTTP MCP 作为 stdio 的底座。可信身份绑定具体资源实例，传输会话不能更换调用者。stdio 程序由 Agent 按正式配置启动，属于同一受监督 ACP 进程树；它不拥有产品存储、协作事实或独立重试任务。实例关闭先拒绝新域调用并唤醒等待，同时推进 ACP 取消与权限结算，最终收束服务、连接、请求及所属进程，映像租约保留至实际回收。MCP 取消、IPC reset/EOF 结束观察与尚未受理调用，不能撤销已移交原业务 owner 的操作。部分失败保留原句柄与错误供原关闭流程重试，其他资源继续清理，不以 drop 或取消通知代替进程退出与任务汇合。具体协议、打包与凭据边界见 [28.12](./28-acp.md#2812-host-mcp-与宿主指令)。

用户输入按调用方提供的稳定 ID 幂等受理。`pl-core` 统一采用纯立即消息语义（不设内核排队队列）；Studio 统一经 `submit_prompt` / `submit_prompt_cancellable` 受理并启用驱动：会话空闲时直接启动新轮次；若当前轮次正处于准备期或流式生成中，则在受理新输入后对当前步发起软抢占，合并待消费输入继续在同一轮次推理；若当前正在执行常规工具批次或等待子任务，则保持常规工具继续完成（同时立即唤醒正在等待的 `wait` 调用），在下一步模型请求准入时按 FIFO 顺序将每条待消费消息独立写入上下文。飞书机器人如需严格“一消息一回复卡片”，则在 Bot 回复协调层按 `thread_id` 获取 `thread_reply_gate` 串行化回复生命周期，再复用同一 `submit_prompt_cancellable` 入口。重复提交相同输入身份仅返回原始回执，不重新启用驱动或重放已消费输入。

HTTP 接口使用 `POST /api/v1/threads/{thread_id}/prompts`（`prompt.submit`），FRB 接口使用 `submitPrompt`；请求的 `input` 载荷包含稳定的 `inputId`、`text` 与 `attachmentDraftIds`。同一 `inputId` 的重试必须保持原始内容；由于附件草稿在首次受理后即提交转正，重复请求会先从权威输入记录返回原始回执，再决定是否需要准备资源。输入受理不伪造 `Turn` ID：提示词提交返回 `inputId` 及首次受理该输入的提交序号（`commit` sequence），客户端通过同 ID 的输入时间线条目关联实际轮次；轮次 DTO 与轮次时间线条目保留关联的 `inputId`，即便模型准备失败也能将错误关联到已受理输入，无需复制从未交付给模型的用户消息。输入受理与模型准入属于两次独立提交：受理成功即返回跨窗口、跨重启稳定的幂等回执——稳定 `inputId` 的最小身份与产生它的状态副作用在同一历史事务中写入，重复提交优先查询该持久化身份索引（见 [15](./15-session-storage.md) §15.3）；仅当模型准备完成且权限与容量复核通过后，输入消费状态才与实际请求记录及每条消息独立的用户上下文条目（`input:<input_id>`）在同一事务中提交，并写出隐藏审计元事件（`input_consumed`）。准备失败时保留待处理输入，驱动暂停不会自动触发产生费用的重试请求。

在途抢占或等待期间到达的多条立即输入均保持 `Pending` 状态并拥有单调递增序号（`ordinal`），在下一份模型请求冻结时严格按 `ordinal` 升序逐条作为独立 `ContextSource::User` 记录并入上下文，每条输入独立保留受理与消费事实（含 `injectedMidTurn` 标记）；模型准备期间或准入前触发软抢占而未消耗完的新到达输入保持 `Pending`，不会提前丢失。附件在输入受理前完成保存并校验字节长度与摘要，完整的业务元数据随实际模型上下文一同进入会话；附件草稿仅在输入成功受理后提交转正。

会话执行驱动状态归属于统一 `ExecutionDriver`（`Idle`、`Active`、`Stopped`、`Failed`）：普通消息在未处于显式停止或失败暂停时直接驱动就绪输入；只有显式停止（`Stop`）与不可自动恢复的执行失败会进入阻止自动启动的暂停/失败态，需由新用户输入、继续命令或交互解决显式恢复。物理取消的目标与执行驱动状态正交，停止操作优先触发 `turn_cancel` 并等待在途模型与工具清理完毕。当前输入集合仅维护一份权威列表，不保留第二份排队队列或兼容投递策略。
无内容继续由可信入口提交 `operationId`、冻结的 `expectedContinuationToken` 与模型路由版本。运行时先完成冷激活，再获取会话操作许可并复核准入；同一操作的重试先回查原 owner 回执，不重新授权。继续点在接纳控制时消费，准备失败形成新暂停原因，不恢复旧 token 或原输入。

`readContinuationOperation` 必须同时携带原 operation 与冻结 token。`Known` 返回原 acceptance epoch、预约的 `executionId`／`turnId`、RAM `acceptedRevision`、原 receipt 和 `Scheduled`／`Effective`／`NotExecuted(reason)`；`NotAccepted` 仅表示 token 仍属当前 owner 且尚未消费。缓存未命中且 token 已失效、换代或没有当前冷态资格时返回 typed `StaleContinuation`。客户端只有收到 `NotAccepted` 才以同 ID 重发，通过原操作的 disposition 与执行关联观察生效，不等待虚构输入消费，也不把后来其他执行的活动当作本次生效。准备前 Stop 结算为 `NotExecuted`；模型请求正式准入才为 `Effective`。控制缓存、恢复与清理责任见 [16](./16-core-contracts.md) §16.1。

准备期即分配唯一执行编号并在建立轮次后保持不变，停止按该编号核对目标；重启不复用旧物理执行编号。重启后的遗留运行结算为中断并保留继续点，载入本身不发起模型请求，只有用户显式继续或父调度消息才会执行。

持续消费输入队列的驱动器归属于 `Thread` 执行体（actor）：Studio 显式启用驱动并传入通用步骤上限后，执行体串行处理已受理输入，产品层不为每条输入派生旁路执行任务。普通所有者命令在下一轮驱动前处理，使模型与工具配置更新得以在轮次边界生效。执行失败、交互暂停或达到步骤上限都会停止驱动，防止自动重复发起产生费用的模型调用；受理新输入本身不解除暂停，宿主必须显式发起继续命令。驱动状态仅描述物理执行，冷恢复时不会自动激活驱动。

根会话与子会话共用同一套 `Thread` 机制；预设解析、工作区分配、父子目录维护、派生/关闭（`spawn`/`close`）及消息路由由 Studio 统一协调，工具层仅调用宿主端口，不维护第二套子智能体运行时。目录写策略、工作树物理隔离和工具放行策略是不同边界，具体语义见 [04](./04-security.md)；工具放行不扩大用户授权，也不使 Shell、Git 或 MCP 正文成为受静态拦截的沙箱。

“立即插入”操作在所有者主循环中先持久化受理用户输入，再依据当前运行阶段处理：若无活动轮次，则在同一次推进内开启新轮次；若当前正在准备上下文或执行流式模型调用，则仅触发 Step 子取消令牌 `step_preempt`（保留父级 `turn_cancel` 与活动 `Turn`）并记录 `StepPreemptionEvent`；若流式响应已积累非空助手正文，则将该部分内容保存为不带 `tool_calls` 的 `ContextSource::Assistant` 局部记录（`{attempt_id}:partial`），再将全部待消费输入按 `ordinal` 升序以独立记录写入上下文并发起下一步推理。若当前处于普通工具批处理（`ToolBatch`）中，则不取消在途常规工具，待工具批次提交或交互结束后在下一步推理自然消费新输入。唯有显式停止（`Stop`）或会话关闭才触发 `turn_cancel` 并取消在途工具调用；关闭与显式停止均撤消自动续接意图，后续恢复必须显式触发；普通子智能体或后台通知仅更新唤醒水位，不会抢占当前步骤。

## 14.3 步骤限制、停止与取消

执行预算、步骤限制与取消属于通用类型化执行策略，而预设、角色与父子生命周期决策归属于宿主。步骤策略明确区分无限制（`Unlimited`）与有限步数（`Limited`）：Studio 主会话的新建、恢复与所有续接均采用 `Unlimited`，不因累计模型调用次数或活动总时长而自动停止；子会话每个轮次的上限为 256 步。每个新轮次从零开始计数并获得完整额度，不继承上一轮次的消耗；同一轮次内的模型与工具往返不刷新额度。达到步数上限后会话暂停，显式续接开启新轮次时重新计数。用户停止、会话关闭、交互等待、真实错误与单次外部操作超时独立生效。旧版 `stepLimit` 历史记录保持原样，不自动重启已停止的任务，且不得通过产品层 JSON 字段篡改内核控制行为。

携带预期轮次身份的中断请求由会话主循环在所有者内部核对，仅取消匹配的当前执行代次；产品层不得先读取快照再去取消一个可能已切换的轮次。显式停止触发 `turn_cancel`，同时将驱动置为已停止并保留未消费的待处理输入，后续继续执行必须由显式继续命令或新输入恢复。轮次取消时，已准入但尚未启动的工具调用直接以取消结果收束而不执行外部副作用，并与轮次取消终态在同一提交中发布。会话关闭同样先收束未启动的工具调用，再关闭工具实例，避免留下未配对的调用历史。控制取消使用父子两级 `CancellationToken`：`turn_cancel` 仅服务显式停止与会话关闭，其子令牌 `step_preempt` 专用于立即消息引发的步级软抢占并在发起下一步时重置；二者均不共享可变对话记录或跨轮次复用。

当模型调用被运行时取消令牌中止时，模型实现必须以取消语义上报结果，不得归类为账号不可用或传输失败。内核随后根据 `soft_preempted` 区分收束路径：属于立即消息步级软抢占时，保持 `Turn` 活跃、发射隐藏 `StepPreempted` 元事件、将已收到的非空部分文本保留为无错误标记的 `Commentary` 完成条目并在同轮立即重入下一推理步；属于 `turn_cancel`（显式停止或关闭）时，才将该轮次收束为取消终态并停止自动继续；真实的账号故障、请求超时与传输错误仍保持原有失败语义。取消判定始终依据当前步骤与轮次的取消事实，不得仅凭错误文本或同一时刻的其他并发信号推断。

## 14.4 后台工具任务与交付

同一会话的后台工具刷新、工作模式重配置与关闭由同一安装所有者串行协调。准备过程支持取消，提交前校验所属代次，内核工具目录与宿主物理绑定的提交不得与其他安装过程交错。关闭流程先封闭刷新准入，取消并等待在途准备及候选资源清理完成，随后释放工作区租约。关闭成功意味着该会话不再持有后台刷新任务或未接管的候选资源；若清理失败则保留原对象与错误状态，不发布成功回执，也不清空其他有效代次的工具实例。

会话所有者统一接纳前台与后台工具完成，工具任务先记录真实 `Running` 再执行。普通工具的并发段、共享快速窗口、前台屏障和容量失败契约见 [09](./09-tool-runtime.md) §9.4。转后台只改变交付方式，保留原任务与租约；完成时接纳已知结果、任务终态及完成消息，后续请求按准入边界消费。任务回执和最终结果是独立事实，结果仅安装一次；归档失败由原 writer 持有待写义务。

工具等待调用（`wait`）仅报告就绪状态，完整的后台任务结果由模型准入阶段统一消费，防止 `wait` 返回值与收件箱重复交付。任务状态查询不消费消息；任务取消调用仅提交取消意图并触发执行令牌取消，直至物理执行与资源清理彻底返回后才生成任务终态，不得将取消请求已发出（`Requested`）视作已取消完成。重复取消不会重复提交，已达终态的任务不可被取消命令改写，取消单个后台任务也不会取消其所属轮次。任务查询、等待与取消仅接受本会话回执中的完整 `taskId`，未知任务一律返回 `TaskNotFound`，不猜测前缀、不转换大小写，也不泄露其他会话的任务信息。

`wait` 工具同时观察指定的后台工具任务与未消费的会话消息，任一所选任务进入已提交终态或任一消息就绪即刻返回，无需等待全部任务完成；当 `taskIds` 为空时仅等待新消息（含子智能体终态报告）。`sleep` 工具产生的后台任务回执与其他工具任务共用同一套身份标识与就绪规则，定时器到期同样参与就绪竞争。若调用前目标已就绪则立即返回；单次返回可包含多个已就绪来源，但不承诺还原同一调度间隙内各事件的物理先后次序。

任务状态、`messagesReady` 与 `timedOut` 由同一等待原语判定。等待截止时间点固定，不因无关通知而重置；到达截止时间时先复核已提交的就绪事实，只要存在任一就绪来源即返回就绪而非超时。正常超时既不伪造任务完成，也不取消被等待的后台任务。常驻内存台账淘汰不代表任务未知：等待原语可按需读取本会话持久化的任务终态事实；对于真正未知的任务 ID、跨会话任务、等待自身调用、调用授权失效或存在待提交结果等情形，仍按各自明确的类型化错误拒绝，不以“未知状态”伪装成功返回。取消或释放等待调用仅放弃本次观察；会话关闭、调用取消、存储读取故障与正常等待超时具有严格区分的结果语义。

完整的业务载荷（payload）、实时观察结果、实际交付给模型的上下文（`delivered context`）与任务终态分别保存。失败的任务仍可附带已观察到的输出；取消后迟到的执行结果照常保留供审计，但不再应用其中的扩展状态变更、交互请求或轮次结束控制。模型历史记录消费当时保存的交付上下文，不得使用当前渲染器重新解释历史业务正文。

当工具执行完成但状态提交因存储背压或故障失败时，会话所有者保留原始完成对象与执行租约，并暂停新模型请求准入；后续提交重试直接复用已完成结果，不重复执行工具。完整载荷与交付上下文随会话历史统一保存，不按工具类型拆分表结构。大型二进制对象或长输出文件通过携带摘要与字节长度的稳定资源引用保存；单页预览、临时文件路径或尚未归档的原始捕获文件不替代完整资源引用。

`exec_command` 与 `write_stdin` 共享会话私有的进程管理器，且任务身份校验先于内部进程映射。命令输出流必须彻底排空后方可执行归档，远端归档通过真实的远端范围读取拉取数据；若归档失败则保留源捕获文件供重试，不重新执行命令。物理路径权限与工作区边界由工具后端强制执行，内核不根据工具名称或参数中的路径字符串猜测授权。

Studio 统一装配根会话、子会话与冷恢复的工具及物理服务。动态目录刷新保持有效租约并复用命令管理器。SSH 重连保留服务器身份、工作目录与权限边界，替换失效连接对应的实例。旧连接任务按原身份记录中断结果，标准输入仍按原进程身份解析。Core 同时发布工具目录、物理绑定与此次装配的技能等运行时事实，Studio 从只读端口读取该版本。工具刷新按会话独立推进，合并重复通知，等待安装期间仍可以提交输入和停止。关闭时收束在途准备与全部实例，失败的清理保留进度供重试。

## 14.5 消息与统一唤醒

跨会话或后台消息按稳定 ID 幂等受理，消息来源与上下文载荷不得冒充 `system` 角色或伪造审批状态。消息消费水位与模型请求准入在同一提交中生效；若请求准备失败或在准入前被取消，消息保持未消费状态。显式用户输入、后台消息与界面观察各自具备独立语义，后台消息到达本身不会隐式触发产生费用的模型调用。在模型推理与工具执行期间，会话所有者继续受理消息投递与历史读取：新到达的消息写入同一所有者的有界收件箱并持久化提交，但不改变已冻结的当前请求或上下文，仅在后续模型请求准入时被消费。收件箱通道容量有界，不维护第二份会话状态，也不得绕过会话关闭时的受理门禁。

运行时内部通知仅用于提示状态可能发生变化，并非需要逐条消费的业务事件。观察者遵循“先注册订阅、再检查当前状态”的顺序；每次被通知唤醒后重新核对已提交的任务终态与消息消费水位，从而允许底层合并通知而不丢失就绪信号。后台任务、定时器与子智能体消息不维护各自独立的等待者登记表，所有等待操作统一复用会话所有者的状态发布边界。

宿主在投递消息时可显式请求唤醒目标会话：唤醒水位随消息受理一同提交；若当前活动轮次在结束前已顺带消费了该消息，轮次结束后不再额外发起模型调用；若会话空闲且存在未消费的唤醒消息，则通过运行时上下文启动新一轮执行，不伪造用户消息；冷恢复保留持久化的唤醒事实，但仍需宿主显式恢复驱动才会开始执行。

## 14.6 生命周期与观测

应用启动只加载轻量会话目录摘要（`catalog`），不遍历或激活历史会话。显式激活时读取并校验完整 `current.json`；缺失/损坏或产品目录关联无效时明确报错，不创建空会话掩盖数据丢失。显式停止/关闭先封闭准入、取消在途执行并等待物理资源退出，再由 Current writer 执行最终捕获与保存、HistoryChannel flush pending，两类结果分别报告。冷恢复将旧运行显示为 paused，不恢复执行器、不重放副作用。

实时状态订阅消费 `CurrentReader` 的 tiny snapshot/watch；History 通过独立 `HistoryReader` 直接读取 schema 25，即使执行 owner 已关闭仍可查询已 flush facts。启用命令行运行归档（见 [29.6](./29-cli-harbor.md#296-运行轨迹用量与关闭结果导出)）时，`RunExporter` 使用登记时保留的 HistoryReader cut，从 canonical originals 读取；它不重建 current 或激活执行 owner。Current/History writer 的失败与未保存事实分别可见，目录写入器不代理会话 History、Current 或通用 Core checkpoint。

## 14.7 交互与业务状态的宿主侧路由

Studio 从内核通用的交互与权限快照（`interaction`/`permission` snapshot）投影产品层提问卡片，并依据编码了会话归属的不透明交互 ID 路由用户回答。计划（Plan）与工作流（workflow）状态由 Studio 负责解释，状态更新采用扩展 CAS 机制；用户回答、扩展状态变更、模型可见上下文投影与续接输入（`continuation` input）在同一内核提交中原子生效。重复提交相同回答仅返回幂等回执，不重复入队或自动触发驱动。

工作模式切换采用空闲重配置策略。安装时复核状态水位与空闲条件，一次提交业务扩展、目标模式的模型选择器、已打开的模型、系统上下文与工具资源。已持久化的历史正文继续按当时的内容展示。普通用户提问、计划确认与执行权限审批共用 Studio 的类型化交互路由，路由层直接从内核快照读取待决事实。用户回答与隐藏续接输入在同一响应中提交。对外的交互 ID 同时标识所属会话与会话内部交互，客户端原样透传。
