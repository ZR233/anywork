# 16 - Core 内核契约

本文定义 `pl-core` 的不透明载荷、通用上下文、模型调用契约、扩展 CAS、交互解析及跨 crate 能力归属边界。crate 依赖方向见 [02](./02-crates.md)，状态与历史存储见 [15](./15-session-storage.md)，Studio 宿主运行时行为见 [14](./14-runtime-host.md)。

## 16.1 所有权总则

`pl-core` 拥有会话（`Thread`）、轮次（`Turn`）、模型与工具调用契约、通用上下文、交互状态、后台任务、消息收件箱、当前状态检查点（checkpoint）及不可变状态副作用（effect）；`pl-model` 与 `pl-tool` 分别实现内核定义的模型与工具接口；网络搜索工具消费 `pl-model` 已解析的模型能力，依赖方向严格遵循 [02](./02-crates.md)。`pl-trace` 只读消费内核观察接口。`pl-studio-runtime` 拥有配置持久化、项目管理、智能体预设（Profile）、工作模式（Mode）、工作流（workflow）、计划（Plan）、子智能体协调及唯一会话装配入口，根会话、子会话与冷恢复共用同一装配路径。内核不提供默认工具集、Git 操作、技能（Skill）扫描或预设自动安装入口：`pl-tool` 的工具组仅负责构造标准工具实例，由 Studio 显式注册并单独注入计划与工作流等业务工具。文件系统操作、容器隔离、技能工具、`exec`、命令任务管理及 SSH 客户端归属 `pl-tool`；宿主子进程创建策略的唯一实现归属 `pl-remote-helper`；GUI 桥接层（bridge）通过 Studio 的 SSH 接口类型映射通信，不直接组合工具运行时。每个会话独占工具管理器、工具实例与模型会话；底层物理服务按身份与隔离边界通过租约共享，关闭单个会话不会撤销其他会话持有的服务租约。

`Session` 的聊天时间线能力见 [15](./15-session-storage.md)：会话所有者（`Thread` owner）仅负责推进执行并生成不可变状态副作用；产品无关的内核 `Session` 共享有界 `TimelineState`，向上层提供无状态历史分页、独立尾部订阅与按身份详情读取，自身不持有可见窗口或滚动位置（接口契约见 [26](./26-timeline-content.md)）。`Session` 不依赖 Studio 协议、Flutter 或物理模型连接，由宿主按需注入基于顺序键（`ordinal`）与条目身份（`item_id`）的历史存储读取能力。读取冷会话历史无需构造模型会话、工具实例或执行所有者。宿主将单次状态提交投影为稳定的 `ChatItem`，同步发布至 `TimelineState` 与可靠历史写入器，最终按内容版本（`revision`）确认落盘并原地更新同一条目身份；宿主不得根据 GUI 当前是否建立订阅来决定是否保留未落盘事实。发布与订阅的同步内存边界位于 `pl-core`，而 SQLite 历史事务与具体业务载荷投影则归属宿主。

### 有界驻留事实读取

完整 `ThreadSnapshot` 仍用于需要完整状态的调用方；只为判断交互等待和输入是否已受理的
消费者不应复制整份快照。`thread::decisions` 定义平台无关的决策摘要与读取额度：摘要
只包含原身份、Turn、revision 及 typed 状态，保留 Interaction 与 Permission 的区别，
不携带提示、响应、上下文或 continuation。摘要不构成权限或持久保存证明；已从驻留
状态退役的决策须由宿主可靠历史提供，不能把驻留集合缺失解释为无历史事实。

`ThreadHandle::decision_summaries(DecisionReadLimits) -> DecisionRead` 同步读取一次一致的
驻留状态，在复制任何身份前核行数和 owned 身份字节额度；返回完整摘要及真实使用量，
或 `LimitExceeded`，不暴露不完整前缀。零额度允许真正空集合，不把越限当作空集合。
读取不解码业务载荷、不等待执行 owner、不跨异步等待保留状态借用，也不改变执行状态。

`ThreadHandle::read_input_presence(&str, usize) -> InputPresenceRead` 在明确最大检查行数内
判断原输入是否仍在待处理或有界终局身份集合中，区分 Known、Absent 与 LimitExceeded，
并返回已检查行数；不复制输入正文。Absent 只表示本次驻留范围内不知该身份，宿主仍须
结合自己的可靠身份索引裁决。上述预算由调用方纳入其单轮共同限额，不隐式每项重置。

## 16.2 不透明载荷与通用上下文

内核载荷由格式标识（`format`）、版本号（`version`）与原始 UTF-8 字符串组成。`pl-core` 不强制要求载荷为 JSON，不解析内部字段，也不执行格式化或改动数字精度、空白字符、换行符与字符编码；内容摘要与字节容量严格按原始 UTF-8 字节计算，未知格式与未知版本的载荷仍可原样存取。上层模块需要使用 JSON 结构时，在各自的编解码（codec）边界自行解析。二进制数据统一通过带完整性校验的资源引用承载；普通资源上下文仅表达资源引用元数据，实际嵌入模型请求的媒体内容则由 `pl-model` 的无角色附件投影显式表达，防止大体积原始日志被自动展开内联。

工具执行结果拆分为完整业务载荷与当时实际交付给模型的上下文投影，两者在同一提交中原子落盘；模型返回的合法函数调用（`function`）参数同样以原始字符串作为唯一权威载荷保存，解析校验通过后不得丢弃原始空白、字段顺序或数字字面量——协议 schema 校验与界面展示解析均属派生操作，历史请求重编码直接复用已保存的参数原文，执行关联摘要也直接基于传入执行器（executor）的原始参数字节计算。工具输出不得自行指定 `system` 角色，框架统一根据调用身份构造工具结果记录。工具名称或 MCP 服务前缀不赋予任何额外的工作区路径访问权限；权限审批、轮次结束、任务取消与状态提交必须通过可信的框架控制接口触发，禁止从工具返回的文本或 JSON 载荷字段中推断。内核按事实提交顺序保存工具结果，模型层则对完整工具调用批次按原 `assistant` 消息中的调用声明顺序执行确定性协议投影：该投影仅重排同一批次内的工具结果顺序，不篡改载荷内容、调用关联或已提交的状态副作用；工具产出的媒体附件同样按调用顺序排列并置于完整结果批次之后；若发现结果缺失或重复则明确拒绝。

公开会话产物沿用同一不透明工具结果提交通道，由 Studio 依据受信调用与版本化回执投影生成；`pl-core` 不解码发布字段，不处理文件路径或外部受众，也不将资源上下文自动视作外发意图。产品发布、本地保存确认与渠道送达的独立语义见 [29](./29-conversation-publication.md)。

通用上下文记录信封显式保存由 `assistant` 发起的工具调用列表（包含稳定工具 ID、调用 ID 与不透明参数原文），不将工具调用混入回复正文或业务扩展载荷；后续模型请求仅凭已冻结的上下文快照即可完整重建工具调用与 `ToolResult` 的配对关联，上下文整体替换时亦强制校验调用 ID 唯一性、结果归属及配对完整性。在单次 `assistant` 工具调用批次与其对应的全部工具结果收齐之前，禁止在中间插入其他角色的上下文消息：通用上下文校验直接拒绝未完成调用批次被其他记录打断；当会话存在待交付的工具调用时，会话的运行时事实与应用更新入口拒绝插入新上下文，宿主须待工具结果提交完成后再行重试。

`pl-core` 不提供跨会话的历史记录继承选项，也不解析或迁移供应商私有续接记录、附件与资源归属。Studio 创建子会话时，使用冻结预设的系统指令、产品初始事实以及父智能体显式提交的自包含任务说明构造全新的独立上下文，严禁将父会话的对话历史复制进子会话。跨会话协作统一通过显式消息投递完成。

历史回放与展示直接消费 Studio 在状态副作用提交时保存的投影快照，不调用当前工具集、当前渲染器或当前全局配置去重新渲染历史正文；已提交载荷保持不可变，上下文替换与裁剪仍保留历史版本记录。即便上层业务解码器（decoder）缺失，底层仍可按原始记录读取；但若继续执行所必需的核心逻辑状态无法解析，则必须按失败关闭处理，不得静默替换为空值。供应商私有上下文变更采用显式的“设置/清空”枚举表达，避免在 JSON `null` 序列化往返中混淆“状态未变更”与“显式清空”。

新建会话的初始上下文由 Studio 显式传入，在对外发布会话所有者之前完成提交并通过通用工具调用配对校验；恢复既有检查点时禁止同时传入非空初始上下文，防止当前工作区、技能列表或最新配置覆盖已冻结的历史上下文。子会话的独立上下文与创建期指令装配遵循 [12](./12-collaboration.md) §12.2，不设继承父会话历史或按旧记录重放工具的兼容入口。

长期项目规则按内容版本冻结；动态运行时上下文发生变化时仅追加完整的新快照，内容未变则不重复追加，显式清空时追加旧快照失效声明，执行上下文压缩时则移除旧快照并在尾部重新补入当前有效值。会话接收上层提供的完整运行时事实集合，按稳定的来源标识（`source` ID）仅对发生变化的正文追加新记录，被省略的已知来源则自动追加失效记录；所有此类记录均保持 `Runtime` 来源标记，不提升为 `system` 系统指令。

继续点、准备期执行身份和输入用途属于 core 的执行契约，产品不复制为第二套可写状态：

- **继续点**：可恢复的逻辑事实，只引用已有输入或收件箱消息的认领，不携带任务正文、进程句柄或不可序列化的运行资源；实际模型请求准入时随消费事实在同一提交清除，准备失败不消费。
- **执行身份**：在选定工作后、等待保存或准备模型前形成，独立于轮次是否已经创建并在建立轮次后保持不变；产品以该身份精确停止，不用当前快照推断目标，重启不复用旧物理编号。
- **输入用途**：明确区分普通消息与无正文控制。控制只能由受信宿主入口构造，上下文为空、载荷只记录所认领的继续点与来源轮次，不能由载荷内容、固定文字或空字符串推断；普通消息不得占用该保留格式，父消息同样在受理期被拒绝。
- **批次消费**：一次继续可以由未消费输入、控制输入与可消费消息共同组成一个批次；批次消费、消息水位与轮次关系同一提交。业务输入仍只来自普通消息，控制不伪造用户正文。
- **投影边界**：投影按用途分类，写入侧据此标注原始记录的来源；读取方信任已写入的事实，不按载荷形状重新解释历史，也不据此授权执行。
- **职责边界**：核心只表达状态、身份与提交顺序，不解释用户与父智能体的操作权限，也不决定交互展示位置（见 [14](./14-runtime-host.md) 与 [12](./12-collaboration.md)）。

## 16.3 模型调用契约

活动会话已提交的内存上下文是后续模型请求的唯一事实源。模型适配器在成功输出的不透明帧中携带完整的 `assistant` 协议回放材料，内核不解析供应商私有字段；回复正文、协议回放材料、调用绑定与更新后的模型私有上下文在同一状态提交中原子落盘。持久化层仅原样保存这份已冻结事实，异步落盘时序不影响历史正文内容与顺序，可靠保存准入与背压暂停语义保持不变。冷恢复先将权威检查点完整装入内存，随后沿用完全相同的模型请求链路。

单次已准备模型调用（`prepared call`）固定绑定同一模型实现、能力集、可见工具声明与冻结输入。通用会话所有者通过模型会话的 `prepare` 接口冻结输入，通过准入检查后一次性发布模型请求与关联上下文；模型产出的回复正文与下一份私有续接上下文在同一快照提交中生效。在准入前或准备阶段取消不会消费待处理输入；准入后发生调用失败则保留本次尝试事实；准入后被取消时，仍完整保留模型最后返回的候选输出或失败记录（含已知词元用量）作为已取消尝试的观察事实落盘，但不推进当前有效正文、工具调用或私有续接状态——禁止仅保留词元用量而丢弃已接收的原始输出事实。底层传输透明重试不会重新扫描工作区文件、刷新工具目录或追加新输入。

系统提示词的来源组合与供应商协议分发分别归属宿主与模型适配层：`pl-core` 仅保存供应商无关的指令记录、完整指令快照及其修订号、内容哈希与替代关系，不引入供应商通信角色（wire role）或产品层智能体类型。宿主统一组合各受信指令来源，模型适配层将其转换为类型化系统提示词并按冻结绑定分发；追加或归并候选与当前来源版本在同一提交中生效，若准备被取消或失败则不得提前发布新指令版本。具体角色映射与前缀缓存契约见 [06](./06-model.md)。

冻结请求中标记为独占调用（`Solo`）的工具身份，必须属于同一次请求的可见工具声明集合。当宿主按工作模式排除部分工具时，上下文容量估算、压缩预览与最终请求准备必须消费同一份排除集合，同步裁剪工具声明及其独占调用约束；既不得残留指向已排除工具的约束身份，也不得让模型适配器静默忽略此类不一致。历史上下文用量作为候选观测值传入准备器；模型层在完成工具过滤与指令修复后，通过 `PreviousContextUsage::matches_input` 核对保留前缀与最终工具计划，并复核模型路由绑定。过滤前的全量注册工具集不得提前否决有效的历史用量观测；一旦前缀、最终工具计划或模型路由绑定任一不匹配，即禁止复用历史用量。

已准备调用可附带模型实现给出的输入词元估算值，并显式标明该估算为精确值还是近似值；会话容量策略明确配置是否接受近似值或未知值，超限拒绝发生在输入消费准入与实际网络调用之前，且请求记录完整保留当次实际采用的估算值，不根据字符数在外部重新推算。已准备调用还可携带由 `pl-model` 编码的不透明工具投影材料：内核不解析其内部格式，随请求准入一并冻结保存，并在执行该请求触发的工具调用时原样透传；工具实现不得读取全局可变模型目录去反向推测已受理请求的能力。同时，已准备调用生成不透明的请求元数据，记录当次实际规范化后的工具声明、路由绑定与生成参数；即便调用失败也原样保留当时的参数快照，不按当前最新配置事后重建。此外，已准备调用可携带供应商无关的用量绑定 `ModelUsageBinding`（包含模型标识、有效上下文窗口、模型最大窗口及最终自动压缩阈值），随已准入的尝试与状态副作用一同冻结；窗口与阈值均为可选词元数，通用会话用量折叠仅原样传递该事实，不解析压缩策略或解码模型私有元数据。若未提供绑定或新绑定缺少某项指标，当次尝试的对应指标即记为未知，不沿用上一模型实例的旧值。

显式重试分配新的尝试 ID（`attempt` ID）并记录 `retry_of` 引用，直接复用失败尝试已准入的上下文与已冻结的工具租约，不重复消费用户输入；唯有当会话当前上下文未发生变更、且工具目录未撤销或修改相关工具声明时才允许显式重试，否则要求宿主重新准备新的执行请求。重试计划复用校验同时比对工具声明与类型化控制权限：底层执行器重连本身不改变模型输入身份，但若工具控制权限被撤销，旧计划即不可重试；`retry_of` 必须指向同一轮次内已失败或已取消的真实尝试，禁止通过篡改引用伪造重试记录。模型传输层内部的透明重试则由 `pl-model` 在单次已准备输入内部自行消化。

模型层的透明重试仅推进供应商无关的模型观察代次（observation generation），不创建新的内核 `attempt`，也不消耗额外的轮次步骤预算。模型流式观察快照严格区分当前活动子尝试、已结束的失败子尝试以及类型化恢复状态；始终保留原始供应商条目与分片身份，重试代次通过独立字段表达，不伪造供应商原生 ID。默认代次为首次尝试，历史旧记录缺少该字段时不推测曾发生过透明恢复。观察快照必须保留有界的失败子尝试观察与恢复边界，确保 `watch` 合帧或慢速消费者不会丢失代次切换边界；同一代次内的内容版本单调递增，进入新代次时不得复用旧代次的内容版本号与展示身份。

已结束的失败子尝试观察与恢复结果随最终的成功、失败或取消回执一同持久化，仅作为界面展示与审计事实，不并入成功输出的权威正文、工具调用列表或供应商私有续接上下文。`pl-core` 仅提供通用的流式观察、身份管理与输出预算原语，不解析底层网络协议或制定重试恢复策略。单次模型调用的可靠输出字节预留同时覆盖当前活动子尝试与已保留的失败子尝试正文，当增量因超出预留被拒时，保留已接收字节并明确报错失败，不得按透明重试次数反复重置或刷新输出配额。实时流与终态收束规则遵循 [07](./07-streaming.md)，持久化旧记录解码与数据保留遵循 [17](./17-studio-storage.md)。

通用的资源读取器（`ResourceReader`）由宿主注入，模型请求在准备阶段捕获资源访问租约；读取结果严格按资源引用声明的字节长度与 SHA-256 摘要校验，文件缺失或内容被替换时直接报错失败。内核不根据文件路径或 URL 猜测资源类型，也不将二进制数据强制转换为字符串。当底层资源服务绑定发生变更时，旧尝试持有的显式重试租约即刻失效，必须重新准备新请求；但该物理服务绑定身份不计入模型前缀缓存键（cache key）。

模型会话的调用准入租约在所有克隆句柄间共享，同一时刻仅允许单个调用（invocation）进入执行；关闭模型会话时先封闭准入，再等待在途调用释放租约。模型传输层的后台收包任务必须由会话显式关闭并等待汇合退出，禁止仅依赖析构函数（`Drop`）即宣称会话已关闭；会话关闭采用共享的关闭异步任务（shared close future），单个等待者被取消仅放弃本次等待，不会丢弃底层连接或后台任务句柄。若模型实现在准备或执行期间发生异常恐慌（`panic`），动态会话入口立即标记为不可用；会话所有者保留失败记录与关闭重试能力，待宿主恢复时重新装入新的模型会话实例。在请求准备期间临时借出模型会话不会改变绑定的可用性状态，期间邮箱查询或进度发布仍须如实报告原会话可用；准备调用返回后重新核查会话健康度，确保真实的 `panic`、连接关闭或替换失败不会被临时借出状态掩盖。

上下文摘要压缩使用独立的临时模型会话，默认复用当前模型绑定、已冻结的工具声明与连续历史公共前缀，并在尾部追加摘要生成指令；压缩过程不执行任何工具，也不推进主模型会话的续接状态（`continuation`），唯有生成成功才原子提交上下文替换，失败则完整保留原历史。文本摘要请求强制将 `tool_choice` 设为 `none` 并移除所有供应商托管工具（provider-hosted tools）；若请求失败，禁止静默删减历史记录或篡改参数自动重调，以免产生隐藏的额外尝试或丢失词元用量统计。取消或超时后迟到的摘要结果不再触发上下文替换；压缩流程必须等待模型执行与临时会话关闭彻底收束后，再将已观察到的词元用量随失败事实一并返回。对于供应商原生压缩能力，由模型层接收已冻结的模型请求、选择实际协议版本并校验返回的唯一检查点，连同真实计费数据一并返回；内核不构造原生压缩协议参数，历史保留策略仅负责组合已验证的替换材料。通用压缩配置仅表达 `TextSummary` 或 `PreferNative`，压缩观测结果仅表达 `Local` 或 `Native`。文本词元启发式估算由 `pl-model` 提供并显式标明为近似值；当遇到多媒体附件、加密检查点或无法静态确定词元语义的原生协议材料时，统一返回“未知”，不回填零值或复用压缩前的旧估算值。

真实模型的会话适配器实现内核模型端口：`assistant` 历史帧完整保存当时的供应商工具调用名称、原始参数与原生协议材料，后续工具结果严格依据历史帧配对，不使用当前工具目录重写历史调用名称；非 `assistant` 来源严禁提交 `assistant` 历史帧，遇到未知帧版本时阻止发起新模型调用但保留既有历史不被篡改。模型准备阶段先完成原生工具与自定义工具（`native`/`custom`）的协议投影及能力校验，再冻结词元估算与执行请求；自定义工具的函数回退包装（`function-fallback`）属于模型协议层内部细节，由 `pl-model` 解包还原为原始文本后再移交工具执行器，无法合法解包的模型输出直接作为被拒绝的尝试记录保存，绝不路由至可执行工具。供应商私有历史材料能否被当前请求消费，由 `pl-model` 在实际请求入口统一校验。供应商托管工具由模型工厂参数传入，在请求准备阶段与本地工具声明合并并校验名称冲突，不进入内核的工具执行器注册表。模型调用失败时可附带由生产者编码的不透明诊断事实，内核不解析其中的定价字段，仅随失败尝试原样保存并支持冷恢复，不伪造零费用；模型失败的界面展示必须同时保留失败类别与原始错误原因，任何只报类别而丢弃原因的错误封装均视为缺陷。

模型请求准备与上下文压缩发生在常规尝试（`attempt`）准入之前；若在此阶段失败，轮次终态仍完整保留模型错误类别、已产生的词元计量与不透明诊断事实，展示投影不得因尚未生成常规 `attempt` 而将供应商错误降级为永久内部错误。非模型原因导致的失败保留宿主原始原因，内核不解析供应商私有的重试协议。

模型输出准入依次校验请求身份、上下文版本号、工具目录版本与工具调用 ID 唯一性，最后校验独占调用（`Solo`）批次约束；在整批输出全部通过准入校验之前，不启动任何工具执行。准入拒绝错误完整保留具体拒绝类型与原始尝试记录。唯有违反 `Solo` 独占批次约束的错误，允许通用轮次循环自动追加框架纠正上下文并重新请求模型生成（每轮次最多纠正两次，计入当前轮次原有的步骤预算）；其余一致性错误均不自动恢复。当服务端已执行的模型请求明确返回上下文超限（`ContextLimit`）错误时，当前轮次可在剩余步骤预算内最多执行一次宿主强制上下文压缩，压缩成功改变上下文后使用新 `attempt` 继续执行；已失败请求的记录与词元用量完整保留，已受理的用户输入与已完成的工具调用不重复执行。框架纠正通过新建 `attempt` 关联被拒绝的尝试，并从权威已提交历史重新准备请求，被拒绝的供应商私有续接状态不进入已提交上下文；显式取消、会话关闭与持久化保存失败均不可被自动纠正覆盖。

## 16.4 扩展 CAS 与交互解析

通用会话提供扩展状态的批量比较并交换（CAS）原语：所有扩展载荷保持不透明，每次更新分配新版本号，删除操作保留墓碑记录（tombstone）与全局版本水位；批量 CAS 中只要任一扩展项发生版本冲突，整批操作即整体中止，不写入任何部分状态。扩展状态更新不会自动进入模型上下文，也不会隐式触发权限审批或轮次流转控制，上层宿主需另行显式提交模型可见的上下文投影。应用更新（`ApplicationUpdate`）原语支持将扩展 CAS 与上层提供的上下文事实投影在同一候选状态中联合验证并原子提交：任一部分校验失败均不对外发布，成功则仅产出单条 `ThreadEffectBatch`，确保上下文正文与业务扩展状态始终处于同一演进版本；内核不尝试从不透明扩展载荷中反向推导上下文投影。

工具实现可基于只读扩展快照计算 CAS 变更，并随工具执行输出一并提交；此类工具必须在注册时显式声明扩展写入权限，且在模型调用批次中强制独占执行（`Solo`）。内核原子应用工具产出的扩展变更与工具结果；若扩展 CAS 发生版本冲突，则完整保留工具返回的业务载荷，将该次工具调用标记为失败并附加框架拒绝说明，不部分更新业务状态。若工具在执行期间被取消，其迟到返回的完整结果仅作为观察事实保存，不再应用其中携带的扩展变更或轮次结束控制。计划（Plan）与工作流（workflow）的模型工具定义、CAS 参数构造、完成证据校验及业务结果投影均由 Studio 提供（见 [11](./11-thread-mode.md)、[13](./13-plan.md)）；两者的系统指令节标识（`section` ID）由 Studio 定义，内核在冻结请求时统一校验当前请求中所有节标识的唯一性及原始正文摘要，若发现重复来源或摘要不匹配则直接拒绝冻结，不猜测哪一业务来源优先。

释放会话运行资源不会隐式取消已提交的待决交互（`Pending Interaction`）：交互属于可持久化的逻辑状态，会话关闭后由检查点完整保留，冷恢复时亦不会重放触发该交互的工具。显式取消交互与关闭运行资源属于两项正交操作；权限审批则按其独立生命周期收束，禁止通过恢复待决交互来继承已失效的执行授权。

会话交互以不透明的请求/回答载荷及显式的 `Pending`、`Resolved`、`Cancelled` 三态保存；解决交互（`resolve`）时严格校验版本号，回答正文与状态流转在同一提交中原子成立，并保持 `Runtime` 来源标记；载荷内部的 `approved` 等业务字段由上层解释，内核不作解析。交互 `resolve` 操作可同时附带一条通用的续接输入（`continuation` input）：内核在同一候选状态内联合校验交互响应、扩展 CAS、上下文投影与输入幂等身份后一次性原子提交；重复提交仅在响应内容与状态变更完全一致时判定为幂等并返回相同回执，不重复入队驱动。显式取消交互通过携带预期版本号的命令执行，将 `Pending → Cancelled` 状态流转与低权限的取消说明上下文在同一提交中生效，不构造空回答或触发业务扩展变更；版本号过期或交互已解决时拒绝取消。当 `ask_user` 工具返回 `AwaitInteraction` 控制信号与不透明提问载荷时，内核分配与原工具调用绑定的唯一交互 ID，并随工具结果一同提交为 `Pending` 状态；此类交互工具必须具备注册授权且独占模型调用批次，使当前轮次返回 `WaitingInteraction` 并暂停推进，唯有通过显式 `resolve` 提交回答后方可继续后续模型步骤。存储背压暂停不会阻止已受理交互的事实收束，而回答后的续接执行仍须经过正常的模型执行准入检查。

终态交互与权限事实的幂等回执随产生它的状态副作用在同一历史事务中持久化落盘；一旦会话所有者瞬态窗口中的对应批次因落盘完成而被释放，后续重复的 `resolve` 请求即直接由历史库中的持久化回执回答或按冲突拒绝，既不回退至内存查找，也不重放外部副作用（见 [15](./15-session-storage.md) §15.3）。

## 16.5 能力归属与组合边界

配置值对象随解释它们的模块边界归属：系统指令配置归属 Studio，技能扫描配置归属 `pl-tool`；Studio 负责持久化并组合这些配置值，内核仅接收冻结后的上下文快照，不持有配置文件或目录发现策略。`pl-core` 的公共 API 不镜像导出供应商目录、凭据描述符、托管搜索能力或 MCP 服务目录 DTO；Studio 的配置目录模块直接消费由 `pl-model` 构造的产品协议 DTO。模型配置解析（含路由构造与推理强度参数解释）集中在 `pl-model`：会话装配入口接收已构造完成的模型运行时实例及已冻结的调用参数，主执行循环与上下文压缩共享同一份已解析参数。

MCP 工具层仅接收已解析完毕的连接参数与有效凭据，不自行选择模型账号或内置服务；内置服务目录、启用状态持久化及供应商凭据选择统一由 Studio 组合。网络搜索的公共请求格式由独立上层协议承载：独立的搜索 HTTP 客户端、搜索能力规划与工具绑定归属 `pl-tool`，Studio 则负责提供已解析的模型路由与产品配置。排他性（exclusive）搜索装配仅注册选中的搜索工具，不会先创建被隐藏的工作区工具实例。宿主原生工具的启用条件由 Studio 根据已冻结的模型绑定判定，并作为同批工具目录变更原子发布；内核不根据供应商能力标志自行筛选工具。命令执行环境（本地或 SSH、操作系统类型、Shell 方言与可执行文件路径）由 `pl-tool` 探测，Studio 随会话资源绑定一并持有，每轮系统提示词直接从已装配资源读取环境事实。

LSP 语言服务仅随 Studio 显式构造的工作区工具绑定，模型推理引擎在每轮步骤中不接触语言服务实例，文件操作工具在构造时捕获对应的 LSP 服务租约；LSP 注册表接收由宿主解析完成的工作区身份，登记新工作区不会隐式淘汰其他已登记工作区，服务的关闭与回收由持有租约的 Studio 生命周期显式驱动。工具工作区组合对象（含工作区授权边界、LSP 变更通知钩子与文件写入租约）归属 `pl-tool`；内核不返回该组合对象，也不隐式读取进程当前工作目录（`cwd`）为其选择工作区，统一由宿主按配置显式构造。物理路径规范化校验、符号链接与重解析点（symlink / reparse point）检查、安全目录删除及工具路径访问策略归属 `pl-tool` 的工作区模块；物理宿主指纹与工作区组合绑定由 Studio 按每会话资源持有，每轮配置核对直接读取同一份冻结绑定，不重复重建工具实例。标准文件工具通过已冻结的文件系统后端执行，历史记录完整保存当时的执行结果与实际交付给模型的预览，冷恢复时不重新读取磁盘文件；外部命令执行（`exec`）的路径授权独立于文件工具访问授权，禁止利用 `exec` 获得的外部路径许可隐式放宽文件工具的访问边界。

现役子智能体工具的参数 schema、参数解析、历史分页与进度通知源归属 `pl-tool`，具体调用则通过协调宿主提供的类型化端口完成；子智能体的状态查询、停止与关闭请求经类型化宿主端口进入 Studio，调用方身份（caller）直接取自内核分配的调用上下文身份，由 Studio 严格核验所属会话树及后代关系，拒绝跨树控制与自我关闭。子智能体创建通过 Studio 的子会话工厂解析智能体预设、配额限制与物理资源绑定，工厂必须先行核验调用方的派生权限；Studio 从同一份配置快照解析已启用的预设与模型路由，旧版产品入口与新版子会话工厂共用这一解析边界。Studio 在准备子会话物理资源之前先预留会话身份与会话树内名额，处于准备期的子任务同样受树深度与总数量上限约束（现役默认策略仅允许根会话创建子任务，每棵会话树最多包含 16 个会话），且每次预留持有独立的取消令牌。达到上限的派发请求立即拒绝且不进入排队，错误回执保留上限数量并明确指引先调用 `close_agent` 关闭闲置子智能体释放名额后重试。子会话工厂必须提供未发布资源的幂等回收端口：当物理准备、会话装配失败或被取消时，先关闭已创建的内核 `Thread`，再回收尚未对外发布的产品级资源；若回收失败则保留所有者、父子关联及重试入口。物理工作区准备属于 Studio 的产品资源职责，Git 工作树租约必须先持久化记录准备事实，再执行物理创建及失败补偿收束。Studio 新建会话的初始化种子严格区分模型可见上下文与不透明扩展记录：预设指令与选定的工作区说明写入模型上下文，创建期元数据与完整工作区回执则保存为会话扩展载荷。根会话与子会话的初始指令由同一套创建期捕获流程生成，复用已选定的远端文件服务与执行环境，并保存配置、角色与项目文档的来源快照；动态技能推荐不混入这份稳定前缀，根会话冷恢复直接装入当前检查点，不使用当前最新项目文档重写历史指令。

Studio 的标准工具装配使用 `pl-tool` 提供的稳定工具声明与构造器，并显式传入同一配置快照中的能力开关：处于关闭状态的能力既不创建执行器，也不获取后台辅助进程（worker）资产，且禁止通过可选构造函数旁路重新启用；当配置更新时，由宿主构建下一代工具目录后原子替换。Studio 的远端与本地辅助进程（helper）资产装配由产品资源模块统一提供，本地命令后端持有可执行映像租约，使嵌入式发布包无需依赖系统 `PATH`。产品附件宿主接口归属 `pl-tool`，由 Studio 注入持久化存储与读取实现；已准备的多媒体数据仅在 `pl-model` 与 Studio 的适配边界传递。工具产出的媒体归档与模型投影共用统一的工具层端口，MCP 媒体输出与文件图片读取均复用该端口。当工具内部需要读取对话背景时，只读访问触发本次调用的模型请求快照，而非读取可变会话状态或尚未准入模型的排队消息；独立网络搜索工具由 `pl-tool` 筛选近期用户与助手可见文本，自动排除系统指令、运行时注入事实、工具结果及供应商不透明材料。供应商前缀缓存分组键不包含采样温度（`temperature`）或最大输出词元数等生成参数，而模型标识、账号与部署隔离身份、协议类型、系统指令、工具声明及影响请求编码的选项则继续参与缓存分组。追踪展示记录及其产品事件格式归属 `pl-studio-protocol` 的追踪交换域；`pl-trace` 依赖 `pl-core`，只读消费会话状态副作用与调用记录以生成诊断视图，观察过程绝不触发模型调用或工具执行。

## 16.6 工具执行与授权边界

内核受限任务模块统一拥有等待原语的状态判定与固定截止时间点逻辑，向工具层返回目标任务快照、新消息就绪标记与正常超时标记；工具适配层仅负责参数解码与结果格式化，不得在外部另行包装超时逻辑或自行拼装不同来源的状态。等待权限、当前调用存活状态、目标任务身份及待提交结果均在观察边界严格校验；持久化终态读取仅恢复已提交的历史事实，不复活任何执行器。内核等待原语不解析 `wait`、`sleep` 等具体工具名称或参数，产品层的使用方式与消息交付契约见 [14](./14-runtime-host.md) §14.4–14.5。

通用会话内核独占管理不透明工具注册表，单个模型推理步骤不从调用方直接接收另一份外部工具声明。每次模型请求在准备阶段同时冻结工具声明与对应的执行器租约，模型输出的工具调用必须引用该冻结计划内的工具且调用 ID 唯一；动态替换工具目录时，仍在途的工具调用继续持有原执行器租约。工具输出的消息角色与调用关联 ID 统一由会话所有者赋值。公开的工具注册值不可克隆（non-cloneable），装入会话时直接转移实例所有权，唯有内核内部已冻结的执行租约支持克隆；若多个工具需要共享底层物理服务，应由具体工具在构造时显式捕获服务租约，禁止通过复制工具注册值在多个会话间共享同一个工具实例。不透明工具契约提供显式的异步 `close` 接口：会话工具管理器保留已被替换但仍归属本会话的旧工具实例，在会话关闭时逐一等待其安全收束；已成功关闭的工具实例不重复调用，关闭失败的实例及剩余未关闭实例则保留在管理器中以供重试。

工具主动结束当前轮次（`finish_turn`）使用独立的类型化控制枚举，工具载荷或上下文正文中出现同名字符串不会触发轮次结束控制。工具注册时必须显式声明结束轮次权限，且拥有该权限的工具调用必须独占模型工具批次（`Solo`）；若未获授权的工具返回了结束控制枚举，内核直接将该次调用记录为工具失败，且不结束当前轮次。延迟揭示（deferred）工具目录状态按稳定的工具 ID 与原始声明保存，工具揭示（`reveal`）属于显式的框架控制操作：发现类工具通过在输出中附带类型化的 `revealed_tools` 请求来揭示隐藏工具，且该工具自身必须在注册时显式获得 `discovery` 权限；内核先校验全部被揭示工具 ID 的合法性，再将其与扩展 CAS 及工具结果在同一提交中原子生效，若调用被取消或执行失败则不改变当前揭示状态，动态业务载荷中的同名字段亦不会触发揭示操作。当执行器发生重连但工具声明未变时，保留已揭示状态；当工具被删除或声明发生变更时，自动清除对应的旧揭示状态，且不单纯因为执行器代次递增而重置可见工具前缀。

动态工具目录替换由同一会话所有者在长耗时调用等待期间安全受理：已冻结的在途请求与已启动的执行器租约保持不变，后续新开启的步骤则消费替换后的新目录；若新目录注册失败则保持原目录不变，目录替换亦不会关闭仍被在途调用持有的底层资源。冻结执行器租约不等同于永久执行授权：模型准备结束、正式准入前会复核原工具计划的授权有效性，工具真正启动执行前会再次复核；若权限已被撤销或工具已被删除，则立即阻止尚未启动的外部副作用，仅对已启动的执行保留完成事实；取消或权限撤销后迟到的工具结果不得应用已失效的框架控制权限；单纯的执行器连接重连或新增其他无关工具不会撤销原调用的执行授权。

工具授权策略身份与模型可见工具声明、执行器实例三者解耦：宿主通过类型化注册接口提供不含敏感凭据的策略身份标识，并在安全策略变更时更换该标识；内核仅比对策略身份是否一致，不解析策略细则。策略身份更换会立即阻止旧工具计划准入、阻止旧批次中尚未启动的调用开始执行，并收回对旧后台任务的取消权限，但不会改变模型可见的工具声明或破坏前缀缓存。工具在启动执行前可绑定宿主的执行策略（`ExecutionPolicy`）：内核根据策略返回的类型化成功或失败结果决定是否调用执行器，不解析审批界面的 JSON 载荷；当审批等待结束返回后，内核会再次核验原执行器的权限租约与当前任务存活状态。执行策略检查通过后返回调用级的执行授予（`ExecutionGrant`），其中的具体能力名称由上层宿主定义，内核视为不透明标识；工具实现仅消费可信调用上下文中的授权能力，严禁读取模型生成参数中的任何所谓“已授权”标记；调用级授权仅对当次工具调用有效，既不进入模型工具声明，也不从冷历史中恢复；同时，物理工作区隔离边界（confinement）仍是工具后端不可被调用级授权放宽的硬边界。文件系统后端可根据调用级授权创建受限的临时访问视图，但仍保持原工作区根目录、写入范围与服务租约不变；唯有本地宿主许可（host-permitted）工作区支持消费外部路径授权能力，受限的 Git 工作树、远端 SSH 工作区与容器工作区默认不提供外部路径放宽视图。工具调用的外部路径访问需求由宿主装配的评估器（assessor）从原始调用参数中提取，内核仅消费类型化的访问需求并管理审批生命周期；若未装配评估器，则默认不授予任何额外路径访问能力。产品层的审批 DTO 直接投影内核保存的许可请求、决定状态、时间戳与原始响应载荷；界面提交的审批响应经 Studio 解码后转换为带版本号校验的类型化命令，遇到未知格式的审批载荷时仅投影为只读原始记录，不得渲染为可点击执行的审批控件。

自动安全审查模型（reviewer）是由 Studio 装配的辅助模型调用，使用已冻结的模型绑定与独立的临时模型会话；内核仅负责提交类型化审查请求、向下传播取消信号并等待审批结论；若当前需要自动审查但未配置审查模型，则直接拒绝该次工具调用，绝不回退为自动批准。支持捕获恐慌展开（panic unwind）的模型与工具适配边界会将运行期 `panic` 转换为类型化执行失败并保留诊断信息，防止会话所有者在记录终态前意外终止；若异常发生时无法获取供应商已知词元用量，则保持用量未知；该捕获机制仅保证运行时状态收束，不宣称能回滚已发生的外部副作用。工具执行失败时允许同时返回已观察到的完整业务载荷与上下文投影：内核完整保存实际观察结果与失败事实，但忽略失败结果中携带的扩展状态更新、交互请求或轮次结束控制；错误源链（error source chain）作为诊断文本保存，自动检测循环引用并限制错误链展开深度，超出上限时显式标记截断。

内置的待办事项（`todo`）与会话笔记（`session note`）工具直接从会话扩展快照读取原始状态：`todo` 工具自行校验核对清单（checklist）合法性并同时生成业务载荷、模型上下文投影与扩展 CAS 变更，若清单内容未发生实质变化则不写入新的扩展版本；`note` 工具正文完整保留原始换行符与 Unicode 字符，不自动注入模型每轮上下文，其写入回执使用会话扩展版本水位给出实际候选版本号。`finish_turn` 工具要求提交非空总结消息，不在应用层设置人为字符截断上限，并通过注册授权的类型化控制枚举触发轮次结束。

## 16.7 用量计量与调用回执

`pl-model` 保存完整的归一化响应回执，而非仅提取回复正文与工具调用列表：供应商响应 ID、实际返回的模型标识、词元用量、定价快照、编排指标与分段时间戳同属不可变调用回执；回执同时记录请求模型标识、供应商实例、协议类型及脱敏隔离身份，产品层通过 `pl-model` 提供的解码接口读取这些信息，内核不解析此类协议字段；调用用途（`purpose`）仅用于计费与诊断分类，不改变工具权限或执行调度。Studio 的计费记录装配仅消费回执中已保存的 `context_window` 与实际计费数据（accounting），不查询当前可变模型目录或最新价格表；回执中未知的窗口容量保持为未知。

计费记录通过独立的 `purpose` 字符串标识调用用途，主推理循环、上下文压缩摘要、自动安全审查与自动标题生成在各自调用点显式赋值；历史记录若缺少用途字段则保持缺省未知，既不根据推理 ID（`inference` ID）、工具名称或模型名称反向猜测，也不参与执行流控制。Studio 在维护会话总费用的同时，按 `purpose` 分类汇总费用与未定价标记并通过类型化 DTO 暴露；缺少用途标记的历史费用独立归入“未知用途”分组，不得并入主推理循环分组；相同推理 ID 的重复投递在任何分组中均保持幂等，不重复累加。辅助安全审查调用无论最终得出批准、拒绝还是遭遇模型调用失败，均如实记录已收到的供应商计费数据；当审查调用被取消时，审查器先完成自身请求收束与计费数据受理，随后再向框架返回取消拒绝结果。

`pl-trace` 汇总已验证诊断日志中的真实模型词元用量：已取消、已失败或被准入拒绝的响应所产生的真实消耗同样计入总量，而仍处于 `Running` 状态的在途调用不重复计费；缓存读取与缓存写入词元独立汇总展示，不再重复累加至输入词元总量；缺失字段或发生整数溢出的计数保持为未知，准备阶段的输入词元估算值不参与真实用量汇总。`ModelUsage` 结构体完整保留供应商明确上报的 `total_tokens` 字段，即便输入或输出单侧计数缺失也不丢弃该总计观测事实；消费方构造时需为新增字段显式赋值或使用 `Default`。`ModelError.usage` 采用 `Box<ModelUsage>` 堆分配持有，使错误返回值的栈大小不随累计字段扩展而膨胀，持久化序列化格式则仍保持原有的内联 JSON 对象不变。

## 16.8 内容寻址资源与物理服务

Studio 的会话文件资源库采用完整字节内容的 SHA-256 摘要寻址：写入时先将数据完整流式写入同目录临时文件并执行磁盘同步（fsync），随后以不覆盖既有对象的方式原子发布至目标摘要路径；相同字节内容直接复用已有对象，若发现摘要路径已存在但内容不匹配则必须报错校验，绝不静默覆盖。资源引用自身携带字节长度、SHA-256 摘要与 MIME 媒体类型，读取方仅凭引用即可校验并恢复完整内容，无需按工具类型建立专门的结果存储表。本地命令输出归档仅读取已彻底排空的本地捕获文件；远端 SSH 命令捕获则必须由对应的远端读取适配器处理。远端辅助进程（helper）协议提供有界文件范围读取与显式文件写入模式：归档客户端逐段核对读取偏移量、文件总长度与实际返回字节数，一旦发现意外截断或文件总长度变化即刻拒绝，逐段写入本地暂存文件并校验完整摘要后才正式发布资源；单帧通信长度上限不得演变为完整命令输出的截断上限；若远端归档失败则保留远端源捕获文件，后续重试仅重新拉取输出文件，绝不重新执行外部命令。

文件写入模式在工具调用参数、工作区文件系统后端与远端辅助进程协议之间端到端贯通：`create` 使用排他创建（文件已存在则报错），`append` 使用操作系统原生追加文件句柄，`overwrite` 使用同目录临时文件原子替换；远端文件追加严禁采用“先读回旧文件全文再整体覆盖写入”的模拟方式。工作区文件原子覆盖写入时自动保留已存在目标文件的原有权限位，新建文件则采用标准普通文件权限并遵守进程 `umask`。附件写入器的唯一契约是有序原子批量写入，单张图片上传同样经过该批量接口，不提供“外部循环逐张写入冒充批量提交”的兼容路径。

MCP 动态工具固定绑定创建时的服务租约与工具声明，执行器解析自身调用参数后直接调用同一服务租约；MCP 工具返回结果中包含的图片、音频与内嵌二进制块按精确字节归档为稳定的会话资源引用，业务结果载荷则保留其余结构化字段与元数据。若媒体归档失败，统一使用显式的 `mcp-unarchived` 结果格式完整保留收到的原始协议材料，既不伪造资源引用，也不宣称已生成正常的模型媒体投影；此时模型上下文仅收到归档失败说明，而历史详情仍可查看原始协议材料。MCP 资源目录、资源模板与资源读取门面（façade）同服务工具共享同一份已冻结服务租约：资源查询仅路由至该租约中声明支持 `resources` 能力的服务，未指定具体服务名时按稳定的服务顺序聚合查询；资源读取结果完整保留返回信封与元数据，内嵌二进制数据同样转换为持久化资源引用，读取或归档失败时明确报错，不返回默认空结果。

宿主辅助命令（如 Git 状态探测等）发生超时时同样必须经过物理进程收束：本地环境使用统一的进程组或 Windows Job Object 包装，同时等待子进程退出与标准输出/错误两路管道排空；远端环境保留原有的退出接收器与输出读取任务，发送终止信号后继续等待收束确认。发送终止请求失败不得伪装成命令已退出，进程退出异常或管道排空失败均保留明确的诊断信息。

用户定向中断（`interrupt`）与新输入打断统一将轮次终态保存为 `TurnState::Interrupted`；会话关闭或底层取消令牌触发则保存为 `Cancelled`。内部取消错误仍用于收束在途异步执行，但不得因此抹去历史数据库中记录的真实停止原因。Studio 将 `Interrupted` 映射为强类型的取消展示原因 `interrupted`；而无结束耗时记录的冷恢复中断则投影为 `recovery`，防止将运行期间的用户定向打断误标为崩溃恢复。FRB 桥接层与 Dart 客户端完整保留这一强类型原因枚举。

执行中的工具或其绑定的宿主安全审批策略，可通过受限的 `TaskAccess` 接口提交不透明的观察回执（如自动审查产生的模型用量回执）。内核严格核验由会话所有者授予的精确调用能力当前仍处于运行状态；调用被取消或执行许可被撤销不会抹去已实际发生的调用计量，而提交观察回执本身也不会反向授予工具执行权限。此类观察回执进入可靠的 `ThreadEffectBatch`，会话检查点按生产者格式仅保留最新一份回执快照，且不注入模型上下文。宿主按状态副作用水位幂等折叠回执中的计量数据，禁止让自动安全审查产生的费用仅存在于可丢弃的调试调用日志中。

## 16.9 轮次准入门控（`TurnAdmissionGate`）

会话支持安装一个产品无关的轮次准入门控（`TurnAdmissionGate`），将“下一轮次（`Turn`）当前是否允许开始执行”从输入受理、队列驱动暂停与存储背压准入中解耦出来：`pl-core` 仅负责在轮次启动边界询问该门控，不解释宿主持有门控锁定的业务原因，也不为特定宿主动作增加条件分支。未安装门控的会话保持原有准入行为不变，既有消费方无需改动。

门控关闭通过持有原因句柄表达：每次调用 `close()` 返回一个 RAII 保持句柄（`TurnAdmissionHold`），析构（`drop`）该句柄即自动释放对应的关闭原因。多个独立原因可同时关闭同一个门控，释放其中任一句柄不会重新打开仍被其他原因持有的门控，从而在根源上消除“旧释放操作意外重开新锁定”的竞态。轮次准入成功时返回一个准入许可（`TurnAdmissionPermit`）；门控同时向外暴露 `is_open`、`is_clear`、当前存活的 `hold` 数量以及当前已准入的在途 `Turn` 数量。当宿主持有关闭句柄时，可通过检查 `admitted_turns() == 0` 确认旧轮次已彻底排空且后续轮次必定处于等待状态；`is_clear` 为真表示门控当前处于开放状态且不存在任何正在执行的已准入轮次，只要仍有任一关闭句柄存活，`is_clear` 恒为假。

轮次准入检查点全局唯一，且严格位于轮次真正开始之前：会话所有者在创建任何 `Turn` 记录、消费任何待处理输入之前先行等待门控开放；`submit_input_and_run`、`run_next_input`、持续驱动器（driver）、消息收件箱唤醒及内部续接（`continuation`）全部汇入同一条所有者准入路径，既不存在第二个旁路调度器，也不是“每个模型推理步骤检查一次”。已获准入的轮次在整轮执行期间持有 `TurnAdmissionPermit` 直至轮次终态收束，期间新产生的关闭句柄仅拦截下一轮次。门控等待期间，会话所有者继续正常轮询服务内部邮箱，会话关闭、取消中断、显式刷盘与存储故障恢复均照常收束；由于等待发生在输入消费与轮次创建之前，被门控拦截的待处理输入在队列中保持原有未消费状态，会话快照则通过 `InputExecution::Blocked` 如实报告该阻塞状态。

轮次准入门控在会话所有者装配阶段安装（`ThreadHandle::resume_with_turn_admission_gate`），严格早于冷恢复后的任何执行续接，确保恢复流程不可能绕过尚未安装的门控。门控属于纯运行时协调原语而非持久化逻辑状态，既不写入检查点，也不参与会话身份计算；恢复后的会话直接使用装配时注入的门控实例。未安装门控时，轮次准入不引入任何额外等待开销。

## 16.10 冻结准备与会话隔离

模型上下文准备开始前，会话所有者先行冻结本步待消费输入、消息消费水位、工具目录租约、当前上下文版本号与业务扩展版本号。准备请求同时向模型层提供包含本步新输入的完整上下文预览以及已提交的权威上下文基线；上下文压缩过程不得提前将待处理输入标记为已消费。准备候选结果中包含的当前运行时事实更新、上下文压缩替换与成功回执，必须在同一候选状态中联合校验并原子提交。若准备过程被取消、调用失败或发生状态版本冲突，均不推进业务状态；准备阶段已实际产生的模型费用（如压缩尝试费用）作为独立的失败计量保留，计量提交仅依据当前账本版本，不会因执行候选状态过期而丢失。遇到版本冲突时最多自动重新冻结准备一次，且不会重复消费用户输入。

各根会话、子会话与同级兄弟会话各自独立拥有上下文、输入队列、业务扩展、当前运行时事实、用量计量及模型续接状态。共享底层物理服务租约或共享不可变配置目录，绝不意味着共享会话逻辑状态。子会话仅接收父智能体在派发任务时显式传入的自包含任务材料，其执行进展与终态报告通过显式消息投递回传父会话。上下文压缩、进程重启与模型路由切换均不改变会话的父子归属关系。

上下文准备器可返回本次模型请求需要临时排除的工具 ID 集合；该过滤策略仅在已冻结的注册工具集合内部收窄可见范围，既不创建新工具，也不授予额外执行权限。准备候选状态提交后，同一次模型请求的工具声明、独占调用（`Solo`）约束与模型输出准入校验统一使用收窄后的工具计划；若准备失败或被取消，则不应用该候选计划。显式重试直接沿用原请求已收窄的可见工具集合，同时复核仍可见工具的原有执行授权与声明未发生变更。

本地上下文准备阶段的容量超限失败与服务端返回的超窗错误（`ContextLimit`）共享当前轮次唯一的一次宿主强制压缩恢复预算。唯有通过扩展 CAS 成功提交原因为 `Compaction` 的上下文替换（replacement）才算作强制恢复成功，普通的运行时事实刷新、上下文重建（`Rebuild`）或单纯的版本号推进均不视作已完成压缩恢复。用户在界面触发的手动上下文压缩仅在会话所有者空闲时执行相同的准备与原子提交流程，既不伪造用户输入，也不重放任何工具调用。
