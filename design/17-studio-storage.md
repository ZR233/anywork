# 17 - Studio 存储、迁移与诊断

本文是 Studio 文件系统布局、目录加载、会话按需激活、历史与调用数据库、版本迁移及恢复诊断的唯一权威源；会话检查点（checkpoint）与历史写入器契约见 [15](./15-session-storage.md)，安全边界见 [04](./04-security.md)。

本版本实施大版本会话存储断代：旧版本的会话目录、目录摘要、产品数据库、调用统计与迁移状态原样保留在旧路径，**不导入、不激活、不自动归档，也不清空删除**。新版运行时在独立的 `v2/` 数据根目录下创建并管理新会话与目录。`config.toml` 与用户自定义智能体预设（Agent Profile）等非会话配置沿用原路径，账号配置结构升级继续由配置模块负责并保护系统凭据引用；旧版会话数据转换不属于本版本的启动路径或验收目标。

## 17.1 数据布局

Studio 数据根目录（默认 `~/.anywork/`）的目录结构如下：

```text
~/.anywork/
├── config.toml                     # 账号、模型路由、指令与技能/MCP 配置
├── agents/<agent-id>.toml          # 用户自定义智能体预设（Agent Profile）
├── modes/<mode-id>.json            # 用户自定义工作模式（Mode）定义
├── v2/
│   ├── settings.toml               # 本版本界面与产品设置
│   ├── workspaces.toml             # 本版本项目与工作区（Project/Workspace）定义
│   ├── catalog.toml                # 本版本会话目录轻量摘要
│   ├── model-catalogs/<account-key>/<query-key>/model.json # 各账号最后一次成功的在线模型声明缓存
│   ├── bots/<bot-id>/              # 机器人管理根目录；使用稳定 ID，不用平台身份作路径
│   │   ├── config.toml             # 版本化非敏感配置与独立配置版本号（config revision）
│   │   ├── state.sqlite            # 版本化会话映射、可靠受理身份、配对及发送操作记录
│   │   └── workspace/              # 受管本地执行根目录；内部复用 .anywork/sessions/<thread-key>/
│   ├── projects/<project-key>/     # project-key = 稳定 Project ID 的 SHA-256 十六进制摘要
│   │   ├── project.toml            # 版本化项目身份与归属清单
│   │   └── sessions/<thread-key>/  # thread-key = 稳定 Thread ID 的 SHA-256 十六进制摘要
│   │       ├── session.toml        # 会话身份、父子归属与固定工作区绑定清单
│   │       ├── history.sqlite      # 对话历史、当前上下文与检查点（同事务持久化）
│   │       ├── attachments.toml    # 会话附件清单，持久化路径相对于本会话目录
│   │       ├── blobs/              # 可靠附件二进制正文（旧检查点子目录迁移验证后回收）
│   │       ├── thread-resources/   # 内容寻址的可靠工具输出与归档媒体
│   │       └── scratch/            # 宿主自有文件传输与处理暂存区，不向模型暴露
│   ├── calls/
│   │   ├── calls.sqlite            # 有界调用调试索引与轻量性能统计投影
│   │   └── logs/                   # 版本化滚动 JSONL 调试日志
│   └── migrations/                 # 本版本内部迁移状态记录
├── migrations/                     # 旧版本迁移状态，原位保留但不读取
│   ├── session-migration.json
│   ├── layout-publication.json
│   └── session-archive/
├── startup-recovery.toml           # 可接续的全局启动备份恢复记录
├── startup-backups/                # 不可覆盖的全局启动备份目录
└── studio/                         # 产品数据库与进程级资源
    ├── v2/
    │   ├── studio.sqlite           # 本版本产品数据库（目录镜像、本地模型评价等）
    │   └── attachment-drafts/      # 尚未绑定会话的附件草稿暂存区
    ├── studio.sqlite               # 旧版本产品数据库，原位保留但不读取
    ├── runtime.lock                # 跨进程独占文件锁
    ├── acp-servers/                # 受管 ACP 服务安装根目录
    └── skills/.system/             # 构建期预置的系统技能（System Skill）
```

权威会话、调用诊断与本版本迁移记录统一位于 `~/.anywork/v2/`；产品数据库位于 `~/.anywork/studio/v2/`，进程级独占锁与预置系统技能仍位于 `studio/`。`<project-key>` 与 `<thread-key>` 分别为项目稳定 ID 与会话稳定 ID 的 SHA-256 十六进制摘要，不使用显示名称、工作区路径或原始明文 ID。项目重命名无需移动磁盘目录；本地项目、SSH 远端项目以及指向同一路径但使用不同 SSH 别名的项目，均按各自独立的稳定 `Project` ID 隔离存储。根会话、子会话与自动安全审查会话各自拥有独立的会话目录。`<account-key>` 与 `<query-key>` 为账号身份与查询参数的安全摘要，不含可逆凭据信息；当账号 ID 原值不变时直接沿用既有目录摘要，不因术语升级另起缓存命名空间。旧版共享库 `studio/sessions.sqlite`、旧版 `studio/calls.sqlite`、旧版全局 `studio/attachments/` 及旧迁移暂存目录原样保留在旧数据根，本版本不读取也不切换它们。

会话数据库始终保存在宿主应用数据根目录下，绝不写入用户的本地或 SSH 项目工作区。进程启动前必须先取得 `~/.anywork/studio/runtime.lock` 的操作系统级跨进程文件独占锁；锁文件内记录的进程 PID、宿主类型与启动时间戳仅用于诊断展示，锁的实际所有权完全由操作系统文件锁裁决。

产品数据库、会话历史数据库与调用诊断数据库共用原生文件路径连接边界：数据库文件路径通过底层驱动的类型化文件参数直接传入，不拼接为 URI 连接字符串，也不剥离 Windows 扩展长度路径前缀（`\\?\`）；目录名中包含的非 ASCII 字符、百分号与 URI 保留字符均按真实文件系统路径处理。打开数据库前仅解析已存在的父目录，写入方负责创建所需目录，只读查询方则严格保持只读打开模式。只读、读写既有文件与读写可创建三种打开模式必须显式区分，路径规范化解析不改变连接池、事务或保存语义。

桌面宿主在创建 Flutter 引擎、原生窗口及任何业务资源之前先行取得 `runtime.lock` 文件锁，并将锁租约移交运行时持有。文件锁的宿主所有权一直持续到桌面进程彻底退出：启动失败、初始化重试或运行时 `Clean` 关闭仅释放各自的内部引用，不会在进程存活期间提前释放数据目录锁。独立服务端（Server）与测试宿主则在其运行时彻底收束完成后释放文件锁。锁文件在磁盘上存在并不代表锁被占用；进程崩溃后由操作系统内核自动释放文件锁，严禁通过删除锁文件的方式抢占实例。

桌面单实例路由键（instance key）直接取自 Studio 数据根目录的物理目录身份（Windows 卷序列号与文件 ID、Linux 设备号与 inode），不包含可执行文件安装路径、版本号或构建模式；指向同一物理数据目录的符号链接、Windows 目录联接点（junction）与路径别名均归属同一实例。该实例键仅用于原生窗口唤醒与命令行参数转发，数据目录的独占访问权仍完全由上述操作系统文件锁裁决。

`catalog.toml` 仅保存轻量会话目录摘要：会话 ID、父会话 ID、所属项目与工作区身份、标题（`title`）、工作模式（`mode`）、角色标识、工作区模式与地址、子任务分发模式与偏好、可验证的冻结子会话模型标识摘要、显式关闭意图投影、创建时间、更新时间、归档状态及目录状态（`status`）。它不保存当前模型上下文、完整轮次记录、历史对话正文、工具调用结果或实时执行状态，也不设独立的实时活动摘要字段：侧栏活动指示器由内存热状态集合实时驱动，持久化的 `status` 仅反映最后一次已提交的目录状态，不可用于判定工具或轮次当前是否仍在运行。

会话目录另行持久化可空的 `last_user_message_at`（通信协议与 TOML 字段名为 `lastUserMessageAt`，Unix 秒时间戳），记录服务端最近一次成功受理用户消息的时间。已成功受理的排队输入计入该时间，被拒绝的输入不计入；用户主动回答提问卡片或确认/修订计划所产生的已受理续接输入同样计入，不因其在模型上下文中呈现为隐藏续接而排除。权限审批决议、程序自动生成的续接输入以及无新输入的重复决议不计为用户新消息；子智能体通知、系统注入事实、工具结果交付与冷恢复重放均不推进该时间戳。`updated_at` 仍表示普通元数据或状态更新时间，不用于会话列表排序。会话目录冷分页、搜索与 GUI 侧栏列表统一按 `(last_user_message_at.unwrap_or(created_at), id)` 降序排列：同一秒内按会话 ID 字典序稳定破平，尚无用户消息的新会话则回退按创建时间排序。目录分页游标采用独立的新版本号，不将旧版基于 `updated_at` 的游标解释为新排序键。普通元数据更新或运行状态写回必须保留最新的 `last_user_message_at`，迟到的状态快照不得使该字段回退；该时间戳通过既有的目录事实发布与持久化链路传播，不在 GUI 本地另立事实源。

当前 `v2` 目录文件与 SQLite 目录镜像的结构升级完整保留全部既有数据。旧版 `v2` 目录记录若缺少 `last_user_message_at` 字段，在迁移时保持为空值（`None`），不拿普通更新时间 `updated_at` 伪造用户最后发送时间；此类旧会话默认按 `created_at` 参与排序，直至下一次成功受理用户消息时更新该字段。排序时间戳仅由输入受理链路维护并经既有目录保存链路落盘；保存失败通过既有错误与重试机制暴露，正常重启直接读取目录元信息。严禁为列表排序而扫描会话历史库，也不在打开会话时查询历史记录来推导或回填该时间戳，不为此新增历史表索引或批量激活历史会话。

`workspaces.toml` 保存项目与工作区定义及稳定引用；物理 Git 工作树所有权则通过版本化的租约（lease）记录维护，完整保存 `prepared | active | preserved | cleanupRequested | cleaned` 状态、持有者会话 ID、仓库路径、工作树路径、基线提交（base）与当前修订（revision）。当前分支属于可变观察，不是租约身份。目录展示信息与物理工作树所有权分属不同职责，禁止相互推导。

`studio.sqlite` 中的目录镜像表可能短暂落后于已持久化的权威 `catalog.toml` 与 `workspaces.toml`。当写入会话目录镜像行时，若发现其所属的父项目（`Project`）镜像行尚不存在，必须在同一 SQLite 事务中先从内存已加载的权威 `workspaces.toml` 事实补齐父项目行，再写入会话行，不得要求用户先在 GUI 中手动打开该项目。若权威 `workspaces.toml` 中确实不存在对应项目，则明确报错拒绝写入，既不猜测项目归属，也不通过关闭 SQLite 外键约束强行写入。已存在的父项目镜像行严格遵循先进先出（FIFO）的目录变更顺序更新，不被冷目录摘要反向覆盖。

机器人独立管理根目录 `v2/bots/` 纳入同一 `v2` 整体备份范围：每个机器人的 `config.toml` 保存版本化的期望配置及独立的 `configRevision`，`state.sqlite` 保存版本化的平台会话映射、可靠受理身份与外发消息操作记录。配置文件中的凭据版本引用与提交恢复身份不包含敏感密钥明文，实际密钥材料仅保存在操作系统凭据库或进程级内存租约中。配置引用发布、提交结果待确认与未引用密钥材料回收分别独立恢复，不得假设原子文件写入报错就代表目标配置文件未被替换；在未决配置提交收敛完成前，系统完整保留相关密钥版本并封闭该机器人的消息准入（见 [27.2](./27-bots.md#272-管理配置与凭据)）。备份普通应用数据不会导出系统凭据库或内存租约；恢复历史配置文件亦不会隐式回退或自动切换至其他密钥版本，当所引用的密钥材料不可用时明确提示用户重新配置凭据。外部聊天平台的消息 ID 不替代 Studio 会话检查点，机器人关联的 `Thread` 仍按标准路径保存在 `projects/<project-key>/sessions/<thread-key>/` 下。平台 `App Secret`、租户令牌（tenant token）与长连接票据绝不写入上述磁盘文件；单个机器人数据损坏仅保留现场并局部隔离该机器人，不触发全局启动备份重置（生命周期与未知发送结果契约见 [27](./27-bots.md)）。

机器人的受管工作区根目录固定为其管理目录下的 `workspace/`。每个机器人聊天会话独立复用标准的会话执行侧文件布局：其中 `uploads/` 保存从平台下载或物化的输入文件，`scratch/`、`artifacts/` 与 `commands/` 沿用标准职责，`.venv/` 由 `uv` 按需创建，且 `UV_PROJECT_ENVIRONMENT` 环境变量仅注入该会话派生的命令子进程。可靠附件清单与二进制正文仍归属标准会话存储目录，受管执行目录不充当附件或对话历史的第二个事实源。旧版机器人的历史存储身份、凭据引用、关联会话与收发账本保持原样；执行侧文件迁移仅复制明确归属于该会话的旧目录内容，保留原业务项目与文件不变。迁移按单文件原子发布并持久化记录完成状态，支持中断后接续，迁移完成后不再重复恢复用户已删除的工作文件；Python 虚拟环境不支持跨路径直接搬迁，保留原环境目录并在新位置按需重建。

项目清单（`project.toml`）与会话清单（`session.toml`）仅记录结构版本、稳定身份与固定父子/项目归属，用于目录自描述与挂载绑定校验，不构成第二套可编辑配置文件。项目显示名称、会话标题、归档标记与列表排序时间等可变摘要仍归属全局轻量目录索引；当前模型路由、工作模式、系统指令快照、计划文档与会话笔记仍归属会话检查点与扩展。归属清单不复制账号密钥或对话历史正文。新建项目或会话资源时，必须在对外发布目录事实之前先落盘归属清单，若清单校验失败则禁止发布错误的目录归属；冷历史读取不会为了补写清单而创建会话历史库。旧版 `v2` 遗留的 `state.toml` 与 `state.prev.toml` 可随原会话目录暂留作为按需迁移源，仅在既有的检查点转换边界读取并在验证落盘后回收，不再作为新会话的保存格式。

### 执行侧会话临时文件

供模型在任务执行期间读写的临时文件位于实际项目工作区（workspace）内部，与上述宿主应用数据根目录严格分离：

```text
<workspace>/.anywork/sessions/<thread-key>/
├── scratch/                        # 临时脚本、中间数据与一次性探针
├── artifacts/                      # 尚未交付至用户指定项目位置的待交付产物
└── commands/<call-key>/output.log  # 命令执行的原始捕获输出；call-key 为调用身份的安全摘要
```

本地工作区、Git 工作树与远端 SSH 工作区统一使用相同的 `<thread-key>` 身份映射与相对目录布局；即便是共享同一代码检出目录（checkout）的多个会话，也各自拥有独立的 `<thread-key>` 临时目录。SSH 远端项目的执行侧路径位于远端服务器的工作区内，严禁使用本地宿主主目录路径替代。会话宿主数据目录下的 `scratch/` 仅用于宿主内部文件传输暂存，而工作区内的执行侧 `scratch/` 则供模型存放任务中间文件，两者均不承担可靠对话历史的持久化责任。命令输出与工具媒体在完成可靠内容寻址归档后才对外发布稳定资源引用，此后工作区内的执行侧临时文件即便被清理也不会破坏历史记录读取。

执行侧临时目录不是正式代码或项目文档的最终交付位置：正式源码与项目文档仍须直接写入用户指定的项目目标路径；生成的非项目交付物若保存在 `artifacts/` 下，则必须在回复中向用户报告真实绝对路径。模型默认不在项目仓库根目录、系统 `/tmp` 或其他会话的临时目录中散落写入中间文件。运行时通过 `studio.session-files` 向模型提供当前会话准确的执行侧路径事实，系统提示词与技能说明统一消费该运行时事实，不从历史对话或进程当前工作目录（`cwd`）猜测路径。

工作区内的 `.anywork/sessions/` 与工作树池目录在首次准备时，各自以排他不覆盖方式在池目录内部创建忽略全部池内容的 `.gitignore` 文件。同池并发首次创建按“最终存在安全的普通文件”这一后置条件幂等收敛，不依赖操作系统错误文本匹配；但若目标路径已存在目录、符号链接或无法确认类型的文件系统项，则不得视作准备完成。文件写入工具原有的 `Create` 排他创建报错语义不因此改变。若用户已预先放置自定义 `.gitignore` 则原样保留，且绝不修改用户仓库根目录的 `.gitignore` 或全局 Git 配置，从而确保项目级技能（`.agents/skills/`）与 `AGENTS.md` 等受版本控制的协作文件不会被意外忽略。运行时不主动扫描、搬迁或清理项目内历史遗留的 `target/pure/`、未知用户文件及已隔离的旧版本数据根目录。会话关闭或项目归档仅回收已明确登记所有权（ownership）的受管资源，不按固定存活时间（TTL）后台删除活跃会话的 `scratch/`、可靠历史或已归档附件。

## 17.2 启动与按需激活

历史数据库版本升级会自动修正旧版投影提前写入的用户输入轮次绑定：唯有当某轮次的 `input_id` 明确指向该输入条目，且同一事务维护的终态输入身份索引中尚无该输入身份时，才可证明该输入实际上仍未被模型消费。迁移事务将清除此类条目的展示层轮次绑定并递增其内容版本，同时完整保留输入正文、附件引用、排序号（`ordinal`）、创建时间、执行记录与保存水位；已消费或无法证明未消费的输入条目保持原样。该修正迁移在会话激活投影读取初始种子之前由唯一的历史写入器在事务内完成，普通的冷历史分页查询仍保持纯只读。

应用统一启动协调器按以下有向依赖图推进初始化：获取跨进程文件锁 → 接续未完成的启动备份恢复 → 准备并校验全局配置文件与独立存储库 → 装配核心服务 → 加载本地模型目录缓存、工作区/会话目录摘要与物理资源归属清单 → 启动后台维护任务 → 对外发布运行时就绪状态并渲染 GUI 首屏。彼此独立的准备步骤并发执行，存在依赖关系的步骤在汇合点后依次推进；在所有前置步骤全部成功之前，既不对外发布运行时实例，也不启动任何会话持久化写入任务。因此，在首屏就绪时刻，已加载的会话内存状态、已打开的会话历史数据库与已读取的历史条目数量均为零。各账号模型目录的本地默认定义与上次成功缓存在校验配置引用之前先行加载就绪；启动在线探测作为独立后台任务，每账号初始化时提交一次，各实例并发且不阻塞首屏。运行期不设置周期轮询，显式账号级同步复用同一所有者、缓存与关闭责任（见 [20.5](./20-config.md#205-账号与模型目录)）。读取本地缓存失败仅生成对应账号局部诊断（见 §17.3）。

启动准备阶段优先执行已知的结构版本迁移、索引重建与可恢复的日志尾记录修复。唯有遇到无法修复的数据损坏、未知的未来结构版本或无法解析的必需引用时，才返回类型化的持久化数据错误；文件权限不足、磁盘空间耗尽、文件被占用、系统凭据服务异常或内部逻辑错误均属于环境或运行故障，绝不触发全局数据备份重置。若启动过程失败或被取消，协调器必须等待全部在途并发步骤收束并关闭已打开的文件与数据库连接；若资源回收失败，则严禁进入备份重置流程。

当确认为无法恢复的持久化数据损坏时，启动协调器在持有独占文件锁的前提下，将 `config.toml`、`agents/`、`v2/` 与 `studio/v2/` 整体移动备份至独立且不可覆盖的 `startup-backups/` 目录，完整保留 SQLite 主库、`-wal`/`-shm` 日志、调用诊断日志与全部会话附件。备份过程通过持久化的 `startup-recovery.toml` 状态机逐项记录“待移动、已移动、备份完成、初始化完成”四个阶段，即使中途崩溃重启也能接续同一次恢复流程。唯有在全部受损数据完整迁入备份目录后，系统才使用默认配置重新执行完整初始化；每次进程启动最多执行一次自动备份恢复，若重建后再次失败则直接向用户报告错误。若备份移动过程本身失败，则完整保留原路径现场与已归档部分，既不发布半初始化的混合状态，也不覆盖既有备份。操作系统凭据库、已隔离的旧版本数据目录、用户全局 SSH 配置以及实际的磁盘项目目录与 Git 工作树在全局恢复期间均保持原样不动；恢复完成后生成的摘要向界面提供备份目录真实路径与脱敏原因说明。首屏发布后的按需单会话读取故障或运行期存储错误仅在对应会话内局部报错隔离，绝不触发全局数据备份重置。

应用启动阶段不遍历磁盘上的会话目录，也不在首屏渲染后于后台批量激活历史会话。全局启动恢复仅处理本版本数据根目录级的全局资源与孤立的物理工作树租约。当 GUI 首屏就绪后，若恢复的界面状态存在当前选中的会话，则由 GUI 对该会话发起一次标准的打开命令；若无选中会话则不打开任何会话。其余历史会话的内部状态恢复与按需迁移一律推迟至用户显式打开、发起执行或人工处置该会话时进行。

显式打开单个会话（`Thread`）按以下步骤有序执行：

1. 校验 `catalog.toml` 中的会话身份与父子祖先归属关系；
2. 合并针对同一会话的并发打开请求；
3. 先由该会话唯一的历史写入器通过同一个 SeaORM Migrator 完成既有 `v2` SQLite 表结构与检查点迁移。序列按生命周期分阶段推进：先准备 SQLite，再导入旧版 `v2` TOML 检查点，随后完成模型接入表示迁移；恢复执行身份时携带已核实的身份与 Mode 定义，推进同一序列中的指令与 Mode 迁移。各数据库内转换及其 `seaql_migrations` 记录由官方框架在同一事务中提交，不再保留框架外的检查点升级事务。随后在短只读事务中读取并校验最新检查点与当前模型上下文；
4. 在内存中纯恢复会话所有者状态，不触发任何模型调用或工具执行；
5. 建立会话状态增量订阅；
6. `Session` 尾部订阅在同一同步边界获取当前内存首帧（最近最多 32 条记录）；共享尾部缓存按需通过游标查询从 `history.sqlite` 补齐最多 100 条历史记录，并将内存中的活动条目与待保存条目按同一稳定身份直接归并，无需阻塞等待历史写入器刷盘。

当用户显式继续父会话执行时，系统会先行核对各子会话的终态通知。对于当前未驻留内存的子会话，同样先由该子会话唯一的历史写入器完成既有 `v2` 结构升级与检查点迁移，再只读提取其最新检查点与终态历史事实；该核对过程不会激活子会话所有者，也不会重放模型或工具。

单纯翻阅历史分页不会激活会话所有者。用户离开聊天页面仅释放界面订阅租约与滑出视图的展示缓存，不会自动停止仍在后台执行的会话。当会话所有者处于空闲状态、无活跃订阅、无待保存数据且未持有必须保活的物理资源时，在完成最终检查点落盘后即可安全释放内存所有者。

## 17.3 配置文件、目录缓存与受管资产

`config.toml` 保存账号、模型路由、系统指令、技能与 MCP 服务等全局配置；`settings.toml` 保存界面偏好与产品级设置；`workspaces.toml` 保存项目与工作区定义；`catalog.toml` 保存会话目录轻量摘要。所有配置文件均采用版本化结构（schema）、带 `revision` 的比较并交换（CAS）并发控制以及统一的同目录临时文件原子替换写入，正常读写路径不兼容双读旧格式。应用更新包的下载进度属于瞬态运行状态，不写入 `settings.toml`（更新下载恢复与安装资格契约见 [23](./23-release-update.md)）。

ACP 接入的期望配置保存在 `config.toml` 中，仅持久化稳定账号 ID、供应商类型（`provider`）与显示名称；配置结构从版本 24 升级至 25 时自动保留账号身份并退役旧版自定义 `program`/`args` 字段，同时保留磁盘上已有的安装文件与系统凭据不被删除。固定发行版的启动命令由内置产品清单与受管安装回执共同确定，不回写至用户账号配置。ACP 认证进展与成功观察属于进程运行态，应用重启后重置为“未检查”状态，不从历史成功缓存推定当前凭据仍然有效。认证连接探测使用产品数据根下按稳定接入 ID 隔离的空工作目录，既不将用户的真实项目目录作为探测进程的工作目录（`cwd`），也不发送提示词或开放工具权限。探测目录与子进程由认证所有者独占持有；探测结束后立即关闭子进程并清理探测资源，不删除官方 CLI 工具自身的凭据文件或供应商本地历史（身份、隐私与生命周期契约见 [28](./28-acp.md)）。

受管 ACP 服务端程序的安装根目录固定为 `<Studio home>/studio/acp-servers/`，由产品路径入口统一解析，与会话 `v2/` 数据根、认证空探测目录、应用更新安装器缓存及会话 `scratch/` 目录严格隔离。资产身份由供应商标识、宿主平台目标三元组（target）及产品内置固定的分发描述符摘要共同确定；进程间文件锁、可续传下载文件、解压暂存目录（staging）与最终不可变发布目录彼此分离。同一资产的跨进程文件锁完整覆盖下载、哈希校验、原子发布与暂存目录清理全过程，且释放锁时不得删除锁文件，防止并发进程在原路径创建出第二个锁文件而破坏互斥。

ACP 安装回执拥有独立的格式版本号，完整记录分发描述符身份、版本号与目标平台、下载来源、可选发行版摘要、本地计算摘要、可执行入口相对路径及完整文件成员清单，不包含任何敏感凭据。唯有当全部文件成员及安装回执均通过目标操作系统的磁盘同步屏障后，方可于同一文件系统内原子移动发布安装目录；后续复用已有安装时必须同时核验安装回执与实际文件成员完整性，不得仅凭目录存在即视为有效。若目录原子发布成功但随后的父目录同步报错，必须如实保留“发布已生效或待确认”的状态事实，不得误报为已安全回滚；磁盘上已有的旧版安装目录与未知目录均不自动覆盖或清理。可续传的部分下载文件归下载模块管理，在下载失败或取消后允许保留以供续传；未完成校验的解压暂存目录绝不作为可用程序对外发布。唯有在持有对应资产锁且确认无在途使用时，方可清理本次操作自身创建的暂存目录。删除 ACP 账号不会卸载共享的受管安装目录或清除官方 CLI 凭据；应用重启不会自动恢复未完成的下载，也不会根据磁盘上存在旧安装目录推定认证已通过——唯有用户发起显式准备命令时才执行下载、续传或发布，显式认证检查则仅只读验证已就绪的固定安装，不隐式触发下载、修复或执行历史遗留的自定义程序路径。

安装身份的通信协议标签不直接拼作文件系统路径组件：下载文件名与安装子目录名统一使用跨平台安全的描述符摘要键，完整可读身份则保存在安装回执内部。在 Unix 平台上，持久化确认包含文件数据同步与父目录同步；在 Windows 平台上，则采用文件数据刷盘（`FlushFileBuffers`）结合同卷写透移动（write-through move）的原生 API 保证，不宣称具备与 Unix 父目录 `fsync` 完全等同的语义。Windows 受管安装对象沿用父目录的操作系统继承访问控制列表（ACL），并按 [28](./28-acp.md) 的私有权限策略核验文件实际所有者与自主访问控制列表（DACL）；若权限核验不通过或无法确认，则完整保留现场并拒绝执行该程序，不自动改写既有磁盘对象的安全描述符。本机可信目录与并发访问边界以 [28](./28-acp.md) 为准。

用户自定义智能体预设（Agent Profile）继续采用“每个稳定 ID 对应 `agents/<agent-id>.toml` 单个文件”的存储方式；内置系统预设（System Profile）仅驻留内存，不写入用户磁盘目录。账号密钥（secret）统一保存在操作系统原生凭据库中；当配置迁移需要变更账号 ID 时，必须先将密钥写入新目标凭据项并完成回读校验，随后才切换配置文件中的凭据引用。

全局目录文件变更与单会话检查点分属不同存储载体，不构造伪造的跨文件分布式事务。会话创建、项目归档等跨越多个资源的业务命令采用显式可恢复的多步操作记录：唯有当目标资源文件全部校验落盘后，才更新并发布新的目录版本号（`catalog` revision）；若中间步骤失败，则完整保留原资源与可重试状态。

### 账号用量观察缓存

账号用量由原用量所有者在产品设置库的 `observed:accountUsage:v2` 键下保存，SQLite 表结构与键名不变；该值具有独立格式版本。格式 `3` 保存当前查询阶段、最近成功值及私有查询身份绑定，正常读取只消费当前格式。同一身份重启可恢复最近成功值；崩溃遗留的查询中状态恢复为可重试的取消失败，不宣称旧网络任务仍在执行。查询身份摘要不进入公开 DTO、日志或 HTTP，配置与凭据变化后不得将旧身份成功值绑定到新查询。

旧格式仅在加载迁移边界解码，完整原始字符串保存在新版值的 `legacyUnbound` 中并原子落盘，不丢失金额精度、多币种、时间或其他旧记录。旧值没有足以证明逐账号凭据身份的信息，因此保留为未绑定历史观察，不冒充当前查询的 last-good；当前可见账号仍按新查询身份补查。未知未来格式显式返回迁移失败，保留原值并停止启动，不作为损坏数据触发备份重置。此处是领域序列化值升级，不改变 SQLite schema 或绕过数据库结构迁移；表结构升级仍遵循 §17.11。

### 在线模型目录成功缓存

在线模型目录属于可重建的账号运行期观察结果，而非用户的期望配置（desired config）或会话历史数据。系统按每个账号实例与查询身份独立保存版本化的 `model.json` 缓存文件，记录查询身份、最近成功时间戳、最近检查时间戳（均为 Unix 秒）、可选的 HTTP `ETag` 以及归一化后的模型声明列表；缓存文件绝不保存明文认证密钥。模型价格字段仅保存该供应商适配器明确声明并已完成归一化的词元单价，未声明或格式不支持的价格保持为 `Unknown`（计价来源与同账号路由的价格回填规则见 [06](./06-model.md)，不改写已落盘的历史账单）。缓存文件完整保留服务端返回的全部模型声明（包含文生图、向量嵌入与语音合成/识别等非对话模型标识）：有效目录保留全量成员，对话模型路由按模型模态类型过滤，而非对话模型列表则作为协议端点（endpoint）服务能力判定与路由的数据源（见 [06](./06-model.md) §6.7）。单个成功缓存文件的读写均受 `8 MiB` 容量上限约束；若归一化后的目录声明超出 `8 MiB`，则保留上一份有效成功观察，拒绝写入会导致下次启动无法加载的超大文件。查询身份摘要完整覆盖账号 ID、完整 `base_url` 路径、供应商协议适配器类型以及影响目录返回结果的自定义请求头与凭据身份；旧查询身份生成的缓存文件不会被新服务地址或其他账号实例复用，也不会因删除账号、重命名或修改地址而顺带删除。

第 2 版查询指纹（query fingerprint v2）显式纳入供应商协议适配器类型，防止同一服务地址在切换协议适配器后错误复用按旧协议解析的模型目录。成功缓存文件格式版本号升级至 `3`：格式版本 `1`/`2` 及第 1 版查询指纹的旧缓存文件仅在明确的缓存升级边界按需读取，完整保留原文件、模型成员、元数据与最后成功时间，并为同一账号的旧查询身份记录唯一迁移目标，确保后续再次切换协议时不会反复导入同一份旧快照。当无法证明旧缓存快照的供应商协议解析来源时，该快照仅作为带标记的历史成功快照保留，用于网络探测失败时的降级回退，而不得冒充当前协议下的新近在线观察，也不得作为新协议解码时的前次声明参与缺失字段继承，且在收到完整在线响应重新验证之前禁止向服务端发送旧 `ETag`。若缓存升级过程失败，仅上报该账号的局部缓存诊断并保留可重试现场，不清空缓存文件，更不触发全局启动备份重置。

在线模型目录探测唯有在网络请求、响应解码、声明校验与查询身份核对全部成功后，才通过同目录单文件原子替换更新 `model.json`，随后再发布内存观察快照。若磁盘写入失败，则保留上一份已发布的内存目录与磁盘成功文件，并如实报告写入失败而非持久化成功；被取消或已过期的迟到探测结果严禁提交。HTTP `304 Not Modified` 响应唯有在当前相同查询身份已持有本地成功快照的前提下，才允许更新最近检查时间戳。缓存文件的结构版本独立于 `config.toml` 与应用发布版本号；系统不按固定过期时间（TTL）或常规应用升级作废本地失败回退缓存，也不将派生的目录缓存回写进 `settings.toml` 或 `config.toml`。缓存文件同时记录模型目录归一化规则版本号：缺少该版本号的旧缓存文件仍可用于网络失败时的降级回退，但在发起在线探测时不附带旧 `ETag`，强制拉取完整目录响应并按当前归一化规则重新落盘，从而使服务端未声明的模态字段得以采用最新默认规则，而服务端明确声明的字段则由新响应权威决定，无需从旧缓存文本中猜测原始响应是否省略了某字段。单纯升级归一化规则版本号不会改变查询身份摘要，也不会删除旧缓存文件。在 Windows 平台上执行缓存文件原子替换时，统一使用系统支持的扩展完整路径形式，防止因用户自定义长数据根路径叠加临时文件后缀超出常规路径长度限制而导致目录保存失败。

应用启动在校验配置中的模型引用之前，先行加载各账号同查询身份的本地成功缓存。若缓存文件缺失、损坏、版本不兼容或读取报错，仅生成该账号实例的局部诊断并自动回退至账号模板的内置默认模型定义，同时保留磁盘原文件现场，不触发全局启动备份重置。后续后台在线探测失败同样不会改写或清空已有的成功缓存文件（动态模型选择暂时无法解析时的不可用状态语义见 [20](./20-config.md)）。配置加载或系统凭据服务本身的环境错误仍沿用原有的启动错误处理边界，不伪装为模型目录缓存缺失。

所有后台在线模型目录探测任务均纳入启动取消与宿主关闭（shutdown）编排：收到关闭信号时先封闭新观察发布，取消在途网络请求，等待正在执行的单文件原子替换与全部后台任务收束退出，最后才释放底层资源，确保不存在脱离生命周期管理的孤立刷新任务或关闭后的迟到文件写入。`v2/model-catalogs/` 目录位于 `v2` 整体备份范围之内，但缓存自身的读写故障绝不作为触发全局备份重置的理由。

## 17.4 对话历史、调用统计与实时流协调

会话附件记录在草稿转正提升（promotion）、目录加载、运行时传递与新写入的输入历史载荷中，始终保存相对于所属会话目录的相对二进制路径（`blob_relative_path`，持久化字段名保持为 `storagePath`，因此既有清单与历史载荷无需重写）。唯有附件存储模块边界可结合记录绑定的会话身份将其解析为宿主磁盘上的完整绝对路径，供内容寻址归档、完整性哈希校验与正文读取使用；常规附件读写接口直接拒绝绝对路径及越出本会话 `blobs/` 根目录的相对路径，历史遗留的旧绝对路径仅在附件清单迁移边界执行一次性转换。已落盘的历史对话载荷仅提供附件展示元信息，不参与磁盘文件路径解析；上层调用方严禁自行拼接路径，或按进程当前工作目录、本地项目及 SSH 远端工作区路径去解析附件位置。

附件草稿暂存区（`attachment-drafts/`）与已受理输入的会话可靠附件（`blobs/`）分属两个独立的所有权域。当用户输入受理并将附件提升（promote）转入会话可靠存储后，系统不会立即自动删除同一草稿 ID 对应的暂存文件，因为客户端较新的逻辑输入草稿可能仍在引用该暂存对象。客户端负责追踪逻辑草稿与已冻结提交的引用计数，唯有当最后一个引用所有者释放后，才显式发命令请求删除对应的暂存附件；若磁盘删除报错，则完整保留内存登记与原文件以供重试，禁止先抹除索引再吞掉 I/O 错误。当输入提交处于“结果未知”状态时，客户端继续持有冻结引用不予清理；活动输入草稿亦不会因界面观察者卸载或固定空闲时长到期而被后台自动删除；已被可靠历史引用的会话附件更不参与草稿暂存区清理。应用正常退出不会删除旧版本隔离目录、`v2` 会话历史、配置文件或系统凭据；客户端关闭仅负责收束在途资源任务，不得以清空本地数据代替生命周期确认（前端草稿状态契约见 [25](./25-frontend-state.md)）。

每个活动会话由会话管理器持有可靠的未提交状态副作用队列，唯一的历史写入器借用队首批次并写入 `history.sqlite`，待 SQLite 事务提交确认后才从队列释放该批次；同一事务内同步写入任务身份索引、终态工具交付记录与交互幂等回执。全局调用诊断记录器（call recorder）则作为独立的尽力而为（best-effort）后台任务写入滚动 JSONL 日志与有界 SQLite 索引库，其队列积压或写入故障绝不阻塞会话执行或可靠历史确认。旧版调用统计库不导入本版本的会话历史库。若历史写入器任务意外退出，未落盘队列仍由会话管理器安全保留，待旧写入任务彻底结束后按当前已落盘水位无缝重试。当实时观察窗口因滞后错过部分状态副作用时，会话累计用量统计直接从可靠检查点的绝对摘要中恢复，无需回读调试日志；批次已进入可靠队列但尚未完成落盘时仅标记为“待写入”，不得将其直接锁存为统计数据丢失缺口。

普通用户问答（`ask_user`）与计划确认（`plan_submit`）的类型化历史展示均派生自权威交互记录（canonical interaction），不维护第二份独立的回答账本。终态交互回执与原工具调用条目的问答状态更新在同一可靠历史写事务中原子提交，确保已解决的交互从常驻内存检查点裁剪回收后，历史时间线仍能完整回看问答详情。针对本版本早期 `v2` 历史库中尚未内嵌问答投影的旧记录，系统通过受版本控制的数据库迁移，从已持久化的交互回执（`history_fact_receipts`）中提取权威问答事实回填至发起该交互的原工具条目，完整保留原条目的身份、排序号（`ordinal`）、创建时间与原始调用内容，既不重放交互、模型或工具，也不清空历史库。该回填迁移保证事务化与幂等性，遇到损坏或自相矛盾的记录时显式报错中止；若缺少已保存的交互回执证据，绝不仅凭工具最终显示成功就伪造用户批准或回答。公开历史投影中的敏感回答（`isSecret`）严格遵循 [18](./18-studio-state.md) §18.8 执行脱敏，而底层的私有原始回执与模型续接上下文则保持原貌不被破坏性改写。此项结构升级在向客户端交付时间线内容基线之前完成，回填操作仅更新工具条目的派生展示载荷而保留其原有内容版本号（`revision`），不占用后续正常状态提交的版本号；迁移完成后的新交互变更则继续按标准内容版本机制递增。计划确认历史沿用同一版本迁移边界，从已保存的计划提问与决定回执补齐对应的 `plan_submit` 工具条目；批准、修改意见、取消状态及其原始顺序完全以持久化交互事实为准，不从当前最新计划文档或工具返回文本中倒推。一旦迁移事务失败必须完整回滚，保持原结构版本与原始条目可重试。

子会话（child `Thread`）的终态完成通知首先依据父会话的历史消息身份索引裁决幂等去重：若相同身份的终态通知此前已被父会话受理、但当前仍停留在父会话收件箱的待消费队列中，本次实时通知必须唤醒正在等待新消息的父会话观察者，既不能因命中去重而跳过唤醒信号，也不能为了触发唤醒而向收件箱重复插入第二条消息；反之，若该通知早已被父会话模型请求消费完毕，则不得再次唤醒或启动父会话模型。子会话终态通知以子会话产生终态时的写入序号（`write_seq`）作为稳定通知身份；通知报告包含观察时刻的终态摘要，事后冷重建的正文差异不作为同一通知身份的内容冲突依据——若父会话已受理过该身份，则保留首次受理的正文并仅按原受理序号触发唤醒；而普通用户消息与智能体主动发送的消息仍严格按正文哈希判定身份冲突。当父会话实时观察窗口出现序号缺口时，系统仅按缺失的 `write_seq` 区间精确补齐子会话终态通知，通知身份依然使用原始状态副作用的 `write_seq` 而非历史条目排序号 `ordinal`；本次进程运行期间新完成的子会话与正常实时投影一样唤醒父会话，而冷恢复阶段补齐的历史旧完成事实则仅修补持久层记录，不自动触发父会话模型调用。

内核后台工具任务完成结果投递至收件箱时，其消息身份由当次消息准入分配的持久化单调递增序号唯一确定，禁止在有界内存消息窗口内搜寻所谓“可复用”的编号。内存消息去重窗口裁剪与检查点冷恢复均不会回收或重置消息编号；既有历史消息身份保持不变，后续新完成的后台任务沿当前已持久化的准入水位继续向上分配，且历史库严格拒绝同一消息身份写入不同内容。

设置页的“模型性能历史”视图直接读取当前统计口径下已记录的成功模型调用样本；缺少有效分段计时的成功调用仍正常列出，仅将对应的时延或生成速率标记为“未采集”。每条性能样本保存同一次成功推理（`inference`）的输出词元数与单调计时摘要，样本有效性判定严格遵循 [06](./06-model.md) §6.12：输出词元缺失、为零或无效的调用不计入总响应耗时分母，计时缺失或前后矛盾的调用亦不参与速率聚合计算；首字时延（TTFT）与首字后生成耗时可独立于总响应耗时保持为未知。原始调用诊断记录原样保留，不因某次调用不具备有效速率样本而删除或改写。会话最近一次已确认生成速率的成对聚合摘要遵循 [18](./18-studio-state.md) §18.8，随会话检查点同步持久化，无需依赖有界的全局性能样本表或滚动 JSONL 日志即可在冷恢复后还原。计费与性能观察的去重身份由**实际执行调用的会话 ID（`thread_id`）与推理 ID（`inference_id`）**联合确定；根会话 ID（`root_thread_id`）仅用于整棵会话树的费用归集与归档清理，绝不能代替实际执行会话 ID 参与调用去重——不同子会话内部即便出现编号相同的局部 `inference_id`，也会各自独立记入调用历史与性能统计，而同一会话内部的重复投递则严格保持幂等。当调用统计库仍有批次在途待写时，查询快照可先行返回已提交部分并显式附带“待写入”标记；待后台写入器完成提交或明确拒绝后，再发布更新后的统计结果与新的展示版本号。读取调用统计库报错时必须显式暴露读取故障，不得伪装为空统计列表；诊断统计缺口独立展示，且不反向阻塞任何会话执行。运行人工模拟验收（`manual-gui`）时使用的隔离临时数据根目录与用户日常使用的默认数据根目录完全隔离，互不共享统计或会话数据。

调用诊断明细遵循 7 天日志保留期；模型性能汇总则使用全局独立的有界样本表，按调用完成时间与复合调用身份稳定排序，仅保留最近 `3000` 条有效成功调用样本，并在每批统计写事务提交前自动裁剪超出窗口的更早样本；会话可靠累计费用、执行幂等身份与对话历史正文不受性能样本淘汰影响。性能样本作为独立投影存储，不持有指向已轮转淘汰的原始日志表的外键。在本版本将生成速率统计口径从“纯解码速率（decode TPS）”切换为“含首字等待的总响应速率（end-to-end TPS）”时，旧口径的性能样本直接作废丢弃，不执行近似折算或迁移；性能历史与速率汇总仅读取新口径样本，禁止从旧 JSONL 日志或历史账单中回填复活旧速率统计。旧检查点中缓存的最近速率派生值同步作废，待新口径下的有效样本产生后重新建立；除此之外的累计词元用量、累计费用、原始调用日志、账单明细与对话历史全部完整保留。性能样本自身内含模型标识、词元用量与计时摘要，聚合查询无需回读已过期的 JSONL 日志正文。统计写入器按批次共用单个 SQLite 事务，批次内部单条记录写入失败通过事务保存点（`SAVEPOINT`）局部隔离，整批成功记录的完成水位严格在外部事务正式提交后才推进；可重试的写入失败按原顺序重新入队，不可恢复的硬错误则显式记入统计缺口并终结对应写入票据（ticket）。

新创建的 `Session` 在首次分配条目顺序键（`ordinal`）前，仅执行一次只读查询获取本会话 `history_items` 表中已持久化条目的最大 `ordinal` 作为初始种子（空库种子为 `0`）。随后 `Session` 在内存中按条目身份分配唯一、严格为正且处于 SQLite 有符号 64 位整数范围内的 `ordinal`；同一条目身份重试时始终复用原序号，未落盘的序号预留在进程重启后不予恢复。实时流式预览与历史写入器共用同一个 `Session` 序号分配器；历史写入器仅负责将已分配好 `ordinal` 的条目落盘，一旦发现序号缺失、被篡改或发生重复冲突，立即按失败关闭中止事务，严禁使用数据库自增主键、SQL 预留表或在写入时动态回退重分配。旧版数据库中遗留的序号预留表既不参与初始种子计算，也不执行迁移。

模型传输层透明恢复产生的展示事实随模型所有者的最终调用回执一并持久化（观察契约见 [16](./16-core-contracts.md) §16.3）。引入观察代次扩展不会重写既有时间线条目的身份或历史排序号；早期 `v2` 回执若缺少观察代次与失败子尝试字段，在其生产者解码边界自动解释为“首次尝试且无透明恢复记录”，原有回复正文与计费数据保持不变。任何新增持久化字段均须明确定义缺省值或版本迁移规则，禁止因旧记录缺少新增恢复字段而清空历史库、重置默认配置或回退读取已隔离的旧版本数据根。

历史写入器的保存确认（`confirm_saved`）仅释放本次事务实际落盘的条目身份与对应内容版本（`revision`）。当一次模型尝试仍处于在途运行状态时，针对其早期条目的保存确认不得清理随后新发布的当前流式观察或已收束的失败子尝试预览——这些运行期观察事实由模型所有者的最终调用回执负责统一收束落盘。唯有当该次模型尝试的终态已正式提交落盘后，方可释放该尝试残留的推测性流式预览，且释放操作不得删除本事务已提交的条目身份或改变它们在历史时间线中的排序位置。

对于已先行写入 `history_items` 但当时尚未关联具体轮次的独立消息条目，后续模型消费该消息时可使用原条目身份与原 `ordinal` 将其绑定至消费它的轮次（`turn_id`）。若该消息条目的 `ordinal` 小于目标轮次在 `history_turns` 表中已记录的 `first_ordinal`，历史写入器必须在更新该消息条目的同一 SQLite 事务中将 `history_turns.first_ordinal` 向前扩展至该消息的 `ordinal`；除这一合法的消费绑定扩展外，任何轮次的首条序号均禁止被随意改写。

输入身份索引（`history_input_identities`）与消费该输入的轮次状态副作用在同一事务中持久化输入的展示属性。普通可见输入必须在 `history_items` 表中存在对应的展示条目；而系统生成的隐藏续接输入则仅在 `history_input_identities` 中保留最小身份与隐藏标记属性，不向 `history_items` 写入可见展示正文。当后续轮次在原始输入正文已滑出有界内存状态后再次引用该输入身份时，历史写入器通过核查“存在可见历史条目”或“存在已提交的隐藏输入身份”来判定引用完整性；实时投影在历史写入器追平水位之前，还可结合自身有界内存窗口中刚受理的隐藏输入事实完成核验。唯有明确带有隐藏标记的输入身份可免除可见展示条目要求；若输入身份缺失、展示属性未知或隐藏标记与实际存在的展示条目自相矛盾，写入器一律按失败关闭拒绝提交。当升级早期 `v2` 历史数据库时，迁移事务仅依据已提交交互回执中与输入身份严格匹配的续接记录（`continuation`）及原始展示选项来精确回填隐藏标记属性，严禁仅仅因为“在 `history_items` 中找不到展示条目”就盲目将该输入猜测为隐藏输入，也不因此清空历史记录或未提交队列。冷历史分页查询对尚未执行此项升级的旧 `v2` 库仍可保持纯只读访问；当活动会话的实时投影首次需要执行隐藏输入身份判定时，由唯一的历史写入器在版本迁移事务内完成数据库升级，只读冷查询绝不为触发升级而创建会话所有者或改写数据库。

Studio 产品投影在每次状态副作用提交时生成权威的轮次、时间线条目与交互状态变更，并以同一稳定身份同步送入内核 `TimelineState` 与可靠历史写入通道：

```text
会话所有者（Thread owner）
├─ 当前状态快照（ThreadSnapshot） ──────────────→ 会话状态订阅流
├─ 条目 / 轮次 / 任务状态副作用（ThreadEffectBatch） → 可靠历史保存通道 → 历史写入器（history.sqlite）
├─ 时间线状态（TimelineState） ────────────────→ 游标分页 / 有界尾部订阅 / 按身份详情 → GUI 与 HTTP
└─ 模型与工具调用统计 ─────────────────────────→ 可丢弃调用诊断记录器（calls.sqlite + JSONL）
```

会话激活后的首帧 `ThreadSnapshot` 仅包含当前逻辑状态、待决交互、运行时视图、工作流状态与目录引用，不内嵌完整的时间线正文。内核 `Session` 是热会话与冷会话历史分页、最新端尾部订阅及按身份详情读取的唯一权威内容源（接口、预算与实时/历史模式切换契约见 [26](./26-timeline-content.md)），普通分页查询既不经过会话执行所有者，也不触发写入器刷盘或激活冷会话。存储层故障通过独立的状态观察流上报，不会被 GUI 内容渲染缓冲阻塞。

前端按需保留当前会话已浏览页面的轻量消息集合，这不等同于在客户端加载完整可靠历史；读取消息原文与展开工具详情均受显式预算约束。时间线内容读取协议的演进不重写已持久化的历史 `payload` JSON，也不清空历史库；任何涉及底层表结构的变更均严格通过 `v2` 版本化事务迁移执行。

## 17.5 持久化收束与诊断

完整的模型协议回放材料作为内存提交时的冻结载荷随状态副作用一并落盘，活动会话在构造下一轮请求时直接读取内存中的权威上下文，绝不从历史展示分页、调用调试日志或界面展示投影中反向拼装模型请求。会话重新打开时，直接从同一事务保存的检查点与有序当前上下文表中读取记录，经校验会话身份、内容哈希、记录条数与历史保存水位无误后恢复至内存。底层的物理模型网络连接与 WebSocket 增量续接缓存不跨进程恢复：重开会话后的首次模型执行将发送完整上下文历史，待服务端响应成功后再建立新的连接内增量续接状态。单纯打开会话既不重新执行已完成的模型或工具调用，也不使用当前最新系统指令去重新渲染已持久化的历史上下文；旧版会话中原本未记录的协议回放材料亦不作事后猜测回填。

每个已加载的会话仅由唯一一个可靠历史写入器串行落盘：对话历史、当前有效上下文、恢复检查点与累计用量统计在同一 SQLite 事务中原子提交，固定刷盘水位（flush watermark）唯有在事务提交确认后才宣告达成，系统中不再运行独立的 TOML 快照定时调度器。当前上下文表仅维护最新有效记录集合，常规对话推进仅增量插入新增记录，触发上下文压缩替换时则在同一事务内更新有效集合并清理被替换的旧记录，不保留多份历史上下文全量快照。

公开的持久化诊断状态完整保留脏数据版本（`dirty`）、正在保存版本（`saving`）与已落盘版本（`durable`），以及历史库与诊断库各自的已接纳水位（`admitted`）、已落盘水位（`durable`）、待保存批次数量与字节数、最老未落盘批次等待时长、当前故障代次（`fault_generation`）及准入暂停状态。当可靠历史保存发生故障时，系统完整保留未落盘批次并在安全间隙暂停新模型与新工具准入，待用户通过显式重试与显式继续协议确认修复后方才恢复执行；调用诊断日志的写入故障则单独上报，不纳入可靠会话保存屏障。聊天界面顶部横幅仅提示可靠存储故障、执行准入暂停或存储容量背压；调用诊断日志缺口仅在设置页的统计视图中提示，不会因全局调试日志曾发生写入失败而在聊天窗口常驻显示保存故障横幅。会话关闭与应用退出必须等待相关会话到达固定的可靠落盘水位，严禁在仍有未保存事实时谎报关闭成功；全局对外报告的已确认水位取所有相关会话所有者的最小值（即要求每个所有者均已推进至各自目标水位），禁止用单个会话的最大水位冒充全局确认。

应用关闭时的持久化收束严格以历史写入器的真实确认（writer ACK）为准：在写入器确认落盘完成之前，系统继续保留会话所有者与数据库句柄；只要仍有任一历史写入器处于运行状态，即禁止关闭底层 SQLite 连接，也禁止释放跨进程实例文件锁。关闭编排按真实的有向依赖顺序推进写入收束链——后台工具任务、活动轮次、子智能体与自动标题生成等上游生产者的停止确认（stop ACK），严格先于可靠保存通道排空（drain）与历史写入器停止；而历史写入器的真实落盘确认，又严格先于关闭数据库连接与释放实例文件锁。与此同时，与会话持久化无依赖关系的独立所有者（如后台文件监视器、本地 MCP 服务、本地 LSP 服务、界面订阅流及应用更新检查器）则与上述写入收束链**并发**推进收束，共享首次退出请求固定的同一绝对期限剩余时间预算，避免逐个串行等待而相互挤占超时预算。

需要注意，SSH 远端传输通道（SSH transport）与远端工具及远端服务之间存在直接依赖，不属于可无序并发关闭的独立所有者：由于 SSH 传输通道承载着远端 MCP、远端 LSP 与远端命令工具的通信，其物理连接关闭（即终止本地 SSH 客户端子进程）必须发生在上述远端依赖项的停止请求下发与结果处理完成、以及驱动远端工具的上游生产者（活动轮次、智能体等）确认停止**之后**；否则提前切断 SSH 管道会导致正在正常退出的健康远端资源被误判为通信异常失败。在满足这一前置依赖后，SSH 传输通道的回收仍与本地数据库写入收束链并发执行，无需等待与远端无关的本地 SQLite 事务提交；若前置远端依赖在预算期限内停止超时或报错，编排器按有界降级策略照常发起 SSH 通道回收，仅放弃继续等待该依赖的停止确认，而将其未收束的所有者句柄留在常驻槽位中保留。

应用退出报告中携带的保存栅栏（fence）与待保存计数仅反映真实落盘进度：状态未知即如实报告 `Unknown`，绝不使用“已排空（`Drained`）”或“`Clean`”掩盖未落盘事实；一旦关闭结果为降级（`Degraded`）或超时，应用在退出前主动保留跨进程文件锁不予释放，交由进程彻底终止时的操作系统内核文件锁回收机制兜底释放，从而防止新启动的应用实例与仍在后台收尾写库的旧写入器发生并发写库竞争（退出报告结构见 [18](./18-studio-state.md) §18.5.1）。诊断日志系统的收尾独立于运行时（runtime）是否已完成初始化：即便运行时从未安装或初始化失败，退出流程仍通过独立的诊断收尾命令刷写并回收诊断资源；退出阶段的严重错误通过同步错误日志、临时应急诊断文件与标准错误流（`stderr`）三重兜底落盘，仅记录错误码（`code`）、关联追踪 ID（`correlation_id`）、待保存事实计数与保存栅栏水位，绝不写入敏感凭据或对话正文，且应急日志写入本身不得延误应用退出的硬期限。

调用诊断日志的容量上限、跨日轮转与过期清理规则见 [15](./15-session-storage.md) §15.7。早期 `v2` 内部格式数据在完成版本化事务迁移并校验通过后，方才回收已被替代的旧文件；会话附件与工具归档媒体按可靠历史引用永久保留，不适用调试日志的 7 天过期淘汰策略。所有文件回收操作仅作用于已确认归属本版本 `v2` 的受管资源，绝不触碰已隔离的旧大版本数据根目录。

早期 `v2` 的会话费用迁移按调用用途（`purpose`）与计价币种核对检查点与调用诊断库水位：主模型调用与上下文压缩费用已包含在检查点累计摘要中，迁移仅将自动标题生成与自动安全审查产生的辅助费用按幂等身份补入检查点，严禁将检查点累计值与调用库累计值直接盲目相加。迁移完成后的后续辅助调用计费统一通过可靠状态副作用随会话检查点同事务提交。当前检查点仅保留最新一份上下文压缩回执，历史压缩调用则以各自的独立调用身份保留在历史与统计中。

账号“不计费（`NoCharge`）”语义升级不会回溯改写历史账单：历史记录中的 `Disabled` 状态仍如实表示调用当时关闭了价格估算，不会在升级后被改写为 `NoCharge` 或零费率。新增的 `NoCharge` 状态属于模型请求冻结时记录的用户显式声明，该调用不产生账单金额，但完整保留原始词元用量、生成速率、模型归属与幂等身份；持久化存储与历史回放直接消费请求冻结时保存的计费模式，不根据当前最新的账号设置去重新计算历史账单。新增计费枚举按所属存储版本边界平滑接入，既有历史账单与累计金额保持原值不变，不得以清空统计库或全量重算代替版本升级。

早期 `v2` 的独立 TOML 检查点在会话按需激活时执行迁移：先校验结构版本、外部正文完整性与历史水位栅栏，再在 SQLite 事务中写入精简后的 `thread_checkpoints` 记录并执行回读核验。唯有回读核验成功后，才依次回收主备 TOML 文件及专属的旧检查点外部正文文件，且清理进度记录支持中断后幂等重试。早期 `v2` 调用统计库则按批次保全累计摘要与保留期内的诊断记录，待发布新迁移版本号后回收旧版外部正文目录（含未登记的孤立文件）；运行中工具参数与终态工具交付在迁移解码边界分别按各自格式解析。

## 17.6 Git 工作树租约与物理资源恢复

`v2` 轮次失败记录包含可选的结构化模型失败事实：缺少该字段的早期 `v2` 记录在持久化解码边界自动恢复为“无结构化模型失败事实”，完整保留原有的诊断文本与身份；新产生的失败记录则原样保存模型层上报的结构化事实，不从旧版错误消息文本中反向猜测账号错误分类。

物理 Git 工作树租约（worktree lease）是工作树磁盘资源的唯一所有权凭证。会话目录摘要中的 `workspace_mode` 与 `workspace_path` 属于目录展示事实，不会因为底层工作树租约丢失或损坏而自动回退改写为 `local` 本地目录模式。当激活 `worktree` 模式的会话时，若发现工作树租约缺失、磁盘目录不存在或 Git 仓库物理身份不匹配，系统立即明确报错拒绝激活，并发布该会话的恢复预览（`Recovery` preview），绝不静默切换至项目根目录继续执行。

工作树租约与冻结工作区回执只登记稳定归属，不保存创建分支作为身份。恢复预览包含租约当前修订（`leaseRevision`）、基线提交、当前 `HEAD`、可选当前分支及结构化检查状态 `inspection`：`available` 表示当前物理身份及状态已核实，`missing` 表示已证实目录不存在，`identityMismatch` 表示注册或身份不一致，`unavailable` 表示 I/O、Git 或 SSH 检查失败、无法确认。已确认 checkout 的分支为空表示 detached；检查失败时不能据空分支推导 detached。未知的 `headCommit`、`dirty` 与 `changedFiles` 均为空值，不以空列表推导干净。诊断区分具体身份条件并保留失败操作和有界脱敏原因，文本上限为 2048 个 Unicode 字符；不向界面泄露凭据，也不从 Git 的错误文本猜测文件系统缺失。

有界脱敏不能以删除全部原因替代：文件访问保留可知的操作阶段与系统错误类别，SSH 连接、认证、辅助进程协议和远端文件访问失败应保持其已知分类，Git 非零退出保留操作、退出码及安全原因摘要。未知原因可以明确表示未知，但不得覆盖底层已知的类型化事实；远端连接失败不冒称本地文件系统故障，原始认证信息及无界 stderr 不直接进入展示。

检查失败只发布观测事实，不把活动租约描述为已转为 `preserved`，也不声称缺失文件仍有备份。故障活动租约、已归档 owner 的租约、孤立租约与保留现场都可以展示诊断，但展示不等于获准清理：动作由后端当前事实决定，所有工作树诊断保留重试入口。活动 owner、缺失、身份不一致、未知或含本地内容的工作树不能成为独立安全清理候选；执行时重新核验 [12.5](./12-collaboration.md#125-git-工作树worktree生命周期与故障恢复) 的授权条件，陈旧界面快照不授予删除权限。当前独立身份修复阶段，归档与取消归档保持租约和物理资源不变，不为了构造诊断阻塞目录操作；下述归档强制清理尚待最终关闭重构接入。

根会话与 child 的普通装配、继续执行或取消归档均不重建缺失工作树。旧版租约中的归档恢复重建授权在版本化存储升级边界退役，原租约身份、修订、状态及关联历史保持不变；旧版已清理资源仍为 `cleaned`，不因升级或取消归档伪装为可用。迁移不得创建工作树、删除残留资源、重置历史或清空数据库。已保留且物理身份可验证的站点按执行准入规则复用，未经验证不得退役恢复诊断。

既有 `v2` 租约及 `studio.workspace` 冻结回执中的创建分支字段在各自版本化迁移边界退役；正常运行只消费不含分支身份的当前结构。仅为真实已发布格式提供转换，不为未发布中间草稿增加版本或运行期兼容。迁移保留 owner、项目、远端目标、仓库、路径、基线提交、业务修订、已有关闭事实与历史水位，未知或损坏格式明确失败且不产生半升级结果。存储表示升级不操作真实 Git 分支或 checkout；旧版专属分支及业务分支均保留。工作区回执升级复用既有检查点维护边界，不为归档另设旁路；旧 `preserved`、关闭状态或未知记录均不能推导为新删除或 force 授权。

错误跨工厂与运行时包装后仍保留可匹配的领域来源，不以解析展示文本补救类型丢失。

**待接入的最终关闭存储契约**：`close_agent { target, force?: boolean = false }` 由并行重构统一接入，不在本阶段扩充旧处置选择。最终关闭意图先耐久保存，随后执行及保存收束，最后按明确自有绑定清理；清理失败不撤销永久关闭，重试只消费原绑定和授权。归档接入时明确传 `force=true`，该授权仅放弃内容保全，不能绕过身份、Git 锁、真实使用者、进程退出或保存屏障；全部必要关闭与清理结果确认后才发布完整归档成功。返回事实须分别表达永久关闭与工作树已删除、不存在、不适用或清理失败，普通应用退出不新增最终关闭意图。

**待接入的失败接续契约**：未发布分配仍由原创建所有者负责，归档不能仅枚举已发布目录而遗失责任；合法私有 owner 在初始 checkpoint 已耐久但目录发布失败时，仍须保存、关闭并排空观察，不能依赖尚不存在的公开关联。原子替换后的同步失败须在既有 canonical 存储边界裁决可能已提交的结果，不能以旧缓存 absence 证明未发布；也不得以已发布会话检查点缺失推导未执行或可删除。故障保证覆盖取消、应用退出/崩溃与重启，不扩展为断电或 OS crash。完整授权与回归要求见 [12.5](./12-collaboration.md#125-git-工作树worktree生命周期与故障恢复)。

一切物理工作树资源的创建、状态流转与清理删除，必须在更新对应的会话检查点或目录版本栅栏之前先行将其所有权租约状态持久化落盘。若底层文件系统或 Git 命令已执行成功，但随后的目录保存失败，系统必须完整保留磁盘资源与补偿记录以供重试，禁止直接删除刚创建的物理现场来冒充事务回滚。

## 17.7 大版本隔离与配置迁移

账号模型术语升级（从 `provider` 统一至 `account`）仅涉及非会话配置文件及本版本 `v2` 内部模型接入身份的保全转换，不构成新一次会话存储断代。全局配置、智能体预设与操作系统凭据引用的可恢复转换契约见 [20](./20-config.md)。迁移过程严格保留账号稳定 ID 原值不变，账号显示名称不参与绑定隔离身份计算，确保同一账号绑定不会因字段命名升级而被误判为另一个新账号。

既有 `v2` 会话检查点中的产品模型路由（`studio.model-route`）与子会话冻结预设扩展，在持久化解码边界按版本号将旧版 `provider`/`model` 字段无损转换为 `accountId`/`modelId`，完整保留原有的模型 ID、推理强度（`effort`）、扩展版本号、检查点水位栅栏与对话历史；随后由该会话唯一的历史写入器在事务内落盘更新为当前结构，若迁移校验失败则拒绝激活模型且不推进结构版本号。按需打开会话、冷恢复与父子会话续接共用同一套按需迁移边界，不在启动时批量打开全量历史库。其中，子会话冻结预设的旧字段严格按其历史序列化契约从 `providerId`/`model` 转换为 `accountId`/`modelId`，不得生搬硬套根会话模型路由的字段名；若同一记录中新旧字段同时存在且指向的账号或模型身份相互冲突，则立即拒绝迁移并原样保留原检查点。类型化账单与调用记录仅转换已知的账号标识字段，不改写供应商不透明协议正文，也不根据当前全局配置去猜测历史调用的账号身份。

统一智能体定义的指令表示升级同样在既有的检查点维护事务中完成：旧版混合角色来源结构与旧版按特定根会话身份硬编码约束指令块数量的结构，各自先按其历史格式精确解码并校验，再无损转换为携带冻结指令块形状与内容身份的当前统一结构。转换过程仅消费检查点内已保存的智能体定义、预设、工作模式、渠道归属及指令正文，不读取当前最新的全局声明去为历史会话强行补入角色块——旧版普通根会话原本不含独立智能体角色块的事实必须如实保留。扩展版本号、指令正文、XML 标签、拼接顺序、有效渲染结果、用户动态事实 `source` ID 列表、模型路由及工作区绑定均保持不变，且绝不重写已落盘的历史模型请求。若发现身份冲突、来源重复或遗漏、未知结构版本或事务提交失败，一律完整保留原检查点数据并阻止不安全激活，严禁降级为空角色指令或重置会话。正常运行时读写路径仅消费当前统一格式，旧版结构兼容解码仅存在于按需迁移边界。

恢复会话所有者之前的检查点维护事务同时覆盖根会话模型路由与子会话冻结预设：仅仅在内存反序列化时兼容读取旧字段不算完成升级，必须在历史写入器事务内比对已读检查点并将转换后的当前扩展载荷正式落盘，且历史水位、扩展版本号与业务逻辑状态不因存储表示升级而发生改变。供应商原生压缩来源的冷恢复同样消费这一版本化回执解码边界，禁止在旧版压缩回执上直接强行反序列化当前账号绑定结构；一旦解码或事务提交失败，立即保留原检查点并拒绝激活。

调用统计数据库（`calls.sqlite`）的表列名、索引与查询投影在版本迁移事务内统一转换为 `account_id`、`account_display_name` 与 `model_id` 语义，原有的调用主键与全部历史费用事实完整保留。模型性能视图顶层按已冻结的“配置账号 + 配置模型”聚合，二级按推理强度（`effort`）细分；缺少配置模型证据的早期历史样本保持为未知（`legacyUnknown`），不使用实际发送模型名（`sentModel`）冒充配置模型。会话级及按用途/币种汇总的累计费用不重新计算、不清空。在线模型目录成功缓存保留同账号、同查询身份的降级回退能力，字段或归一化规则升级仅在显式版本边界转换；磁盘上的旧缓存文件与最后一次成功声明完整保留，严禁通过清空目录缓存或拒绝一切历史缓存的方式来实现术语改名。

本版本不执行旧版会话事务日志（journal）、旧版产品数据库或旧版调用统计库的格式转换、导出与归档，也不提供 `migrate-legacy-storage` 命令。`~/.anywork/studio/sessions.sqlite`、旧版 `studio/studio.sqlite`、旧版 `studio/calls.sqlite`、旧版全局附件目录及旧迁移报告全部原样保留在原路径；新版会话仅读写 `v2/` 与 `studio/v2/` 下的独立数据根，且绝不将旧版本隔离数据作为新会话缺失条目的回退补全来源。唯有全局账号等非会话配置按配置契约安全升级；当遇到无法恢复的数据损坏时，按 §17.2 执行整体备份后重建初始化，且操作系统凭据始终保留（见 [20](./20-config.md)）。

### `v2` 平铺会话目录向项目层级目录的迁移

本版本早期直接存放在 `v2/sessions/<thread-key>/` 下的平铺会话目录，必须无损迁移至归属项目下的 `v2/projects/<project-key>/sessions/<thread-key>/`，此项内部布局调整不构成新的存储断代。布局迁移在启动协调器取得数据根目录独占锁、完成 `catalog.toml` 与 `workspaces.toml` 加载校验之后，且在任何会话历史写入器启动与服务对外发布之前执行；迁移计划完全根据已加载的目录身份摘要生成，不逐个打开会话历史 SQLite 数据库，也不激活任何模型或工具实例。对于未在 `catalog.toml` 中登记归属的孤立旧目录，原位保留并输出启动诊断，绝不为尚未物化的空会话目录凭空捏造历史数据库。

版本化的布局迁移日志保存在 `v2/migrations/` 下，逐条记录每个会话目录的“准备、移动、验证”状态。迁移采用整目录原子重命名（rename）方式移动，完整保留会话目录下的 `history.sqlite` 主库、`-wal`/`-shm` 日志、旧版检查点文件、可靠资源正文及任何未知的普通文件；项目与会话归属小清单（`project.toml`、`session.toml`）的生成与更新则复用标准同目录临时文件原子写入原语。附件清单（`attachments.toml`）中若存在已知的历史旧绝对路径，仅在本次迁移边界核验其确实指向当前会话的原平铺源根目录后，将其转换为相对于本会话目录的相对引用；正常运行时路径不再兼容旧绝对路径，且迁移绝不篡改对话历史正文、工具调用参数或提示词中的任何路径字符串。

若迁移中途进程中断，重启后直接读取同一份布局迁移日志幂等接续已完成步骤，正常运行时读写仅消费已完成迁移发布的新目录布局。当目标路径已存在目录、但无法由当前迁移日志证明其归属本次迁移时，严禁盲目合并或覆盖；在目标目录及归属清单全部通过完整性核验之前，绝不清理源目录资源。一旦遇到未知的布局迁移版本、损坏的归属清单、目标路径冲突、符号链接或重解析点（symlink / reparse point）越界、文件权限不足、磁盘空间耗尽或文件被占用等错误，迁移立即中止并完整保留可重试现场，同时停止后续启动初始化——严禁将布局迁移失败当作触发全局备份重置并清空数据的理由。迁移错误完整保留底层原始原因：权限、容量与文件占用仍按环境故障上报，可恢复的布局数据转换错误则按启动迁移故障上报。

完成磁盘目录的物理移动并不替代会话按需激活时的检查点内部表示升级：当会话后续被打开或恢复时，仍由该会话唯一的历史写入器在事务内无损转换账号模型路由、子会话冻结预设与工作模式定义快照，保持扩展版本号、历史水位与业务状态不变，绝不因为物理目录已经移动就跳过内部结构升级。迁移日志中记录的源目录键、目标目录键以及项目与会话归属关系，必须与稳定 ID 的 SHA-256 摘要及当前 `catalog.toml` 完全吻合；迁移完成标记必须经过磁盘状态核验，禁止仅凭目标目录已存在就跳过日志校验。在创建目标项目目录之前，必须先行逐级校验既有祖先目录的符号链接边界，防止通过恶意链接在受管数据根之外创建目录。附件相对路径转换严格核验本条迁移日志指定的源会话根目录，而非匹配任意名为 `blobs/` 的路径。在执行整目录原子移动之前，系统先在源会话目录内落盘一份可校验的固定归属证明文件；若目录重命名已成功但迁移日志尚未推进即发生崩溃，重启接续时唯有核实目标目录内持有匹配的归属证明且源目录确已消失，方才允许继续推进完成标记，禁止仅凭目标路径存在同名目录就盲目接管。对于日志中已标记为验证完成的条目，重启核验时仅检查源目录确已不存在且目标路径为安全的普通目录——该快速核验仅读取文件系统目录元数据，不逐个打开 SQLite 历史库或重扫全量附件内容。若核验发现附件文件缺失、非常规普通文件或字节长度与清单记录不符，一律保留现场并拒绝标记迁移完成，绝不以重新定位、填充空文件或忽略长度差异的方式强行放行。在读取附件清单并核查每条二进制附件之前，必须自可信数据根目录起逐级校验通往目标文件的全部路径组件，防止 `blobs/` 目录或其分片子目录本身被替换为越界符号链接；该路径组件校验仅针对清单中实际引用的附件逐项执行，不递归扫描未被引用的无关文件。新建的项目层级目录与布局迁移日志一并纳入安装状态判定与 `v2` 全局备份保护边界，且重复启动应用不会重置已达成的迁移水位。

## 17.8 数据库配置与发布验收基线

所有新建的 `history.sqlite` 与 `calls.sqlite` 数据库均强制启用 `WAL` 日志模式、`synchronous = FULL`、外键约束（`foreign_keys = ON`）与 `5000 ms` 忙等待超时（`busy_timeout`）。构建打包时必须记录并核验实际静态链接或随包分发的 SQLite C 库版本号，不得仅凭 Rust ORM 或包装 crate 的版本号宣称已包含某项底层 WAL 修复。本版本的存储迁移与发布验收至少覆盖以下基线不变量：

- 旧版本的会话库、调用统计库与产品数据库在原路径保持字节级不变，既不导入也不自动归档删除；
- 账号配置、系统凭据关联等非会话配置安全完成结构升级；遇到不可恢复的数据损坏时先执行完整备份再重置初始化，原始受损字节与系统凭据完整保留；
- 新建 `v2` 会话的数据在 WAL 已提交、进程重复启动与写入中途中断后均可完整恢复；
- 会话检查点水位（`history_fence`）绝不越过已落盘的对话历史水位与外部二进制资源栅栏（blob fence）；
- 当历史写入器遭遇数据库锁忙（`SQLITE_BUSY`）、I/O 失败或确认状态未知时，可靠保存通道绝不丢失任何已受理批次；
- 存在海量历史会话时，应用启动耗时保持恒定（不扫描历史会话库），且单会话游标分页查询成本不随历史总长度线性增长；
- 冷历史分页与详情读取不激活会话所有者、不触发模型或工具执行、也不改写任何磁盘文件。

## 17.9 诊断内容与隐私脱敏

运行期错误与持久化诊断统一携带操作名称（`operation`）、会话/轮次/交互/调用身份标识以及脱敏的关联追踪 ID（`correlation_id`），严禁在诊断中记录 API 密钥（token）、工作模式提示词正文、用户系统凭据或未经授权的完整请求正文。验收失败产物（artifact）可包含迁移状态记录、数据库表结构版本、SQLite `PRAGMA quick_check` 结果、写入水位、队列背压指标、GUI/Flutter Driver 日志与文件差异对比（diff）；包含用户原始数据的启动备份目录则受操作系统文件权限保护。

时间线中的工具调用条目（`tool` item）在调用开始时即分配稳定身份；供应商流式返回的调用标识后到时仅原地更新同一条目。一旦检测到历史序号缺口、重复的 `ordinal`、同一 `(item_id, revision)` 内容冲突、检查点水位栅栏越界或二进制附件哈希不匹配，系统必须立即按失败关闭（fail-closed）处理，严禁使用当前工作区磁盘文件内容或当前工具渲染器去掩盖或修补损坏的历史记录。

## 17.10 模型目录观察缓存迁移

在线模型目录成功缓存（`model.json`）执行格式版本升级时，完整保留原始模型成员、元数据、成功时间戳与查询身份，对迁移前未知来源的字段如实标记，不冒充服务端在线明确声明的值。当升级涉及补充此前未保存的正文字段时，禁止在下一次在线刷新中使用旧 `ETag`，强制拉取一次完整目录正文，而在拉取失败时仍允许继续使用已迁移的本地缓存快照降级回退。模型成员的成功声明顺序随缓存文件原子持久化，收到 HTTP `304 Not Modified` 时不改变既有字段与排序优先级；缓存升级过程不清空本地缓存，也不回溯修改历史会话目录或历史账单中的计价快照。

## 17.11 上下文来源与版本升级

当前会话检查点与会话历史数据库的结构升级统一采用显式 SQLite 事务迁移，完整保留既有 `v2` 会话数据、对话历史及未知的供应商原生材料。对于早期记录中无法还原来源的旧词元用量，在迁移后显式标记为来源未知；旧版供应商原生压缩检查点仅从身份可核验的生产回执中恢复来源绑定，若缺乏可靠来源证据则原样保留历史数据并明确拒绝不安全的续接执行或模型切换。执行上下文回退操作时，继续保留当前最新的计划文档、工作流状态及其他业务扩展状态，上下文裁剪或回退不等同于业务扩展状态回滚。

所有自有 SQLite 存储（Studio 产品库、单会话历史库、调用统计库、机器人账本和内核通用会话库）统一采用 SeaORM 官方迁移系统。各存储所有者定义有序、具名且发布后不可改写的迁移，新建库与内存库也执行同一序列；迁移所需的历史结构固定在迁移边界，不随当前领域类型自动变化。`seaql_migrations` 是已完成步骤的唯一事实源；旧数字版本仅用于首次接管时识别已完成转换和存储格式校验，不再由独立调度器推进。接管前只读核验身份、格式和完整性，未知未来版本及无法验证的非空无版本库在任何 schema 写入前拒绝。数据库内的每个迁移显式启用框架事务，使转换、格式标识和该步骤的完成记录共同提交；失败保留原数据，按未完成步骤重试。迁移错误保留存储归属、步骤和底层原因，归入迁移失败，不触发损坏数据自动重建。

检查点信封版本与历史数据库结构版本分别演进；检查点格式升级必须有独立的具名数据迁移，不能依赖此前的上下文来源迁移顺带转换，也不能因数据库表结构未变化而跳过。显式打开会话订阅时，先由该会话唯一的历史写入器完成存储准备，再读取关闭意图、恢复状态或发布首个快照；冷根会话、子会话与已关闭子会话遵循同一顺序。子任务交互列举与打开/恢复共用现有生命周期准入锁，等待并发的存储准备完成后再只读投影，不自行迁移或激活子会话。转换与迁移记录在同一事务中提交，失败保留原检查点和未完成步骤以供重试，普通快照与历史分页仍严格只读。已保存的用量来源、上下文来源、业务扩展、历史水位与未知供应商正文完整保留，不重复应用更早版本的来源推断。

调用统计从 SQLite 正文导出到滚动 JSONL 的跨资源步骤显式采用可恢复、幂等的文件提交，不声称具备跨文件 SQL 事务。每次重试先扫描已持久日志并重建幂等索引，保全费用摘要并确认日志持久化后，才在后续数据库事务中清理旧表并登记完成。日志保留期与统计口径不变，迁移期间仍由原有唯一写入所有者持有资源。

继续点、输入用途与输入身份索引的扩展属于既有的 `v2` 结构升级，不另起数据根、不清历史。旧输入按普通消息解释，只有存在可证明的中断轮次、准备执行或未消费输入时才形成继续点；正常完成、仅有保存故障或在等待回答的旧会话不伪造成可执行，无法证明原因时按执行已中断显示。控制受理身份与其摘要进入既有输入身份索引，待处理阶段即可查询，不从终态身份筛选推断。

## 17.12 工作模式定义快照升级

会话的工作模式扩展（`studio.mode`）完整保存工作模式的执行定义快照及状态图修订号（graph revision），随会话检查点、系统指令快照与工作流状态在同一事务中原子持久化。因此，即便用户事后在全局配置中删除了某个自定义工作模式，绑定该模式的冷会话与已归档会话在恢复时仍可直接从会话自身保存的定义快照完整还原，既不依赖全局模式目录，也不会将历史快照反向重新发布回全局模式目录。

针对早期 `v2` 仅在扩展中保存了工作模式 ID（`mode_id`）的旧版检查点，系统在显式按需恢复检查点的边界执行升级：结合当前可用的模式定义与检查点内已保存的工作模式指令正文，还原出完整的工作模式定义快照。若旧检查点缺失原工作模式指令，或既有工作流所处的阶段节点无法与当前模式状态图安全对应，则完整保留原检查点数据并报告恢复错误，严禁静默重置对话历史或工作流状态。该快照升级在激活会话所有者之前，由该会话唯一的历史写入器在事务内比对原检查点并立即落盘持久化，无需等待下一轮模型执行或应用退出保存，且升级过程不改动历史保存水位、对话正文或工作流当前阶段。正常运行时仅消费完整的工作模式定义快照，不因删除全局配置、轮次进入终态或项目归档而删除会话历史数据。

## 17.13 分发模式选择与本地模型评价存储

会话创建时确定的子任务分发模式与偏好（`delegationMode`、`delegationPreference`），以及子会话创建时冻结的最终账号、模型标识、推理强度（`effort`）、智能体预设与派发来源，均作为权威会话事实随检查点持久化保存。全局会话目录与智能体目录仅投影这份权威事实的轻量只读摘要，不支持独立脱离检查点编辑；历史会话展示严格消费已保存事实，不根据当前最新的预设配置、全局默认设置或供应商模型别名事后补造。会话创建、冷恢复与目录事件发布全程保持同一身份事实，且不会为了渲染侧栏列表而批量激活全部子会话或扫描其历史对话正文。

既有 `v2` 目录与会话检查点通过显式版本迁移，为早期记录补入默认的“固定预设（`fixedProfile`）”模式与“平衡（`balanced`）”偏好；子会话的模型身份摘要仅从其检查点中已保存的冻结预设绑定提取。若早期数据缺少冻结绑定证据，则在目录摘要中如实保持为未知（`None`），后续用户显式打开或恢复该子会话时可从同源检查点事实中补齐，绝不凭空猜测历史模型。检查点迁移由该会话唯一的历史写入器在激活前通过事务原子提交，完整保留历史水位、对话正文、工作区绑定、模型路由及其他业务扩展，不批量激活冷会话，也不读取已隔离的旧大版本目录。

父智能体或用户对子会话发起的**显式关闭意图**由 Studio 的版本化会话扩展唯一拥有，并随子会话检查点可靠落盘；全局目录与 `studio.sqlite` 目录镜像仅承载派生的只读摘要，不构成第二个可独立写入的关闭事实源。宿主应用正常退出关停不会写入显式关闭意图，内核检查点处于 `Closed` 状态也不等同于子会话已被显式关闭封口。针对同一子会话的显式关闭、冷恢复、继续执行与任务评价操作在同一个会话所有者边界串行排序；对尚未驻留内存的冷子会话执行显式关闭时，按需恢复并更新其持久化检查点事实，不启动模型会话或工具实例。一旦子会话的显式关闭封口事实持久化成功，即便随后的物理资源回收或目录摘要发布中途失败，该子会话也绝不允许再次恢复执行；后续重试直接从已提交的检查点修复目录投影并继续完成剩余的物理资源回收，严禁以清空历史或撤销关闭标记的方式冒充回滚。由于轻量目录摘要本身不足以独自证明子会话未被封口，任何执行恢复请求均须在子会话当前检查点的准入边界完成核验。此外，子会话的显式关闭意图不等同于项目归档事实，不会扩大项目归档操作对只读目录与常驻内存状态的扫描边界。

既有 `v2` 检查点、目录文件与 SQLite 镜像在各自的版本化迁移边界平滑转换，保留其余运行状态、历史水位、冻结路由与扩展版本号不变。早期记录若无显式关闭意图扩展，则保持原有的可恢复语义，不从内核 `Closed` 状态、项目归档标记或工作树租约状态反向猜测关闭意图；若迁移遇到未知格式或自相矛盾的事实，则明确报错并保留现场。只读目录列表查询不会为了补齐关闭意图摘要而激活全部子会话；按需读取与执行恢复共享同一套解码契约（子会话关闭意图与物理工作树处置的行为边界见 [12](./12-collaboration.md)）。

子任务完成后的**本地模型评价（task evaluation）**归属于产品数据库 `studio/v2/studio.sqlite` 的独立业务领域，既不属于全局 `config.toml`、在线模型目录缓存或 `calls.sqlite` 调试统计，也不属于单个会话的 `history.sqlite`。版本化的评价表以子会话 ID（`child_thread_id`）为唯一主键，完整持久化父子会话归属、冻结的账号/模型/推理强度、智能体预设、派发策略、被评价的最终轮次 ID、评价版本号（`revision`）、任务结果判定、分项评分、简短评语以及创建与更新时间戳。数据库按 `(account_id, model_id, updated_at DESC, child_thread_id DESC)` 建立复合索引：按账号模型查询评价详情时仅读取最近 `10` 条记录，评分摘要也仅基于该有界窗口计算，不将全表历史评语加载至内存（评分维度与父子授权契约见 [12](./12-collaboration.md)）。

本地评价的首次写入与针对同一子会话的评价修订由单一领域所有者串行裁决并在 SQLite 事务中原子落盘，唯有事务提交成功后才向外发布更新回执；依靠唯一子会话身份与评价版本号（`revision`），即便网络或 IPC 响应丢失，调用方重试仍可保持严格幂等。写入失败或被取消时绝不发布虚假成功回执或写入部分字段，应用关闭流程亦会等待在途评价写入事务收束。本地评价记录独立持久化，不会因滚动调试日志过期淘汰、会话归档或对应模型账号被禁用而丢失；查询历史评价记录亦无需激活对应的子会话。新增评价表结构通过 `studio.sqlite` 的版本化事务迁移创建，不重建或清空既有 `v2` 产品数据。
