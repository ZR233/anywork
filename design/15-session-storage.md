# 15 - 会话状态、历史与调用记录

本文是会话（`Thread`）当前状态导出、对话历史写入、调用诊断记录、保存屏障与冷恢复的唯一权威源；Studio 数据目录布局与迁移协调见 [17](./17-studio-storage.md)，内核契约见 [16](./16-core-contracts.md)。

时间线内容读取统一采用 [26](./26-timeline-content.md) 的“游标分页 + 尾部订阅 + 按身份详情读取”，不保留几何滑窗实现。当前格式的正常读写与旧 `v2` 数据的按需迁移严格分离（见 [17](./17-studio-storage.md)）；旧大版本会话数据不迁入 `v2/`，账号配置单独安全迁移。文档声明不是运行证据，模拟结果也不证明真实账号兼容性。

## 15.1 事实源分离

同一会话的持久化数据划分为三个职责正交、互不替代的事实源：

| 数据类别 | 活动事实源 | 持久化载体 | 读取路径 |
| --- | --- | --- | --- |
| 当前执行状态、有效上下文、待处理输入与待决交互 | 会话所有者（`Thread` owner） | 会话 SQLite 检查点（checkpoint） | 会话激活时完整读取一次 |
| 已提交轮次（`Turn`）、时间线条目（`Item`）、任务身份与完整工具交付 | 历史写入任务（history writer） | `history.sqlite` | 内核 `Session` 合并历史存储、内存尾部与未保存事实；任务按身份读取 |
| 模型与工具调试诊断记录 | 可丢弃观察投影 | 滚动 JSONL 日志与有界索引库 | 独立分页查询；记录缺失不代表零消耗 |

会话的用量摘要（`usage_summary`）是当前状态中的绝对累计摘要，随对话历史与检查点在同一事务中保存，不替代可丢弃的逐次调用诊断库。通用 SQLite 存储（`ColdStore`）在提交状态副作用（`effect`）后、捕获检查点前折叠内核已知的模型用量；Studio 的可靠写入器继续依据已保存的调用回执补充价格、耗时与辅助调用统计。用量折叠按状态副作用序号幂等推进；若部分词元（token）统计缺失或计数溢出，既不伪造完整总量，也不覆盖最近一次已知的上下文窗口用量，而是显式标记统计不完整。通用 SQLite 存储执行显式版本升级时，会在独占数据库租约下按序重读旧版本已保存的状态副作用，将缺失的用量累计补入各会话检查点，并与版本标记在同一事务中提交。若旧状态副作用缺少模型绑定，则保留未知模型与容量；迁移过程中若遇到序号缺口或损坏记录，必须立即失败并完整保留原数据库。

累计摘要中的有效上下文窗口、模型最大窗口与最终自动压缩阈值由同一次主模型请求绑定整体替换，并随检查点持久化；辅助计费与上下文压缩回执不会覆盖这组主请求绑定事实。既有 `v2` 记录在持久化解码边界将缺失的新增可选字段解释为“未知”，完整保留原有的词元数、费用、历史与已知窗口，不根据当前配置倒推历史阈值或模型最大能力。该字段扩展无需清空、重建数据库或重放历史，在下一次主请求准入后即按新绑定自动更新。

会话执行所有者不驻留完整可靠历史；完成 Session 管理不可变 pending 与统一查询，Runtime 管理当前活动/执行索引，查询不排队等待模型命令。首屏由事件 Baseline 提供完成小页；冷历史不激活模型、工具或重放事务日志。

“运行时不驻留完整历史”不代表丢弃模型请求上下文。下一次模型调用所需的上下文快照（`ContextSnapshot`）、账号私有续接状态（`continuation`）、当前运行时事实与未完成任务状态仍由会话所有者持有；面向界面展示与审计的对话历史则拥有独立生命周期。模型上下文可执行压缩、替换或裁剪，但已提交的对话历史不会因此被删除。

内存仅保留各 owner 必要的活动缓冲、可靠待保存批次、完成 pending、有限未交付批次和有界查询结果；共享不可变引用不等于第二正文事实源。提交后才释放可靠责任，页面离开不丢未保存事实，不以 recent cache 支撑正确性。

### 本地优先的原子完成时间线

Session 统一读取不可变完成 pending 与已持久化历史，完成发布后可立即分页/读详情，不等待数据库。Runtime 拥有可变执行事实、活动正文和内部 ordinal/revision，不能把其终态后的可靠修订当作可变完成历史。完成发布顺序、epoch、读写交接和预算的唯一契约见 [26](./26-timeline-content.md)。

同一 PreparedEffect 由产品投影准备一次，完成批次先原子可查询，再由现有 writer 与执行事实、checkpoint、身份/回执同事务保存。保存确认仅推进连续提交前缀并回收 pending，不更改完成载荷或触发历史更新；保存状态在独立当前态报告。发送成功只代表受理，不代表已落盘或模型执行，不能由 Flutter 合成第二条输入。

计量与完成内容沿同一次准备共享交接：PreparedAccounting 只从该效应的权威回执提取一次，实时累计与可靠事务消费同一不可变材料，不在发布重试或保存回合重新解码。可靠提交同时保存完成原子与计量/检查点，成功后返回已提交的轻量计量结果，并只确认该批次实际持久化的完成前缀；不回读完整检查点、不恢复旧可变内容确认或预览清理路径。调用诊断没有全效应保存义务，其观察退役不撤销可靠历史状态的逐 incarnation 报告、共享故障恢复或真实排空责任。

稳定完成身份不依赖展示组或晚到 Turn 绑定。当前实时文本、工具进度、计时和待决交互经各域事件交付，不进入历史；后台工具与模型请求各自按真实生命周期收束。模型上下文、压缩、UI 阅读意图和完成历史互不拥有对方的数据，压缩不删除完成项。

冷历史采用同一注册 Session 与显式存储准备，不激活模型/工具或执行所有者。历史读取独立 feed/credit，关闭观察不关闭 Session、执行或 writer。

### 展示缓存与可靠准入的预算边界

内存与资源预算按事实所有者分层核算，不将不同层级的“有界”合并为单一笼统上限：

| 预算层级 | 计量对象与所有者 | 释放与超限处理语义 |
| --- | --- | --- |
| 核心完成 pending 与读取 | Session 持有尚未可靠交接的不可变完成引用，查询捕获有界候选 | 提交后才回收 pending；订阅关闭不能释放未交接事实，缓存不承担正确性 |
| 运行时与内核可靠准入 | 历史保存通道、未入队批次、已准备正文、实时投影与报告累积器、在途实际输出 | 按 §15.3 的会话级与进程级字节额度计费并施加背压；达到阈值时暂停新工作准入，绝不丢弃既成事实 |
| 客户端资源与显示选择 | SDK 当前态与有限未交付批次、独立查询 scope、草稿/附件/操作，Flutter 已加载原子引用 | retiring/unresolved 仍计费，close/join 后释放；SDK 不保留历史镜像 |

客户端 ResourceBudget 只代表资源数量准入，不是 heap/RSS 字节证明。已加载原子随翻页增长，详情/图片/在途批次另有预算；切会话或呈现 owner 真正释放时回收展示集合，单纯回到最新不重建历史。关闭未完成保留所有者与许可，禁止提前归还后无界打开。

本节旨在划清各层预算责任边界，不依据静态常量或资源计数宣称内存峰值已受控。全文展开、长轮次、多会话并发、慢速观察者、关闭失败及大型附件预览的真实内存表现另行通过压力测试证据记录，验证分层见 [24](./24-testing.md)。客户端不持有可靠历史权威，不得通过清空数据库、默认值覆盖或删除 `v2` 数据来掩盖展示层预算问题。

## 15.2 内核状态与输出事实

`pl-core` 的会话核心类型划分为三类：

- `ThreadSnapshot`：当前内存执行状态快照，仅包含恢复当前逻辑状态及供活动观察者派生视图所需的事实。
- `ThreadCheckpoint`：可序列化的当前状态 DTO，包含结构版本（schema）、会话身份、状态版本号（`state_revision`）、历史水位栅栏（`history_fence`）、当前模型上下文、未完成输入/交互/任务/交付、当前业务扩展以及子会话引用。
- `ThreadEffectBatch`：单次原子状态提交生成的不可变输出事实批次，供实时投影、历史写入器、调用诊断记录器与产品观察者消费；它不是重放恢复日志，完成持久化落盘后不再由会话所有者驻留。

会话检查点保存以下内容：

- 当前轮次（`Turn`）与尝试（`attempt`）的逻辑状态；
- 当前有效模型上下文、上下文压缩结果、运行时事实及可持久化的模型私有状态；
- 尚未消费的输入、待决交互与权限请求、未结束的后台任务及尚未交付的工具结果；
- 当前业务扩展、模型路由、工作流状态、资源引用与子会话 ID 列表；
- 当前状态版本号及其依赖的历史水位栅栏（`history_fence`）。

会话检查点不保存以下内容：

- 已结束的历史尝试、已完成轮次、已交付给模型的工具结果与已解决的交互记录；
- 历次模型请求的完整旧输入上下文及上下文替换前的历史内容；
- 完整的状态副作用日志、GUI 展示条目、运行时句柄、同步锁、异步任务（future）或取消令牌。

大型正文与二进制数据通过稳定的内容寻址资源引用（blob reference）保存；不透明载荷保留其 `format`、`version` 与原始 UTF-8 正文，不在检查点边界预先解析再重新编码。

### 瞬态副作用窗口与持久化权威

会话所有者维护一个瞬态副作用窗口（`effect window`），向活动观察者提供“最近已提交但尚未完成持久化确认”的 `ThreadEffectBatch`。该窗口仅保留尚未越过固定写入水位的批次：任一提交一旦获得持久化确认（durable）即从窗口释放，不充当第二份历史缓存。副作用窗口不序列化进会话 SQLite 检查点，也不单独执行字节编码计量——单次提交仅克隆一个 `Arc` 指针，状态发布不会阻塞在完整正文序列化上，窗口亦不设置按批次数量的淘汰上限。

释放副作用窗口不会丢失尚待投影的事实，因为持久化水位只能推进到**已被该会话唯一的实时投影所有者接管并移交可靠保存通道**的提交序号：会话所有者将不可变的 `ThreadWrite` 放入可靠保存通道后，实时投影所有者消费同一份受理事实、执行唯一一次投影并将展示内容发布到共享 `Session`，历史写入器则仅消费这份已完成投影准备的批次并确认条目身份、内容版本与保存水位。历史写入器自身不执行投影：当队首批次尚未被投影所有者接管时，写入器既不落盘也不推进持久化水位。因此，“某条状态副作用已从瞬态窗口释放”必然蕴含“该状态副作用已完成实时投影并发布至会话视图”。尚未被投影接管的批次仍按原始序号留在可靠保存通道中，其编码字节数纳入既存の会话级与进程级字节预算（`pending_thread_bytes`、`process_bytes`）核算；触及预算上限时暂停新模型与工具准入，绝不静默丢弃。慢速 GUI 订阅者不在该背压路径上：可靠保存通道的消费者是会话自身的后台观察任务，而非前端界面。

接管与准入的时序交错由投影所有者自行收敛：会话初始化提交在遭遇存储背压时可能先暂存于所有者内部，晚于观察任务安装才进入可靠通道；此类提交的序号早于投影播种基线，不会被当作实时增量帧重复播放。投影所有者因此监听可靠通道自身的水位变化信号重新执行接管，补齐“序号更早但此前尚未入队移交”的提交；其等待的持久化目标也是自身实际移交的**接管票据**（已移交批次的最大提交序号），而非绝对提交水位——本进程新激活的会话拥有全新的可靠通道，其早先提交在上一进程生命周期内早已落盘，若按绝对提交水位等待则会陷入无限期等待。接管票据为 `0` 表示当前通道不存在待确认的交接批次。

由此，会话 SQLite 检查点无需内嵌历史对话正文：已结束轮次、工具交付正文与已解决交互仅保存在 `history.sqlite` 中，检查点仅记录其对应的持久化水位栅栏。

投影移交与终态对外通知的责任亦须分开：批次已经 prepared 或 durable，不代表原父报告发布及审查裁决已接管。Studio 在原投影与既有受管 operation 之间保持连续、可取消等待的责任移交，保存故障或登记所需容量不足后仍能按真实恢复条件自动接续；不能依赖重投影同一批次、公开查询或关闭扫描补洞。该产品交付操作不负责重新生成内容投影，可按原身份读取已保存消息与成功工具交付；正常内容投影的热路径不因此增加历史回读。具体所有权、预算与恢复边界见 [17.15](./17-studio-storage.md#1715-审查结论与独立投递异常的可靠交付)。

产品观察任务直接消费内存中的状态副作用来投影计费、目录摘要与轮次终态事实，不逐批刷盘等待：每条状态副作用由该会话唯一的实时投影所有者投影一次，终态报告与目录摘要直接取自这份可靠内存投影结果，从而使跨越多次状态提交的长轮次能够完整携带此前已提交的正文，而非仅包含收束轮次的最后一条提交。终态报告仅纳入**已正式提交**的条目身份：流式预览仅属界面展示事实，未经提交收束的预览正文不进入父会话报告或目录摘要；同一 `(item_id, part_id)` 的正式提交条目直接原地替换流式预览，不追加第二条记录。内存投影无法证明自身覆盖该轮次自起点以来全部条目时，才在投影安装或无常驻投影的冷恢复边界按 `items_for_turn` 重建有界切片，并遵守必要的持久化屏障。常规正文变化命中当前投影，不按 token 回读 SQL；已回收身份被迟到可靠事实重新引用时，允许按该事实的精确身份读取现有 `history_items` 和完成集合，恢复原 ordinal、revision 与已完成判定，不扫描整段历史、不等待 flush、不重新封口。内存投影从轮次起点连续折叠时，终态报告与目录摘要完全由内存生成。

实时投影为生成终态报告维护**有界的报告累积器**：按条目身份归并的终态文本、有数量上限的可见旁白（`commentary`）兜底摘要、最新工具调用条目，以及当前仍需的已提交身份。同一条目更高内容版本原地替换，不随词元或修订次数膨胀。可变正文只在仍可能被后续提交引用时驻留；其余已完成正文归完成 `Session` 的有界 pending 与磁盘历史库，不存在第二份尾部历史缓存。可选的历史位置元数据最多保留 `LIVE_ITEM_WINDOW` 条，当前运行中轮次、尝试、输入、工具交付实际仍引用的身份和未持久化事实不随窗口淘汰；这些必须保留的居民同样受可靠字节预算约束。终态记忆和已封口身份只保留相同的有界职责范围，不以整个进程或会话累计身份数为上限。脱离活跃引用且已可靠保存后回收，迟到预览先校验当前来源生命周期，不能复活已结束成员；迟到可靠事实在精确身份冷读边界恢复。报告、索引、终态记忆和驻留内容的实际内存均计入所属预算（见 §15.3），保存完成后无活跃义务的身份必须使预算回落。

瞬态副作用窗口的释放同样无需等待显式 `flush` 命令：存储后端在每次压力报告中附带类型化的已落盘水位（`StoragePressure::durable_sequence`，`0` 表示尚无已确认提交），会话所有者在每次状态提交后的内存安全边界（`admit_cold` / `refresh_storage_pressure`）将其折入自身的 `durable_sequence` 并立即释放已被覆盖的窗口批次，避免正常保存的会话将整段对话的历史批次积压至最后一次显式保存。会话所有者外层命令队列中的 `Flush` 仅在所有者空闲时处理，而正在执行的轮次会使所有者停留在轮次异步任务内部；正常观察路径不依赖外层 `Flush`，从而避免将实时产品状态更新拖延至整轮执行结束。

原始状态副作用流的慢速消费者仍可能收到滞后通知（`lagged`），但完成 `Session` 的客户端无需自行拼接查询与流缺口：按实际接纳的完成 cursor 连续补发不可变批次，epoch 变化下发完成窗口 `Reset`，不再发送旧内容修订 `Patch`。可靠保存队列的容量背压仅暂停新模型与新工具准入；已产出的执行结果、取消状态、会话关闭与交互收束仍由可靠保存集合接管落盘。

## 15.3 副作用发布与背压控制

会话所有者在串行提交边界一次性完成以下动作：

1. 校验候选状态合法性；
2. 分配单调递增的 `state_revision` 与 `write_seq`；
3. 发布更新后的当前状态快照（`ThreadSnapshot`）；
4. 将同一 `ThreadEffectBatch` 提交至可靠历史保存通道，调用诊断统计则作为独立的可丢弃观察旁路分发；
5. 向实时状态订阅通道广播增量事件。

状态提交不阻塞等待磁盘 I/O。每会话的 `HistoryChannel` 由会话管理器强引用持有，生命周期独立于后台写入任务与 GUI 订阅；当非阻塞入队（`try_publish`）因通道满载返回失败时，原批次返还给会话所有者暂存并在安全间隙重试，串行发布机制保证所有者侧最多暂存一个未入队批次。历史写入器仅借用队首批次，唯有在 SQLite 历史事务提交成功后方可按 `write_seq` 确认并释放队首元素；写入任务异常退出不会转移或丢弃批次所有权。已执行完成的工具结果、取消事实、会话关闭与交互收束始终允许进入保存队列，禁止为满足内存阈值而丢弃既成事实。

历史写入器仅消费唯一投影准备的同一不可变批次，未完成投影不推进保存水位。事务提交后释放该批次可靠预算并确认其完成前缀，不回读或再次发布正文。执行事实的版本化修复仍在执行表内，不能修改冻结完成项。

历史保存通道同时实施三项配额限制：待保存批次数量上限为 `4096` 批；每会话可靠内存上限为 `64 MiB`（涵盖队列中的状态副作用、已准备投影批次、实时投影表与报告累积器、以及在途实际输出）；全进程可靠内存上限为 `256 MiB`（仅汇总各会话队列中状态副作用的编码字节数与在途实际输出——已准备投影批次与实时投影表持有的是队列状态副作用已计费的同一份正文引用，若重复计入进程总额会导致单份正文被双倍计费，使进程上限在真实占用的半数处提前触发）。会话所有者侧暂存的未入队批次由内核在安全间隙同时计入会话级与进程级总量后再判定阈值，确保“已生成但尚未入队”的事实同样处于预算约束之下。单次模型或工具操作（operation）的可靠输出上限为 `16 MiB`。当会话级或进程级占用任一达到 `64 MiB` / `256 MiB` 上限时，内核立即进入准入暂停状态，唯有当两者分别回落至 `32 MiB` / `128 MiB` 低水位及以下时才解除阈值暂停；任一指标达到 `32 MiB` / `128 MiB` 即发布存储压力警告。运行时通道的容量拒绝与内核的高低水位门控共同构成同一可靠保存责任的边界，不同于展示层推测性缓存的淘汰机制。模型与工具调用在启动前先登记有界输出额度，实际产出字节在接收前原子计费；处于空闲等待的调用不会按假设的最大输出额度预先占满进程预算。任何未知或无界输出源必须先补齐可中止的上限契约后方可接入。

单次模型调用的可靠输出共享**同一总额度域**：回复正文、推理内容（`reasoning`）与工具调用参数合计受 `MAX_OUTPUT_BYTES` 约束。`ToolInputStarted`、`ToolInputDelta`、`ToolInputCompleted` 与 `ToolCallReady` 事件在将参数字节复制进权威累积器**之前**，先按各调用身份的已计费高水位执行差额计费：等长的权威完成帧（`completed`）不重复计费，替换后继续追加的增量也不会漏计，从而防止单个模型响应同时无界堆积正文与工具参数。若工具参数在 `ToolInputCompleted` 之后迟到或传输失败，仅保留已接收的不完整回执（partial receipt）供诊断，**不执行**参数未闭合的工具调用，也不拼接不完整的 JSON；若可靠队列已满，则以类型化 `QueueFull` 错误拒绝新准入。

单次命令执行的标准输出与标准错误（`stdout`/`stderr`）合流捕获同样受独立配额约束：工具后端通过 `capture_limit_bytes` 声明单命令落盘上限（未显式声明时采用默认的 `MAX_CAPTURE_BYTES`，与内核单操作输出上限同量级；特定宿主环境可显式声明更宽的上限），并在**接纳输出块之前**通过 `capture_storage_cost` 按真实磁盘写入成本计费——同时写入合流文件与分流文件的后端必须按双倍落盘字节计费，防止配额仅约束其中一路文件。一旦触及捕获上限或遭遇磁盘写入/刷盘失败，后端立即终止该命令的整棵进程树并等待进程真实退出，**完整保留**已落盘部分与有界观察视图，绝不静默截断输出后谎报命令执行成功。上述两类终止按错误类别严格区分：触及配额上限属于预期内的容量终止（返回类型化 `OutputLimitExceeded`，携带配额上限、已保留字节数与被拒字节数），必须与 32 KiB 级的模型上下文截断、命令超时及非零退出码明确区分，且**不**触发可靠输出存储故障；而磁盘无法继续写入则属于存储故障。标准输出与标准错误两路流各自仅按读取顺序将数据块（chunk）接纳进同一个有界有序修复计划并唤醒唯一写入任务，读取端不阻塞等待磁盘 I/O；写入任务与命令操作同生命周期，唯有当它将全部已接纳字节落盘、或将未落盘块作为有序修复计划完整保留后，命令操作才发布终态（操作终态不早于写入任务收束）。首次追加写入失败后不再接纳新数据块，但此前已接纳排队的双流数据块全部按序保留且不被后续错误覆盖；故障重放以存储后端确认的已提交文件长度为截断基准，禁止使用内存分片长度冒充文件偏移。当磁盘写入失败时，生产者通过类型化的 `OutputStorageFault` 错误在会话所有者现有的故障代次（`fault_generation`）与恢复门控下立即暂停新准入，后续后台写入器的自动重试不会自行解除该门控；内核仅读取该类型化错误类别，绝不解析错误诊断文本。受控字节归档遵循相同原则：`retain` 按有界分块流式复制，超出资源上限时直接返回类型化失败，而非先将无界大文件读入内存或创建临时磁盘副本；本地归档 I/O 失败映射为类型化存储故障，而远端 SSH **传输**失败仍归类为普通工具执行错误。

两类输出停滞具有不同的恢复条件：纯可靠内存预算超限仅保留已接收片段并记录可停止事实，待落盘屏障满足、水位回落后即可继续；而生产者的**可靠输出存储故障**（捕获文件写入/刷盘失败、归档文件未落盘）则必须附带一份 `OutputRetryObligation`——该义务按稳定身份重新保存**同一份**已接收字节（不重新执行外部命令，也不构造残缺结果），唯有显式重试成功且同一 `fault_generation` 的保存目标与历史水位栅栏（`fence`）全部落盘后，`canResume` 方可置为真。健康的会话历史写入器将该次调用的失败状态写入 `history.sqlite` **不能**证明失败的外部捕获归档已修复落盘，因而不能视为故障已恢复；重试过程保持幂等，不丢失也不重复追加已接收内容。生产者在捕获写入失败的当刻即通过运行中调用的可靠通道上报类型化故障，使并发的模型与工具准入立即被阻断，无需等到 `execute` 函数返回。命令捕获配额仅约束命令输出捕获路径，不对通用的 `retain_file` / `retain_bytes`（如用户附件、文件导入等资源）施加额外限制；远端命令捕获在**传输任何字节之前**即按已知捕获上限先行校验拒绝。当显式重试修复成功后，补充生成的持久化资源引用通过 `ThreadEffectBatch.delivery_repairs` 按**原始调用身份**随同一状态副作用发布：实时投影与历史写入器将该资源引用补入对应已提交工具结果的资源元数据，并同步补齐 `history_tool_tasks` 表中交付事实的资源引用，确保界面实时视图与冷恢复看到完全一致的完整输出；条目的正文、排序序号、终态状态与身份均保持不变，既不重新运行命令，也不重复触发结果交付。该修复机制不依赖任何有界内存观察窗口：若目标条目身份仍在实时窗口内，唯一投影所有者直接在内存中原地补齐；若条目身份已滑出实时窗口，同一投影所有者先按原始调用身份从历史库读回**已提交**的正文，折入自身状态表完成补充后再发布交付，确保权威条目及其内容版本始终由该唯一投影所有者决定，而历史写入器仅执行纯保存确认（仅按原始调用身份补齐持久化交付事实，不自行发明条目内容版本，也不回读正在写入的状态副作用正文）。因此，内存窗口淘汰不会将已提交身份误判为缺口，观察窗口大小也不会影响可靠保存的成立。

保存故障、队列满载、写入器不可用以及存在待写记录却长期无进展，均作为持续的类型化状态维护：存储后端将**无需解析错误文本**即可确定的类型化故障类别（`queueFull`、`writeFailed`、`writerUnavailable`、`noProgress`、`checkpointFailed`、`blobFailed`）连同故障代次（`fault_generation`）、已接纳水位（`accepted`）与已落盘水位（`durable`）一并写入压力报告，会话所有者将其镜像至自身存储状态，再经独立的 `watch` 通道与 `ThreadStorageState` 通知 GUI。

短暂背压与硬存储故障具有截然不同的收束语义。队列或字节预算短暂触顶仅产生背压：会话所有者在安全间隙等待水位回落后自动恢复执行，不改变持久化事实。而持久化保存真正失败则会锁定新模型与新工具准入（内核置 `resume_required` 为真，协议层映射为 `ThreadStorageState::resume_required`）：已在途的执行结果在预留预算内收束，若预算耗尽无法继续接纳输出则取消该在途操作并保留已产出内容，随后停止开启任何新的模型或工具工作。故障恢复拆分为两个显式动作：

1. `retryThreadHistory(thread_id, fault_generation)`：仅重试底层持久化保存，并等待该故障代次固定的保存目标落盘确认；
2. `resumeThreadHistory(thread_id, fault_generation)`：在会话所有者重新核验故障代次匹配、硬故障已消除、所有已发布批次均已移交保存通道、**且故障发生时固定的持久化栅栏（durable fence）已真实落盘**后，方才解除准入锁定。

故障发生当刻，会话所有者即根据自身已发布的事实固定本次恢复必须到达的持久化栅栏（取已移交的最新提交序号与存储通道尚未接管的队首批次序号中的较大者），该栅栏在当前故障代次解除前保持固定；存储后端仅仅“接收了批次”或“当前不再上报错误”均不足以解除准入锁定，栅栏尚未落盘时的继续请求一律以类型化错误（`ThreadError::StorageRecoveryPending`）立即拒绝，不在调用内部无界阻塞等待，以便调用方先执行保存重试再来确认继续。当故障代次由存储后端命名时，会话所有者还要求**该后端自身核验确认**的已恢复代次（压力报告中的 `recovered_generation`）恰好等于当前故障代次，否则以类型化错误（`ThreadError::StorageRecoveryUnverified`）拒绝——旧代次写入任务的成功不能为新发生的故障背书。显式继续命令通过会话所有者的**有界邮箱（mailbox）**投递，因此当轮次暂停在存储安全间隙、仅轮询邮箱时同样可达，无需经过仅在所有者空闲时才被轮询的外层命令队列。处于空闲状态的会话所有者同样无需等待下一条外部命令：存储后端的 `watch` 通道是其事件循环（`select`）中的一等唤醒源，一旦底层恢复完成即可立即重算并发布就绪状态，而准入锁定本身仍唯有通过显式继续命令方可解除。若传入的故障代次过期、仍存在未移交批次或内存压力尚未消退，继续请求均会被明确拒绝。检查点或二进制资源（blob）保存失败同样触发准入暂停；调用诊断统计写入失败则不影响执行准入，也不纳入可靠保存屏障。

#### 在途输出的可靠计费

模型流式回复累积器与工具子进程输出在正式提交前同样占用真实进程内存。可靠存储后端通过 `reserve_operation_output` 登记单次操作的有界配额，通过 `charge_operation_output` 在生产者接收每个流式增量前原子核对并记账，并在完成可靠交接后通过 `release_operation_output` 释放剩余配额。登记配额本身不预扣字节预算：处于等待响应状态的模型或工具调用在尚未产出任何字节时，不会以其 `16 MiB` 的理论上限阻塞其他并发操作。当进程实际字节预算耗尽时，新操作进入等待；当在途流式增量因预算不足无法记账时，立即拒绝新片段、保留已接收部分，并沿既有的类型化故障与显式恢复流程收束，禁止超预算无界缓冲。

每个在途操作分别记录配额上限、已接收累计字节数以及已转移给可靠状态副作用的字节数。重复上报相同的累计值不会重复扣费；后续增量仅按累计值之差记账，已转移部分不再重复收费。`ThreadWrite::output_claim` 指明唯一生产者身份，状态副作用入队时直接接管该操作尚未转移的实际已计费字节，序列化编码产生的额外字节开销则另行申请余量；无操作归属的普通状态提交不得借用其他在途操作的预留余额。计费核对与归属转移在同一临界区内原子完成：批次提交落盘后释放状态副作用持有的字节额度，操作结束时仅释放仍归属该操作持有的未转移部分，确保重试、取消与迟到的重复释放既不会泄漏额度，也不会重复扣减。

增量计费被拒绝的当刻即通过 `OutputRefusal` 通知会话所有者；所有者立即锁存 `QueueFull`、故障代次与 `resume_required` 状态，无需等到耗时操作返回后才向界面暴露故障。未提交的执行结果或未入队的暂存批次继续持有其已计费字节额度，直至完成可靠交接。单操作配额上限与当前实际内存占用是两个独立指标，界面存储压力展示仅依据实际字节占用与准入状态。

在途计费表按操作身份维护单条记录，表项数量严格等于当前并发操作数，不随对话历史增长；延迟释放集合同样仅随并发操作数有界增长，并在保存队列排空时清空。

**非流式原子结果的计费边界**：不主动上报流式进度（`progress`）的工具终态输出，以及无流式进度的模型一次性大响应，不经过上述流式增量计费路径。它们作为**原子结果**直接进入常规状态副作用准入流程：若当前预算余量足以容纳则直接入队；若余量不足则触发类型化 `QueueFull`，完整保留该原子结果（作为未提交完成体或所有者暂存批次）并计入所属会话的保留体预算，同时将会话置为暂停等待显式继续，绝不截断已完成的结果。因此，输出可靠性语义不依赖生产者是否调用 `progress`：流式片段在接收写入前按配额拦截，而一次性原子结果则要么完整接纳、要么令会话携带完整结果安全暂停。

实时事件通道是有界观察通道，并非可靠重放日志。内核尾部订阅允许慢速消费者从有界最新状态重建基线，无需 GUI 重新播放词元流或自行查询数据库拼接；底层状态副作用观察若出现序号缺口，统一由内核结合有序历史存储与未保存内存引用平滑恢复，不向会话所有者索要已释放的历史状态副作用。

需要同时更新历史与调用队列的保存状态报告，应原子采用本会话与同期调用队列的绝对观察，再生成一次进程级压力快照，不先发布缺少本会话新状态的中间聚合。全局调用状态仍由原 CallsStore 提供，实际采样、变化判断与接纳必须处于同一有序边界；入口消费原来源能力，不接纳调用方提前捕获、可能晚到的无序快照。独立队列查询及产品事件更新遵循同一边界，不能先比较、稍后再无条件覆盖较新状态。

仅观察可靠历史变化的 incarnation 报告只更新自身历史义务，沿用协调器已接纳的调用状态，不重新查询或发布 calls。合并观察不改变各写入者 incarnation 的所有权、故障代次、未提交义务或排空等待条件；它不是逐事件日志，也不得借减少发布丢弃真实故障与水位变化。不为修复顺序另建调用状态镜像、修订账本或后台采集任务。

### 幂等回执与按身份读取条件

会话所有者的串行提交边界同时生成可持久化的幂等回执，确保重复命令在跨窗口、跨进程重启后仍返回一致结果，不会重放外部副作用：

- **用户输入回执**：`submitPrompt` 的稳定 `inputId` 以最小身份写入历史库的输入身份索引（`history_input_identities`），并与该次状态副作用的条目行及轮次行在同一 SQLite 事务中提交；重复提交优先查询该持久化索引并返回原始回执，不重复受理输入，也不重放历史。
- **继续控制回执**：无内容继续的操作身份就是其控制输入身份。继续点认领、输入事实、请求摘要、预期继续点与首次受理提交序号在同一提交写入输入身份索引，控制仍待处理时即可查询；后续已消费或已放弃状态取自既有输入事实，不新增可写操作状态。相同身份与内容返回原回执，不同内容拒绝，重复查询或重发不重新授权，也不解除其间发生的停止。已受理但回执尚未落盘期间的重复继续回答可重试的忙（`Busy`），内部等待标记不进入公开命令结果。
- **交互与权限回执**：终态交互与权限事实的 `(item_id, revision, digest, payload)` 与产生它的状态副作用在同一历史事务中写入 `history_fact_receipts`；重复提交决议（`resolve`）仅在回答内容与状态变更完全一致时返回同一回执，若载荷冲突则明确报错拒绝，不重复授予执行权限或重放状态副作用。
- **消息去重账本**：跨会话或后台消息按稳定 ID 幂等受理；已消费消息身份在内存中维护固定条数的有界账本，超出内存窗口的重复消息则由 `history_message_identities` 中已持久化的受理事实回答，使内存去重账本不会随对话历史无界增长。
- **审查结论与投递异常的事实复用**：审查授权保存在版本化的冻结工作区扩展中，结论及全文来自已提交 finish 工具交付；原父报告随真实终态副作用冻结并同事务保存，不依赖未来回送结果。回送异常经既有不透明应用扩展 CAS 形成独立真实副作用，其不可变消息原文沿同一投影/历史写入通道保存至事实回执，再可靠通知创建者，不后写定稿原报告、不伪造核心水位、不另建报告正文库或投递队列。扩展提交、在途副本及投影正文均纳入现有可靠预算。跨线程副作用须先确认原授权材料耐久，已有回执优先；冷恢复无可证明回执时保持未知而不首次发送。旧记录显式保全、不增权；产品路由见 [12](./12-collaboration.md)，原文、异常恢复及分别确认的关闭义务见 [17.15](./17-studio-storage.md#1715-审查结论与独立投递异常的可靠交付)。
- **任务与工具调用按身份读取权威**：后台任务状态与工具结果交付的持久化权威位于每会话的 `history.sqlite`。通过 `(thread_id, call_id)`（或 `task:{call_id}`）主键可直接读取任务身份与当前状态而无需加载大段正文；终态工具交付则按同一身份按需读取完整正文。可读性成立的前提是该事实已完成持久化落盘且归属于当前会话：对于非终态、跨会话或未知身份的查询，统一返回“无此事实”，调用方必须显式报告未找到，不得将其当作已完成结果或作为新任务重新受理。

通用 SQLite 存储后端在写入状态副作用的同一事务中维护 `(thread_id, task_id)` 任务身份索引、完整交付所在状态副作用的定位信息以及后续归档资源补充记录。任务元数据与资源引用附带完整性摘要；完整交付正文则仅保存在原始不可变状态副作用记录中，按索引定位单条读取，不复制第二份历史正文。遇到未知或过期任务身份时直接按索引未命中返回，禁止退化为全表分页扫描无关的状态副作用。数据库结构升级仅在显式离线迁移中按提交顺序有界回填索引，普通打开操作直接拒绝未完成升级的数据库；版本号更新、索引创建与数据回填在同一事务中原子完成。删除已停止的会话时同步清理其全部索引记录。

当会话所有者仍在内存中驻留时，重复命令可直接由瞬态副作用窗口中的最新提交回答；一旦对应批次完成落盘并滑出瞬态窗口，相同查询即无缝切换至上述历史身份索引、终态事实回执与按身份读取接口回答。两条路径语义严格一致，不会因释放内存窗口而改写终态或重放外部副作用。

控制输入沿用同一可靠准入与保存栅栏：受理不等待磁盘，但确定模型请求前必须先到达认领对应的固定持久化水位，等待期间不持有产品生命周期锁，也不通过等待自身外层刷新形成环。控制输入的分类只认类型化用途（`InputPurpose`），载荷格式与结构仅作校验；普通消息不得占用保留的控制格式，父消息同样在受理期被拒绝，控制载荷结构不接受未知字段。历史**不在读取期改写**：原始记录按写入当时的投影显示，运行时说明只在写入侧由类型化的继续控制产生（`ThreadRawItem.origin = runtimeControl`）。载荷形状不能单独证明来源，因此既不能据此改写历史，也不能据此授权执行；旧记录按普通消息解释，不猜测不存在的继续或控制事实。

## 15.4 当前状态的原子保存

每个会话由唯一的历史写入器（history writer）将该次提交的时间线条目、幂等身份索引、工具交付记录、累计用量统计、最新模型上下文与会话检查点在**同一个 SQLite 事务**中原子提交。唯有事务提交成功后，写入器才确认固定写入水位并释放可靠保存队列中的批次；若事务失败则完整保留原批次以供重试，从而在根源上消除“对话历史已落盘但检查点未更新”（或反之）的跨文件不一致窗口。

检查点仅保存最新的逻辑恢复状态。当前模型上下文按记录身份与顺序存储：普通上下文追加仅增量写入新增记录，上下文压缩或整体替换则在同一事务中更新当前有效集合并清理已失效成员。轻量检查点元数据不重复内嵌完整上下文正文。外部附件必须先完成二进制文件落盘栅栏（blob fence）后方可提交检查点引用；遇到未知格式、文件缺失或摘要损坏时一律按失败关闭（fail-closed）处理。

常驻内存的尝试记录（`attempt`）仅保留当前在途执行、最新可重试身份、上下文版本号及必要计量摘要。完整的模型请求体由当前在途调用持有，终态正文通过可靠状态副作用完成交接后即刻释放。当前轮次的工具调用身份去重账本独立于模型请求正文与上下文压缩生命周期，防止释放旧上下文快照后重复执行同一工具调用。显式重试仍要求目标为最新失败或取消的请求、当前上下文未发生变更且工具计划保持兼容；冷恢复过程不会自动触发模型调用或工具执行。

旧版 `v2` 的 TOML 检查点文件（`state.toml`）仅在按需激活的迁移边界读取：校验会话身份、结构版本、正文完整性及历史水位栅栏无误后，在 SQLite 事务中导入最新状态；完成回读校验后才回收已被替代的主备 TOML 文件及无引用的独立检查点正文。迁移过程支持中断重试，发生异常时完整保留源数据；正常读写路径不再读写 TOML 检查点，也不再保留上一版完整快照文件。

## 15.5 会话历史数据库

`pl-core::persistence::SqliteSessionStore` 用于保存通用的内核状态副作用（`ThreadEffectBatch`），与下文 Studio 产品层的每会话 `history.sqlite` 属于不同层级的存储适配器。采用前者的嵌入式宿主通过 `read_thread_effect` 与 `query_thread_effects` 接口，按会话身份与提交序号读取已持久化的状态副作用；内核负责校验存储信封完整性、会话归属与序号键。宿主仅将这些通用事实投影为自身的轮次、工具调用与审查记录，不直接读取内部 `session_entries` 表，不自行解码 `pl.resource.thread-commit.*` 存储键，也不从当前检查点反推已滑出内存窗口的历史。宿主对外提供的可见对话内容与长历史分页统一通过内核 `Session` 的内容读取接口访问；配置文件与业务领域状态则仍由产品宿主自行管理。

内核通用 SQLite 后端将状态副作用与其对应的当前状态检查点作为单次原子写入落盘：当一条 `ThreadWrite` 经队列受理后，写入器在同一事务中追加 `pl.resource.thread-commit.<sequence>` 状态副作用记录，并插入或更新（upsert）该会话的最新检查点行（位于内核内部 `thread_checkpoints` 表）。因此，持久化回执水位仅在两者同时落盘成功后才向前推进，绝不会出现引用了未落盘状态副作用的检查点。由于内核层不设会话级外部二进制资源根目录（blob root），内核检查点以裁剪后的全内联重启 DTO 格式保存：超出常规阈值的正文仍内联保存在存储信封中，而非替换为无法再次物化的外部引用，其序列化字节数与状态副作用一并计入写入器背压预算。宿主通过 `read_thread_checkpoint(thread_id)` 读取检查点，由内核统一校验存储信封与内容哈希、会话身份、检查点结构版本、`state_revision` 与 `state.commit_sequence` 的一致性、以及 `history_fence` 不超出状态版本，并通过同一类型化读取入口核验栅栏位置处的完整状态副作用及归属；宿主不直接查询 `thread_checkpoints` 表、内部存储键或原始信封。内核写入器重新打开时，从已校验的会话提交资源恢复各会话的已落盘水位；`Thread::resume` 保留检查点中的 `history_fence`，在挂载存储后端前要求该后端已确认至少达到同一水位，随后将其初始化为会话所有者的已接纳与已落盘基线水位。禁止将已恢复的会话状态挂载到缺失对应历史记录的存储后端，也无需为早已落盘的历史状态副作用重复等待写入。

嵌入式宿主在取得独占运行时所有权并完成一致性备份后，通过统一迁移入口持有数据库独占锁，按版本顺序依次执行结构升级：新增检查点表不改动既有状态副作用记录；后续版本升级按连续历史补齐累计用量，将旧版完整请求快照转换为轻量执行记录，并从完整历史补齐模型与工具身份去重账本。每步升级在独立事务中提交，中断后可从已提交版本继续；普通打开操作不自动触发格式转换或全库重建，且不开放绕过独占锁的单步迁移入口。

通用 SQLite 后端删除已停止的会话时，通过 `delete_session` 在独占数据库锁下于同一事务内删除该会话的检查点、当前资源与历史记录；若存在活跃写入器则拒绝删除，其他会话的数据不受影响。产品目录索引、物理工作树资源与用户工作区文件不属于该通用数据库删除操作，由宿主按自身的可恢复清理流程协调。

Studio 每会话的 history.sqlite 同时保存执行恢复事实与唯一完成读模型 timeline_records，不保存完整内核 effect 日志。物理布局和正式内容迁移归 [17](./17-studio-storage.md)。下列 history_items 等表是内部执行/恢复结构，不是公开 Timeline 分页协议；完成原子形状、预算和读取归 [26](./26-timeline-content.md)。

```sql
CREATE TABLE history_meta (
    id                INTEGER PRIMARY KEY CHECK (id = 1),
    schema_version    INTEGER NOT NULL,
    database_id       TEXT NOT NULL,
    thread_id         TEXT NOT NULL,
    applied_write_seq INTEGER NOT NULL
);

CREATE TABLE history_items (
    ordinal         INTEGER PRIMARY KEY,
    item_id         TEXT NOT NULL UNIQUE,
    turn_id         TEXT NOT NULL,
    kind            TEXT NOT NULL,
    revision        INTEGER NOT NULL,
    lifecycle       TEXT NOT NULL,
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL,
    payload         TEXT NOT NULL CHECK (json_valid(payload)),
    last_write_seq  INTEGER NOT NULL
);

CREATE INDEX history_items_by_turn               ON history_items(turn_id, ordinal);
CREATE INDEX history_items_by_kind_lifecycle     ON history_items(kind, lifecycle, ordinal);
CREATE INDEX history_terminal_turns_by_write_seq ON history_items(last_write_seq, ordinal)
    WHERE kind='turn' AND lifecycle='terminal';
CREATE INDEX history_items_by_kind               ON history_items(kind, ordinal);

-- 终态 Turn 首次提交时的 last_write_seq 作为终态通知身份，后续修订不得改写该序号。

CREATE TABLE history_turns (
    turn_id         TEXT PRIMARY KEY,
    first_ordinal   INTEGER NOT NULL,
    last_ordinal    INTEGER NOT NULL,
    revision        INTEGER NOT NULL,
    payload         TEXT NOT NULL CHECK (json_valid(payload)),
    last_write_seq  INTEGER NOT NULL
);

CREATE INDEX history_turns_by_last_ordinal ON history_turns(last_ordinal);

CREATE TABLE history_input_identities (  -- submitPrompt 跨重启幂等身份索引
    item_id        TEXT PRIMARY KEY,
    ordinal        INTEGER NOT NULL,
    revision       INTEGER NOT NULL,
    digest         TEXT NOT NULL,
    request_digest TEXT,
    payload        TEXT NOT NULL CHECK (json_valid(payload)),
    last_write_seq INTEGER NOT NULL
);

CREATE TABLE history_fact_receipts (     -- 交互、权限及产品可靠消息事实（与所属状态副作用同事务写入）
    item_id        TEXT NOT NULL,
    revision       INTEGER NOT NULL,
    kind           TEXT NOT NULL,
    digest         TEXT NOT NULL,
    payload        TEXT NOT NULL CHECK (json_valid(payload)),
    last_write_seq INTEGER NOT NULL,
    PRIMARY KEY(item_id, revision)
);

CREATE TABLE history_message_identities ( -- 已受理消息最小身份索引；digest 可空
    message_id     TEXT PRIMARY KEY,
    item_id        TEXT NOT NULL,
    sequence       INTEGER NOT NULL,
    digest         TEXT,
    last_write_seq INTEGER NOT NULL
);
```

`ordinal` 在条目首次创建时分配，后续完成次序不会改变该顺序号；`revision` 表示同一条目的内容修订版本，`last_write_seq` 表示持久化协调水位。条目更新必须满足以下不变式：

- 相同 `(item_id, revision)` 且内容逐字节相同时保持幂等；相同 `(item_id, revision)` 但内容不同则判定为版本冲突；
- 较低的旧 `revision` 不得覆盖较高的新 `revision`；
- 条目的所属会话、`turn_id`、`ordinal` 与 `kind` 一经写入不可更改；
- 已处于终态（`terminal`）的条目拒绝迟到的流式草稿或增量分片（`delta`）。

实时投影侧对第一条幂等性不变式负有直接保证责任：同一个 `(item_id, revision)` 产出的载荷必须**逐字节严格一致**。条目内容版本由实时投影自身的计数器维护（与状态副作用提交序号及保存水位无关），唯有当轮次绑定、正文内容、结构形态或终态形状发生实质变化时才递增 `revision`；若重复投影未改变上述实质内容，则必须沿用上一次交付的位置元数据与时间戳，将每次投影时的当前墙钟时间排除在“内容变化”之外，防止同一 `revision` 产出两份时间戳不同的载荷而触发保存冲突故障。

后台工具任务可在所属轮次已结束、且会话所有者已裁剪该轮模型尝试记录之后才完成并交付结果。此时结果状态副作用仍完整携带工具任务与交付事实；实时投影必须从已提交的同一 `tool` 条目回读原始调用身份、调用参数与所属 `turn_id` 后再更新其终态，既不能要求会话检查点永久保留已结束的模型尝试，也不得猜测或重新生成工具调用记录。实时视图优先从会话内存窗口读取该工具条目身份，滑出窗口时回读历史库；历史写入器按 `write_seq` 顺序保证先落盘工具调用再落盘工具结果。若内存窗口与历史库均未找到对应的已受理调用，则持久化保存明确失败并保留待保存结果以供恢复，绝不静默丢弃或将其当作新的工具调用插入。

`history_items.payload` 存储条目自身的 JSON 正文，表结构不设独立的 `payload_format` 或 `payload_version` 列：当需要保存无法按现有结构解释的原始载荷时，统一存为 `kind = 'raw'` 的条目，将其格式与版本随 `ThreadRawPayload` 封装在 `payload` JSON 内部（见 [16](./16-core-contracts.md)）。`history_meta` 中的 `thread_id`、`database_id` 与 `applied_write_seq` 共同构成游标与水位身份；`history_message_identities.digest` 允许为空，仅用于兼容历史迁移回填留下的“身份已知但原始正文不可验证”的记录（读取方对此按失败关闭处理）。

内核在接管用户输入或收到供应商原始展示条目时即刻分配顺序键（`ordinal`）；历史写入器直接消费已分配的顺序键，首帧界面渲染无需等待 SQLite 写事务完成。`watch` 通道可合并中间流式预览，但不得跳过原始条目的顺序键预留。流式增量（`delta`）仅更新内存组装缓冲与 GUI 视图，不写入 `history_items` 表，也不按固定时间间隔落盘中间草稿。成功、失败或取消等终态事实随同一 `ThreadEffectBatch` 受理，由该会话唯一的历史写入器写入对应条目的最终 `revision`；用户输入回执与消息身份回执仍与该状态副作用在同一事务中生效。存储层不持久化逐词元事件日志，且检查点更新必须严格等待历史写入器水位栅栏。

Runtime 执行顺序索引由现有 `HistoryChannel` 强持有并显式注入实时投影，不使用进程级强注册表。writer 替换复用同一活动 channel 的分配上界与未决预留；停止并真实汇合全部所有者后释放，冷重开从 `history_items` 最大执行 ordinal 恢复。同步原始展示预留显式携带真实 attempt 身份，不解析 item ID 推断生命周期。索引只保留活跃来源、仍被引用或待保存的身份；事务确认和来源退役共同触发回收，保存失败不得提前丢失预留。持久化身份重新引用从原事实恢复顺序，不新分配；可丢弃的未物化预览预留在来源结束后释放，但标量分配上界不回退。索引居民计入线程可靠预算，不能靠取消计费掩盖增长。

父智能体或跨会话输入受理后生成冻结的可见输入事实；尚未知的消费 Turn 不在之后补写历史。收件箱和内部 history_items 保留正文/身份与执行 ordinal/revision，消费绑定可更新内部事实但不得修改完成原子。恢复按原身份幂等，不重新发布同一可见输入。

实时投影初始化时的历史读取范围同时涵盖当前检查点状态、内核瞬态窗口保留的未落盘提交，以及可靠保存队列中尚未完成投影移交的批次引用。当存储背压导致部分提交暂存于内核窗口尚未进入保存队列时，初始化过程仍须从内核保留窗口获取引用。恢复提交可能已收束早期轮次，且最新检查点已裁剪该轮次及对应输入正文，但此类状态裁剪不得抹去保存队列中待投影批次所需的历史依赖。投影初始化必须完整加载相关的轮次、工具调用、消息条目及隐藏输入身份，再按队列提交顺序依次投影；禁止因找不到展示条目而将缺失输入猜测为隐藏输入，也不在投影报错后执行事后补查或重放。

## 15.6 完成读取与内部执行查询

对外 Timeline 的 Latest/Before、完成序号/epoch 游标、冻结详情与有界补发统一由 Session 提供，契约归 [26](./26-timeline-content.md)。HistoryStore 的完成 reader 只读 timeline_records，与内存 pending 合并后返回同形原子；不保留旧 UI 的 ordinal/revision 分页、Around、字段 patch 或旧表 fallback。

history_items、history_turns、输入身份、工具交付和 checkpoint 保留执行恢复及子智能体审查职责。其内部按 ordinal/write_seq/身份读取不得作为第二 Timeline 正文源；仍有独立执行消费者的查询保留其真实领域名称，不以转发别名维持旧 UI API。数据表和载荷升级只能在 [17](./17-studio-storage.md) 的正式迁移 preparation 内完成，正常 reader 不解码旧格式或自动清库。

### 可靠计量投影与缺口来源

同一提交的模型回执在准备边界提取为绑定 Thread、效应序号和调用身份的不可变计量事实，供实时累计、可靠累计、按用途费用及统计交接复用，不为每个消费者重新解析完整正文。可靠历史事务成功后直接返回已提交的轻量计量结果与材料变化；正常提交不紧接着回读完整检查点，恢复时仍从权威存储读取。

Studio 的 `PreparedEffect` 持有共享的 `PreparedAccounting`；准备时校验调用身份与冻结绑定，轻量解码不得省略回执与可见正文、工具绑定的关联校验。已提交的绝对费用投影只在金额或未定价状态变化时交接；未受理时保留最新材料做有界重试，不通过定时回读完整检查点补偿。重试耗尽与真正丢弃须明确报告统计缺口，不能把仍保留待重试的暂态错误当作已经丢失的事实。

累计缺口按终态、用途及缺失字段或矛盾原因解释，并保留最多 `8` 条最近来源样本及最近主模型终态完整性。累计缺口不会因下一次完整调用消失；输入缓存样本覆盖与总体用量完整性分别表达。未知贡献不增加已知词元，却不能解释为真实零消耗；取消只说明收束时保留到的事实，不证明供应商从未发送用量。新诊断与累计值共用效应幂等和检查点事务。

## 15.7 调用调试日志与性能统计

模型与工具调用诊断采用版本化的 JSONL 滚动日志存储，不参与会话冷恢复、上下文压缩或可靠累计计费。诊断记录队列仅接收调用身份、模型标识、上下文版本号、重试关联、词元计量、分段计时、错误摘要及当次调用结果，不接收完整的 `ThreadEffectBatch`、全量历史输入上下文或重复的工具声明列表。单条诊断记录上限为 `1 MiB`，超出部分显式标记诊断截断，不影响可靠的聊天历史正文。诊断日志写入或过期清理失败仅上报诊断缺口，绝不阻塞可靠的会话状态提交。

JSONL 日志单文件段上限为 `16 MiB`，按 UTC 自然日跨日轮转；系统在应用启动后、运行期每 15 分钟以及文件段轮转时执行过期清理，保留最近 7 天记录且日志正文总容量不超过 `256 MiB`。单条记录按精确时间戳判定 7 天保留期；文件段按 UTC 自然日归组，唯有当整个自然日的所有记录均已超过保留期时才删除该文件段，不得在自然日零点提前淘汰当天仍处于保留期内的记录。全局唯一的诊断写入器串行协调日志轮转与文件清理：若删除失败则保留可重试责任；当总容量触顶时直接拒绝新诊断写入，防止磁盘占用无界增长。损坏或未写完的尾部半行记录不作为完整事件读取。SQLite 诊断索引（`calls.sqlite`）仅覆盖当前存活的日志段，支持重建并随日志段淘汰同步清理；日志缺失、已过期淘汰、单条截断与写入故障在查询结果中必须明确区分。

主模型调用、上下文压缩、自动标题生成与自动安全审查的累计词元用量及费用统一由可靠状态副作用幂等折叠，并与会话检查点在同一事务中持久化；全局统计仅维护带版本号的轻量汇总投影。性能窗口保留最近 `3000` 条当前统计口径的成功调用样本，允许单项用量或计时未知；汇总再筛选成对有效样本。历史与汇总同源于轻量 SQLite 性能投影，不回读 JSONL，也不受诊断日志七天保留期影响。样本保留真实调用身份、用途与计时观测来源，未知输出不折算为零。严禁为计算账单而回读调试日志正文。旧版调用库迁移先保全既有累计摘要，再转换仍可证明的事实；迁移不得将新旧累计值相加。

调用写入器保留有界队列和短批事务，所有 mutation 在共同边界执行独立保存点，局部失败不留下半份 locator/性能样本，也不污染其他有效项。最终编码、散列与长度一次准备后复用；日志同步按同批触及的文件段合并，轮转前同步旧段，文件屏障成功后才能提交引用它的索引和确认成功。半行修复、完整孤立行恢复、完整性校验和容量责任不因批量优化而放宽。

绝对费用摘要只在材料变化时交接，同一 Thread 待处理摘要合并为最新有效版本，仅性能样本变化时裁剪。调用队列仅接纳真实的 attempt、工具交付、Billing 和已提交绝对 Summary 材料；不含调用材料的状态副作用没有诊断保存义务，不分配 ticket、不入队、不写调用库，也不因调用写入器停止或容量不足而制造统计缺口。`history.sqlite` 的可靠水位是唯一会话保存确认，不在调用库维护覆盖全部状态副作用的第二份水位。

调用写入器发布实际材料的类别代次和全局处理票据；已处理 ticket 可以包含明确拒绝，不能命名或解释为成功耐久水位。真实失败、重试与 gap 分别表达，拒绝不会推进成功材料代次。逐 Thread 诊断 effect 水位、其后台观察及空效应合并机制不再存在；可靠历史确认和实际调用队列处理分属不同观察，不用逐 Thread SQL 轮询、虚构空操作成功或新增缓存替代退役账本。已有绝对 Summary 的有界交接在原保存所有者内收束，后到费用仍正常发布，不另建补偿保存器。

## 15.8 SQLite 配置与关闭收束

所有 SQLite 数据库连接默认启用以下配置：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

每个数据库仅由单一逻辑写入器批量执行短写事务；历史分页查询在单次短只读事务内完成，不跨用户滚动操作持有数据库事务。可靠保存屏障仅等待发起时刻固定的目标水位落盘，不等待整个系统进入空闲状态。调用诊断的全局票据明确区分 `admitted_ticket` 与 `processed_ticket`；处理屏障只确认实际材料已处理，成功物化、错误与缺口仍须独立观察。

会话关闭流程先封闭准入并收束当前在途工作，随后提交真实的终态副作用；对话历史与最终检查点在同一事务中到达固定写入水位后，方可释放会话所有者。若持久化保存失败，会话保持 `Closing` 状态并留存所有者、未保存事实与重试入口。会话数据库连接与写入任务按需创建，当会话处于空闲状态且无活跃订阅、无在途执行、无待保存数据时自动释放。

会话关闭（`close`）与显式刷盘（`flush`）两项控制命令在“会话所有者正在运行轮次或因存储背压暂停在轮次内部”时同样保证可达：`close` 在投递关闭命令前先触发中断信号（取消在途模型与工具调用，并唤醒处于存储安全间隙的等待），使当前轮次安全收束，随后由所有者外层循环处理关闭命令，确保最终固定水位保存不会因背压暂停而死锁；显式 `flush` 则通过会话所有者的**有界邮箱（mailbox）**投递（与显式恢复继续共用同一可达路径），因为暂停中的轮次仅在存储安全间隙服务邮箱，若将 `flush` 放入仅在空闲时轮询的外层命令队列，就会陷入“等待那个正等着被刷盘的轮次自己结束”的死锁。`flush` 的等待目标在所有者处理该邮箱请求时固定为当时的已接纳水位（`admitted` sequence），后续新准入的提交不会推远本次屏障；`flush` 仅负责推进落盘，不启动新工作，也不解除存储暂停。

## 15.9 冷恢复与格式演进

激活会话时，在同一个只读事务中联合校验最新检查点、当前模型上下文与历史数据库水位；若发现数据损坏或水位不一致则明确报错拒绝激活。旧版 `v2` 的 TOML 检查点按需迁移时，可校验上一版备份文件并发布显式恢复诊断，但禁止将检查点挂载到水位不匹配的历史库。冷恢复统一将遗留的 `Running` 状态收束为 `Interrupted`，不重建模型连接、工具实例、外部子进程或取消令牌，也不重放任何历史副作用；后续需要继续执行时，由 Studio 重新装配当前服务实例。

重新激活已关闭的会话会将会话生命周期状态置回 `Open`，并将该变更作为一次新的状态提交落盘。挂载存储后端时从检查点初始化的已落盘水位仅证明历史提交已持久化，并不涵盖本次重新激活产生的新提交。因此，恢复后的首次 `flush` 仍须等待本次新接纳目标对应的状态副作用与检查点在同一事务中落盘；唯有当该新目标已确认落盘且后续无新提交时，保存屏障才可直接返回而无需等待磁盘写入。

已提交的待决交互（`Pending Interaction`）属于可持久化的逻辑状态，而非随进程退出自动作废的瞬态运行资源。正常关闭会话或退出应用时，检查点完整保留待决交互的原始请求、身份、版本号及关联业务扩展，不隐式提交交互取消；关闭流程仍须停止并等待在途模型、工具与后台任务收束，且待决的权限请求不会因此获得跨重启的执行授权。重新打开会话时，直接从检查点原样发布待决交互，唯有用户的显式回答或显式取消命令才能推进其逻辑状态。恢复待决交互展示不会触发模型或工具执行，用户回答后产生的续接输入（`continuation`）沿用既有的原子提交与幂等去重契约持久化。应用正常退出前必须等待包含上述事实的最终检查点与历史水位栅栏落盘。

本次大版本断代不迁移旧版会话数据：删除原有完整 `ThreadCommit` 日志重放（replay）、旧会话读取与基于日志生成恢复状态的接口，不保留供正常路径或迁移调用的平行执行实现。旧共享 `sessions.sqlite` 在原路径完整保留，不打开、不导入；账号配置与系统凭据关联按 [20](./20-config.md) 安全升级。

通用 SQLite 存储仅保留受支持 `v2` 格式的离线升级能力；早于该边界的格式明确拒绝且不改写。受支持库中遗留的 effect 编码在专用迁移边界规范为当前格式，当前条目、历史提交内的对应条目及其完整性摘要必须同事务保持一致，稳定身份、提交顺序、正文事实与检查点水位不变。普通 effect 解码仅接受当前格式，不保留旧标签别名；历史条目的通用一致性校验不等同于重建旧 Thread 执行状态。嵌入式宿主应改用当前检查点、类型化 effect 历史查询与显式数据库迁移入口，不再使用旧 journal 读取或重放 API。

遇到未知的未来结构版本、损坏数据、缺失迁移路径或未知的必需生产者格式时，必须按失败关闭处理并完整保留原始字节；仅影响历史展示而未知结构的载荷则封装为 `raw` 类型历史条目保存。任何结构迁移均不得以清空数据库、重置为默认状态或“仅备份不转换”来代替。当内核通用会话存储结构从版本 7 升级至版本 8 时，唯一变更为新增 `thread_checkpoints` 表：既有状态副作用、条目与历史行原样保留，尚未写入过新检查点的旧会话在首次读取时返回空检查点，待下一次状态写入时自动落盘。

向轻量检查点的迁移完整保留公开的状态副作用历史查询能力。模型与工具调用身份去重账本仅记录调用身份与原始所属轮次，不保存请求或响应正文；上下文压缩、轮次结束与进程重启均不会清除去重身份。
